# 复盘：美术线为什么连续五轮被打回（2026-10-18）

用户第十二问原话：「总结为什么会出现这么多错误？是我们的底层还是制作方式出了
问题？到底是什么原因。」「在交工前不要再想着敷衍我了，这样都是浪费时间和功夫，
我不是瞎子。」「你每次能不能去搜索一下动漫立绘的参考啊？」

这份文件不写"将来会注意"，只写**查出来的原因**和**已经改掉的机制**。

---

## 结论先行

**底层（引擎 / rig / 物理 / 动作）没有问题。** 80 个部件、21 个动作、物理 2.0、
532 条 selfcheck + 1215 条素材闸全部跑得稳。崩的不是引擎。

**出问题的是美术生产方式**，具体是四层，外加一个真正的底层 bug。

---

## 第一层：我把"画"和"拆"的顺序做反了 —— 这是根本原因

Live2D 的标准流程（官方 PSD 教程 / booth 上卖的差分素材 / 所有画师教程）是：

> **画师先画出完整的差分立绘**（马尾那一版是整张重新画的），**再**拆成图层。

我做的是反过来的：

> 拿一张**鲍勃头**的成品立绘 → 挖开 → 把 AI **单独生成**的碎片贴上去。

每个碎片是一次独立的生成调用，彼此之间**没有共同的几何、光照、轮廓约束**。
贴到一起必然是"一坨头发缠在一起"——用户原话。这不是手艺不精，是**流程本身决定的**。

**已经改掉的**：从第十二问开始，发型按"这一档需要哪几类部件"**成套补齐**，
而不是"在原发型上加一个挂件"：

| 档位 | 收起 | 换上 |
|---|---|---|
| long | `hair_side_l/r`（齐腮短鬓） | `hair_sidelong_l/r`（垂到胸口的长鬓）+ 收窄后的 `acc_hair_long` |
| pony | `hair_side_l/r` | `hair_crown_pony`（**向后收拢的头顶**）+ 掠发两缕 + 马尾 |
| twin | `hair_side_l/r` | 掠发两缕 + 两条辫子 |

**仍然欠的**：真正彻底的做法是每个发型**整张重画再拆**。当前是"成套替换关键件"，
是朝正确方向走了一大步，但还不是教程里的标准流程。这条诚实记在这里。

---

## 第二层：我用数字代替了眼睛

我建了一堆闸门量覆盖率、宽高比、Lab 统计、剪影连续性。它们能抓**"有没有接上"**，
抓不了**"好不好看"**。更糟的是：**数字全绿给了我"已经交付"的错觉**。

今天这轮最典型的一例：新画的长发刘海，Lab 三个通道和参考池都对齐了
（L 78.79 对 80.90、a 6.47 对 6.77、b −8.81 对 −7.74）——**可它看着就是顶灰假发**。
统计上完美，视觉上废品。

**已经改掉的**：
- 每一轮交付前必须出**组合矩阵抓帧**（4 发型 × 戴/摘 = 8 格），人眼扫一遍；
- 闸门的定位从"验收标准"降为"**防回归的网**"，不再当作交付依据；
- 新件必须和**它要替代的那一件**并排看（LESSONS 222）。

## 第三层：我没有去看参考 —— 用户说对了

这是最该认的一条。五轮里我**一次都没有去搜过动漫立绘的参考图**，
提示词全靠想象，AI 返回什么就用什么。

第十二问按用户的要求搜了一次，**30 秒就看懂了之前一直做错的东西**：

> **长发的横髪也是长的** —— 从太阳穴一路垂到胸口，不是齐腮的短鬓发。

我之前每一版长发都保留着齐腮短鬓 + 背后挂一片长发 = **结构上根本不是长发**，
是"短发女孩背后挂了片头发"。用户说"不契合"，说的就是这个。

同理，**马尾的头顶必须是向后收拢的**，不是蓬松的鲍勃头顶加一条尾巴。

**已经改掉的**：动手前先 `image_search` 看真实参考，结论带 URL 落
`docs/REFERENCE_NOTES.md`。这条之前只写了"要查教程"，没写"**要看图**"——
文字教程讲的是**工序**，图才讲**长什么样**。两样都要。

## 第四层（真·底层 bug）：淡紫头发被洋红键系统性抠成半透明

这一条是实打实的代码缺陷，影响**所有**头发挂件。

`tools/make_attach_parts.py: key_alpha_soft()` 用洋红底抠图，判据是

```
excess = (R + B) / 2 − G        a = 1 − excess / 255
```

它的文档串里自己写着前提：「**前景本身不能是洋红系**」。
而**本项目的头发就是淡紫** —— R 和 B 都比 G 高，正好部分命中洋红判据：

| 颜色 | excess | 算出的 alpha |
|---|---|---|
| 淡紫 (200,190,225) | 22.5 | 0.91 |
| 再紫一点 (180,150,220) | 50 | **0.80** |

于是**整件头发**（不只是边缘）被抠成半透明。实测 `alpha>240` 的像素占比：

| 部件 | 修复前 | 修复后 |
|---|---|---|
| `acc_hair_crown_pony` | **1.9%** | 96.8% |
| `acc_hair_sidelong_l` | **18.8%** | 85.7% |
| `acc_hair_sweep_pony_l` | **26.8%** | 87.9% |
| `acc_ear_l`（猫耳） | — | 91.6% |
| `acc_hood_up`（兜帽） | — | 96.6% |

画面上就是"能看穿的头发"：发丝底下透出衣领、透出发卡。
**这个 bug 从猫耳那一轮就存在了**，一直没人发现，因为没有任何闸门在查 alpha 分布。

**已经修了**：新增 `harden_interior()` —— alpha 超过阈值的区域先腐蚀 2 像素得到
**内芯**，内芯一律补成不透明，只有外圈 2 像素的带子保留软过渡（抗锯齿还在）。
不去改 `key_alpha_soft` 本身，它算**边缘覆盖度**是对的，错的是把它用在内部。

## 还有两个反复出现的"观察链路"问题

1. **预览进程把 rig 读在内存里，改完不重启看到的是陈帧**（LESSONS 221）。
   第十一问据此连续做出两个错误判断，差点把正确的方案否掉。
2. **QA 拼图的合成方式会凭空造缺陷**（LESSONS 212，更早一轮）。

> 这两条是同一件事：**看到反常结果，先怀疑观察链路，再怀疑被观察的东西。**
> 这个项目里已经栽了三次。
