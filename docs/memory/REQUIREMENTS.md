## A25 玩游戏 / 陪玩（2026-10-14；范围经用户两次澄清，以本条为准）

**用户原话（第二次澄清，排他）**：「不是完全禁止网游，而是让他们可以在网游
也陪伴聊天和实时屏幕操作进行回应对话，而其他的可以真正的游玩。」

所以不是"哪些游戏能玩"，而是**按游戏类型分成三档能力**。档位是硬约束，
不是偏好 —— 网游永远锁在只读档，这既是守规矩也是技术现实（反作弊会检测输入注入）。

### 档一 · 观战陪聊（**所有游戏都能用，含网游**）

AI 看着你玩，实时说话。**零输入**——不碰键盘、不碰鼠标、不碰手柄。

- A25.1 **实时读屏**：按窗口/区域抓帧，帧率可调，不看时不占资源。
- A25.2 **看懂画面**：帧喂给视觉模型，得到结构化状态（血量/技能CD/小地图/结算画面）。
- A25.3 **实时回应对话**：看到关键事件就开口 —— 夸、吐槽、提醒、安慰。
  这正是 A27（neuro-sama 式实时回路）最典型的落地场景，两者共用一套事件流。
- A25.4 **绝不操作**：这一档在代码层面就不接输入通道，不是"默认关闭"而是"没有这个口"。
- A25.5 **英雄联盟一类网游强制锁死在本档**，不提供任何提升到档二/档三的开关。

### 档二 · 协议游玩（Minecraft，优先做）

- A25.6 用 **Mineflayer**（Minecraft 协议客户端）以**一个普通玩家**身份登录，
  拿**结构化世界数据**（方块/实体/背包/聊天），不是像素。**不装 mod、不截屏、不模拟键鼠。**
- A25.7 动作空间是**代码**（Voyager 已验证）：模型生成调用 Mineflayer 的脚本，
  跑通的存进**技能库**复用，越玩会的越多。
- A25.8 常用动作走**参数化命令**（照 MINDcraft：`!collectBlocks("oak_log", 1)`），
  只有复杂行为才现写代码 —— 可靠性差别很大。
- A25.9 **快慢分工**（实测：GPT-4 每动作 25 秒，本地 7B 300~500ms）：
  走位/躲怪/应答走**本地模型**，造房子/定目标走**云端模型**。直接依赖 A23 双路由。
- A25.10 生成的代码必须**限时执行 + 失败计数 + 熔断**（Voyager 的已知坑是
  反复试同一个错法、一直烧额度）。依赖 A30。

### 档三 · 手柄游玩（本地双人 / 局域网双人，非 Minecraft）

- A25.11 屏幕捕获 + 状态理解（复用档一的 A25.1 / A25.2）。
- A25.12 **输入用虚拟手柄**而不是模拟键鼠 —— 本地双人本来就是手柄分屏，
  虚拟手柄更贴合"第二个玩家"这个身份，也更容易做频率上限。
- A25.13 **全局急停热键**，任何时候一键切断输入。
- A25.14 进本档必须**逐游戏显式授权**，默认只读。

- A25.15 要有一张**游戏档位表**（游戏 → 允许的最高档位），网游条目**不可提升**。

  ← **已落地**：`config/game_tiers.json`（3 档 / 4 类别 / 7 个游戏条目）

## A29 统一权限模型（2026-10-14 审计补登，横切 A25/A26/A27）

P4 这批能力合起来意味着：AI 能**看屏幕、控键鼠、读文件、联网、常开麦克风**。
这几件事单独看都合理，凑在一起就是一个很大的攻击面 —— 而现在只有 A25.4 一句
「逐游戏授权」在管它。必须有统一的权限模型，否则每加一个能力就多一个后门。

- A29.1 能力按**危险度分级**：只读（看屏幕/读文件）< 发声 < 联网 < 控键鼠 < 写文件/执行代码。
- A29.2 每一级要**独立开关**，默认全部关闭，开启要用户显式确认一次。
- A29.3 **全局急停**：一个热键切断所有"动手"类能力（键鼠控制、代码执行），任何时候可用。

## A34 A33 的边界与校准（2026-10-15，用户授权："你可以自行判断我的规则，做出边界以及优化"）

A33 的内核是对的，它针对的是**可量化的真实失败**：2026-10-14 一天翻了四条自己的结论，
没有一条是算错，全是"没验就下结论"。但原话里有两处按字面执行会产生负作用，
用户明确授权调整，所以定成下面这版。**A33 正文继续有效，A34 是它的执行口径。**

- A34.1 **"再三检查"改成"至少两种不同方式检查"**。
  同一个方法查三遍，错三遍还是错三遍。真正能翻案的是**换一种方式**：
  做负控 / 找独立来源 / 用另一条路径重算。三者至少占一种，外加"命令·数字·路径"三选二。
- A34.2 **只有"有后果的结论"进登记表** —— 三条判据占一条即算有后果：
  ① 会**关掉一条路**（否决类）；② **别人会照着做**（写进文档、变成规范）；
  ③ 会被**写进契约 / 配置 / 闸门**。
  反过来，**可逆又便宜的决定直接做**，错了改回来比登记一遍快。登记它们只会稀释这张表。
- A34.3 **用户的指令不是我的结论**。用户定的事（不要豆包、云端音色、游戏三档、
  形态先留空）只记录来源与边界，**我不做"负控"去反驳它**，也不许用"我检查过了"
  当作推翻用户偏好的理由。要改只能由用户改口。
- A34.4 **反稀释**：`selfcheck` 分两栏报 —— **工程事实**（红了=软件坏了，拦交付）与
  **文档纪律**（红了=记账没跟上，当轮补齐）。闸按**规则**计数，不按"条目×字段"计数：
  2026-10-15 折叠前这两张表刷出 324 项（占 600 项的 54%），折叠后 52 项，
  **六次负控逐条复验，报红能力完全不变**。
- A34.5 **反膨胀**：登记表 ≤ 40 条（闸检查）。超了就把"已推翻且无人引用"的移进归档段。
  一张没人读的表等于没有表。
- A34.6 **负控写"不适用"的必须给替代检验**（路线选择类结论确实没法改坏重跑，
  但要说清楚拿什么代替：独立三次否决、可证伪的真机判据、明写代价）。闸检查。

## A33 下结论之前必须先查（2026-10-15 用户要求，★ 硬规矩）

用户原话：「我发现你自行推翻了很多自己得出的结论，下次再给出结论之前一定要仔细确认，
再三检查，旧结论可以推翻。但是检查必不可少。」

**允许推翻旧结论，不允许不检查就下结论。** 这是对 2026-10-14 那轮的直接纠正 ——
那一轮推翻了自己四个结论（踮脚鞋会变扁 / 脚部拆件否决 / 异号等量就算修好 /
docs.live2d.com 不可达），每一个都是**当初下结论时少做了一步验证**。

- A33.1 **任何有后果的结论都要先写"前提"**，并且**前提本身必须被验证过**。
  踮脚那次翻车的根因不是结论算错，是**前提（"鞋会变扁"）从没被验证**。
- A33.2 **否决类结论的标准更高**：否决会关掉一条路，代价最大。
  否决前必须给出"如果反过来会怎样"的检查，不能只拿一次模拟就定案。
- A33.3 **结论要带可复算的证据**：命令、数字、文件路径三样至少有两样。
- A33.4 **能做负控的必须做负控**：闸门要故意改坏看它红不红，
  测量要有一个"确定不受影响"的对照项。
- A33.5 **否定结论标注复查触发条件**（"什么情况下这条会失效"），
  因为否定结论会过期（LESSONS 81：'docs.live2d.com 不可达'就是这么错的）。
- A33.6 落点：`docs/memory/DECISIONS.md` 结论登记表 + `check_decisions` 闸，
  **每条有后果的结论都要登记**，字段不全就判红。

## A35 VTuber / VRChat 生态接入：一条 OSC 总线（2026-10-15 用户提问后确认要加）

用户原话：「能否制作接入 vrchat 以及 3d 模型控制」。查完官方文档后的结论是
**这不是几件事，是一件事**：VRChat、VMC Protocol（VSeeFace / Warudo / バーチャルモーション
キャプチャー）、bHaptics、TouchOSC 全都走 **OSC over UDP**，报文格式是同一个。
做一条总线，上面这些顺带全通。OSC 报文自己极简（地址串 + `,` 开头的类型串 + 大端参数，
各自补零对齐到 4 字节），**纯 C 实现大约三百行，不引入任何依赖**。

- A35.1 **发到 VRChat**（我们当 client → UDP 9000）
  - `/avatar/parameters/<名字>` 只吃 Int / Bool / Float，**类型对不上 VRChat 会静默丢弃**
    （官方原文：type mismatch is silently ignored）——所以映射表必须带类型，且要有闸。
  - `/chatbox/input`：把小寻的台词打进 VRChat 聊天框。
  - 小寻的 mood / 动作 → avatar 参数，走**可编辑的映射表**（`config/osc_map.json`），不写死。
    因为参数名由 avatar 作者定义，每个模型都不一样。
- A35.2 **从 VRChat 收**（我们当 server ← UDP 9001）
  VRChat 持续广播内置参数：`Viseme`(Int 0–14)、`GestureLeft/Right`(Int 0–7)、
  `VelocityX/Y/Z`(Float)、`Grounded`/`Seated`/`InStation`/`MuteSelf`/`AFK`(Bool)，
  换模型时还会发 `/avatar/change`。
  **这是 A26（陪伴联机）和 A27（实时读屏回应）在 VRChat 场景下最便宜的信号源** ——
  不用截图、不用 OCR、不用模型推理，游戏自己把结构化状态送上门，延迟是 UDP 级。
- A35.3 **VMC Protocol**（Marionette 39539 / Performer 39540，现行 V3.1）
  收 `/VMC/Ext/Bone/Pos`（Unity HumanBodyBones 名 + 位置 + 四元数）和
  `/VMC/Ext/Blend/Val` + `/VMC/Ext/Blend/Apply`（**必须攒到 Apply 再一次性生效**，
  这是规范明写的）。我们是 2D，骨骼位置用不上，但 **BlendShape 可以直接驱动小寻的脸**：
  用户拿 VSeeFace / waidayo 对着摄像头，小寻跟着做表情 —— 等于白捡一套面捕，
  我们一行面部追踪代码都不用写。注意 VRM0 与 VRM1 的表情名不一样
  （`Blink_L`↔`blinkLeft`、`Sorrow`↔`sad`、`I/U/E/O`↔`ih/ou/ee/oh`），**收的一侧要做转换**。
- A35.4 **明确不做**：OSC Trackers（`/tracking/trackers/1..8`）是喂全身 IK 的，2D 立绘没有意义。
- 落点：T32。**先做 A35.1 + A35.2**（当天就能看到效果），A35.3 随后。

## A36 3D 模型控制（2026-10-15；分三层，只承诺前两层）

用户问的「3d 模型控制」有两种完全不同的理解，成本差两个数量级，必须分开说：

- A36.1 **控制别人的 3D（做，和 A35 是同一件事）** —— 我们当 3D 的"大脑和嘴"，
  不当渲染器。通过 OSC 总线驱动 VRChat / VSeeFace / Warudo / VMC 里**已经跑着的** 3D 模型。
  用户现有的 3D 生态全部可用，我们的渲染成本是**零**。
- A36.2 **读得懂 VRM（做，中期）** —— 解析 `.vrm`（本体就是 glTF 2.0 二进制 + VRM 扩展），
  取出 BlendShape 名单、Humanoid 骨骼名单、缩略图、作者与授权元数据。
  **纯数据解析，不渲染**，成本可控。价值在于：知道对面模型有哪些表情，映射表才能自动生成，
  而不是让用户手敲参数名。
- A36.3 **自己开窗口渲 3D（可行，但排在 2D 主线之后）** ——
  **这一条我本来准备否决，实测把自己否了**：写了个纯 C 软光栅基准（`/tmp/b3/bench3d3.c`，
  848×1360、2 万三角、3 层 overdraw、蒙皮 + 透视正确 UV + 双线性纹理 + MToon 描边遍），
  单线程 **116.7ms（8.6fps）**；去掉纹理与描边是 41.3ms（24fps）。
  对照我们 2D 现在一帧 30.8ms —— 3D 贵约 4 倍，**贵，但不是数量级不可能**。
  再算上分块多线程（2D 上实测 1.66×/2 核）和用户本机的核数，30fps 是够得着的。
  所以**不否决，只排序**。真正的成本不在帧率，在工程量：glTF/VRM 解析、蒙皮、
  morph target、半透明排序、MToon、抗锯齿、摇骨物理 —— 都是 2D 管线里一样都没有的东西。
  完整理由、反向检验与解锁条件见 DC42。
- 落点：T33。

## A37 唱歌（2026-10-15；分三档，S1 先做。**当日用户质疑后大改过一次，见 DC45**）

**先把话说死：TTS 不会唱歌。** 语音合成和歌声合成是两套模型，
拿 TTS 硬凑旋律只会得到用户已经否过两次的那种机械音。

**★ 但我第一版把问题框错了**：我默认"唱歌 = 从零合成歌声（SVS）"，于是整条路被算得又贵又远
（要乐谱、要 1–3 小时标注、要 GPU 训练）。用户当场质疑「那网上那些 AI 唱歌怎么来的」，
查下来**网上绝大多数 AI 唱歌根本不是合成，是换音色**：拿一首已有的歌，
把人声换成目标音色，旋律节奏咬字情感全部来自原唱。**不需要乐谱，不需要标注。**
修正后的三档：

- A37.1 **S1 跟唱 / 对口型（先做，便宜且效果立竿见影）**
  音频从哪来都行（用户自己唱的、OpenUtau/DiffSinger 渲好的、买的、下载的），
  我们负责**口型 + 节拍 + 表情同步**。关键是**不需要音素对齐**：
  短时 RMS 包络 → 嘴开合（`ParamMouthOpenY`），基频 F0 → 头部摆动与眉毛高度，
  起音检测 → 身体节拍。纯 C 几百行，没有模型、没有依赖。
  **这个底座不止给唱歌用** —— TTS 播放、用户麦克风、系统音频都能复用（见 A39）。
- A37.2 **S2 小寻自己唱 = 换音色（RVC，首选，比原计划便宜一个量级）**
  定义「歌声引擎适配器」接口，**把 RVC 当外部进程调用**（它是 Python+PyTorch 栈，
  官方仓库当前 334 个文件里没有 onnx，塞不进我们的纯 C 运行时 —— 这点已核实，见 DC45）。
  流程固定三步：**UVR5/Demucs 分离人声伴奏 → RVC 换成小寻音色 → 混回伴奏**。
  - **成本**（RVC 官方 README + 社区实测）：训练数据**只要 10 分钟低底噪干声**、
    不需要任何标注；推理 4GB 显存、训练 6GB；RTX3060 上 200 轮约 **1–2 小时**。
    CPU 能推理但慢 10–20×（离线出一首歌可以接受，实时不行）。
  - **音色从哪来 —— 一条干净的闭环**：小寻已定案走云端 TTS 音色（2026-10-11）。
    那就**用云端 TTS 生成 10 分钟小寻说话音频 → 训 RVC → 小寻会唱歌**，
    音色和平时说话一致，也不碰任何真人的声音权。
    **⚠ 但这一步有未解问题**：拿商业 TTS 的输出去训练衍生模型**可能违反服务条款**，
    我没查到定论 —— **动手前必须先读 Azure / OpenAI 的条款，不许默认可以**（DC45 复查触发③）。
  - 备选引擎：so-vits-svc（数据要 30min–2h、8GB 显存、训练更久；第三方 benchmark 里
    说话人相似度 0.79 / UTMOS 3.95，均低于 RVC v2 的 0.85 / 4.19）。
  - **真·歌声合成（DiffSinger / NNSVS）降为后备**：它解决的是"没有原唱也能唱"，
    代价是要乐谱 + 1–3 小时标注 +（DiffSinger 自动建库）只支持中文。
    等 S2 跑通、确实需要"唱没人唱过的歌"时再上。
- A37.5 **"想要一首全新的歌"走生成服务（Suno / Udio）** —— 词曲唱编混一次出。
  **Suno 没有官方公开 API**（只有第三方转发，约 $0.55/首），免费档无商用权；
  且 2026-09-18 又被 Universal / Sony 起诉，**版权环境不稳定**。
  所以只做成**可选的外部供应商**，不作为主路径，并遵守 A28 的排除清单。
- A37.6 **★ 版权边界（必须写进 UI，不是免责声明了事）**
  - 《民法典》第 1023 条：**自然人声音参照肖像权保护**。只要生成的声音能被识别到
    某个特定真人且未经许可，就可能侵权 —— **与是否直接复制原音频无关**。
  - 翻唱他人歌曲还会碰到**词曲著作权**，用原曲分离出的伴奏还会碰到**录音制作者权**。
  - **"仅供学习 / 非商用"不免责**：声音权属人格权，不以盈利为前提。
  - **→ 我们的产品形态天然是干净的那一侧**：小寻是原创虚拟角色，音色来自我们自己的
    TTS 通道，不碰真人声音权；只要歌曲本身是原创或已授权（或 Suno 付费档生成），
    整条链是干净的。so-vits-svc 作者自己的话正是这个意思：
    「这个项目是为了让开发者最喜欢的动画角色唱歌而开发的，任何涉及真人的东西都与开发者的意图背道而驰」。
  - **产品上要做的事**：① 不内置任何真人歌手音色、不提供"一键 AI 某某"；
    ② 导入第三方音色模型时弹明确的授权提示；③ 输出文件打 AI 生成标识。
- A37.3 **S3 实时 SVS（不做）** —— 边想边唱，当前开源生态做不到可用延迟。
- A37.4 **风险要事先说**：还有一条更便宜的路是拿 TTS 单字做变调拼旋律，
  但本地音色已经因为"机械音"被用户否过两次（2026-10-11），这条大概率也会被否，
  **所以不自作主张去做，等用户点头**。
- 落点：T34。

## A38 对话语气变化（2026-10-15；四项里最便宜，应当最先做）

- A38.1 **语气标签由模型输出，不靠关键词猜** —— LLM 回复里带 `<mood:excited>` 这类标记，
  我们剥离后**同时**喂给 TTS 和立绘。关键词匹配猜情绪是死路：同一句话在不同上下文里语气相反。
- A38.2 **云端 TTS 侧**（已定案走云端音色）
  - Azure：`<mstts:express-as style="cheerful" styledegree="...">`，
    **styledegree 官方区间 0.01–2.0**，可连续调强度 —— 这正好能接 mood 的强度值。
    配套 `<prosody>`/`<break>`/`<emphasis>`/`<phoneme>` 做细粒度控制，并支持逐词时间戳。
    **注意**：style 列表按语言不同，日语当时只有 chat / cheerful / customerservice 三种，
    **中文有哪些必须实测，不许照抄文档清单**。
  - ElevenLabs v3 / v4：走 **audio tags**（`[happy]` `[sad]` `[whispers]` `[laughs]` `[sighs]`），
    官方明说**这两个模型不支持 SSML `<break>`**，停顿要用 `...`，强调用大写。

  - 两家风格不同：**Azure 是数值可复现，ElevenLabs 是表现力更强但不可复现**。
    适配层要抹平：对上统一成 `(mood, intensity 0–1)`，对下各自翻译。
- A38.3 **语气和脸必须同源** —— 同一个 mood 既改 TTS 又改立绘表情，
  不能出现"声音在笑、脸是平的"。这条要有闸。
- A38.4 不绑死供应商：遵守 A28（**绝对不要豆包**）。
- 落点：T35。

## A41 人格与主体性（2026-10-15；把 A19 的「L6 人格层」从一行展开）

用户原话：「能不能像 neurosama 一样模仿人，而且设置几种变量，工作模式，模仿人的模式等等等等，
需要吗？还是说有更好的办法」。

**先回答"需要吗"：需要，但不是做成"几种模式"。** 理由见 A41.2。
**"模仿人"要分两种**，混在一起会出事：
① 模仿**某个具体的人**（声音/说话方式）—— 碰《民法典》1023 条声音权，**不做**（见 A37.6）；
② 像人一样**有连续的主体性**（有脾气、会累、记得你、会自己开口）—— 这才是 neuro-sama 的本质，**要做**。

- A41.1 **人格放在哪** —— neuro-sama 的人格**烤在权重里**（微调 2B 模型），
  prompt 只给情境。我们走云端 API，**微调这条路默认是关的**（DC46），
  所以人格只能靠工程手段撑：
  **L0「魂」一份不可变的身份定义，每轮/每次会话重新注入并钉在 context 顶部**。
  不能指望"开头说一次她就记得" —— 注意力会被后面的对话稀释掉。
- A41.2 **★ 为什么不做"几种模式"（这是对用户提问的正面回答）**
  做成 `工作模式 / 陪伴模式 / 模仿人模式` 这样的互斥开关，有三个必然的坑：
  ① **人不是开关式的** —— 硬切换会让她在切换瞬间像换了个人，反而更假；
  ② **模式会爆炸** —— N 个独立维度就有 2^N 种组合，最后要么漏要么互相打架；
  ③ **切换时记忆和人格怎么继承说不清** —— Neuro 和 Evil Neuro 的做法是
     **两个独立程序 + 两份独立记忆**，不是一个程序的两个开关。
  **更好的办法 = 连续变量 + 预设，而不是模式**：
  - **一组连续状态变量**：精力、心情（valence/arousal 两轴）、对用户的亲近度、
    专注度、话痨度。随时间和事件连续演化，**不跳变**。
  - **"模式" = 这些变量的一组预设值 + 一组权限开关**（比如"专注工作"= 话痨度压到很低 +
    主动打断只允许紧急 + 不播音乐），**是 preset，不是 if-else 分支**。
    用户可以存自己的 preset，这就天然解决了"要几种模式"的问题 —— **要几种由用户定**。
  - **真要第二个人格**（像 Evil Neuro）→ **开第二个实例 + 第二份记忆**，不是加个开关。
- A41.3 **人格漂移必须可度量，否则等于没做**（这条是 A41 的验收闸）
  参照 PersonaGym 的做法：一份固定剧本，在第 10 / 50 / 100 轮分别测人格一致性。
  **已知基线：普通 LLM 10 轮 90%+、100 轮掉到 60–70%。** 我们要比这个好，
  好多少要有数字。量不出来就不许说"人格做好了"。
- A41.4 **context 不是越大越好** —— context rot 的甜点区是 **8K–16K tokens**。
  所以"把所有记忆都塞进去"是错的方向，要靠 A43 的分层与衰减去挑。
- 落点：T38。

## A42 主动性：她得会自己开口（2026-10-15；把 A27.4 从一行展开）

A27.4 早就写了"没人说话时角色也会自己开口"，但一直只有一行、没有设计。
**这是"桌面上的工具"和"住在桌面上的人"之间的分界线**，不是锦上添花。

- A42.1 **心跳循环（heartbeat）**：`醒来 → 观察 → 判断 → 行动或继续睡`。
  不维持长驻上下文（贵且脆），由调度器定期唤醒、注入当前状态、给一次行动机会；
  不值得行动就继续睡，**不输出任何东西**。
- A42.2 **主动性分级，默认不要给满**（业界常用的 5 级，我们取前 3 级）：
  L0 纯被动 → L1 定时触发（整点、日程）→ L2 事件触发（你回来了 / 切到某个程序 / 长时间没动）
  → L3 信号触发（阈值：连续工作 2 小时）→ L4 机会触发（她自己判断"现在适合说句话"）。
  **先做到 L2–L3，L4 要等 A41 的状态变量稳定之后**。
- A42.3 **★ 什么能自己做、什么必须先问 —— 一条线划死**：
  **可逆且只在本机内部的**（说句话、换表情、记一条笔记、调整自己的状态）→ 可以自主；
  **不可逆或触及外部的**（发消息给别人、发帖、花钱调 API、改用户的文件）→ **必须先问**。
  这条和 A29（统一权限模型）、A30（成本熔断）是同一套闸。
- A42.4 **反打扰是硬需求，不是选项**：
  免打扰时段 / 专注时自动降频 / 同样的话 24 小时内不重复（内容哈希去重）/
  **只在空闲时做主动动作**（这是天然的限流）/ 连续被忽略 N 次就自动降频。
  主动型 AI 犯错的代价比被动型大得多 —— 被动的你不问它就行了，主动的它已经打扰你了。
  **所以可中断性和可观测性是第一原则**：她为什么开口，要能查。
- A42.5 **要能量"吵不吵"**：记录 主动发言次数 / 被用户回应的比例 / 被忽略的比例。
  参考清华 Proactive Agent 的四个指标：需求遗落、静默应答、正确检测、错误检测。
- 落点：T38。

## A43 记忆的生命周期：分层 + 遗忘（2026-10-15）

我们有"记忆区"（G52 / T20），但只写了"有这么个区"，**没写记忆怎么活、怎么死**。
而这恰恰是同类产品拉开差距的地方（30 天事实召回：Character.AI ~15% vs Kindroid ~80%）。

- A43.1 **四层，各有各的寿命**（neuro-sama 和主流伴侣产品是同一套）：
  | 层 | 内容 | 寿命 |
  | --- | --- | --- |
  | L0 魂 | 身份定义、说话方式、底线 | **不可变**，每轮重锚 |
  | L1 核心记忆 | 你是谁、重要约定、关键事件 | **不衰减** |
  | L2 工作记忆 | 最近几天发生的事 | **随时间衰减**，几周后淡出 |
  | L3 会话记忆 | 当前这段对话 | 关掉就没了 |
- A43.2 **谁决定什么进 T1** —— Neuro 的做法是**她自己从短期里挑**，Vedal 偶尔清理。
  我们照这个来：**她提名 + 用户可见可改可删**。不可见的记忆等于定时炸弹。
- A43.3 **召回要的是"准"不是"多"** —— 一股脑全倒出来反而像机器人。
  按 相关度 × 新近度 × 被回忆次数 加权。
- A43.4 **要能改、能删、能导出** —— 存错的事实会一直复读；这也是隐私底线。
- A43.5 **"重建"比"检索"更对** —— 不是"找出相似的旧消息"，
  而是"现在这件事的状态是什么"。旧状态被新状态**取代**，不是并存（否则会自相矛盾）。
- 落点：T38。

## A44 话轮与打断（2026-10-15）

我们的语音链是 `VAD → STT → LLM → TTS` 单向跑完，**没有"她说一半被打断"，
也没有"她判断该不该现在插话"**。真人对话里这两件事无时无刻不在发生。

- A44.1 **她说话时用户开口 → 立刻停**（TTS 可中断、立绘口型同步停）。
- A44.2 **等待延迟可调** —— neuro-sama 就是靠一个可调 delay 判断"对方说完了没"；
  对方在延迟内又开口，她要**收回**自己准备说的话。
- A44.3 **唱歌/长内容要能被打断**（Neuro 的说话模型就会打断唱歌模型，这是已知行为）。
- A44.4 **被打断后不要从头说**，要接着说或跳过。
- 落点：T38。

## A45 更生动的脸：星星眼这一类「瞳孔差分」（2026-10-16）

用户看着截图 6（整只瞳孔变成金色大星星）问「能不能做出星星眼等更加生动的面部形象」。
**先说清楚现状和目标差多远**，别让人以为改个开关就有：

- 我们**已经有**的叫 `eye_hl_style`（Pose 组 round / star / none），切的是**虹膜上那一点高光**：
  `eye_hl_star_l@2x.png` 只有 **40×40、172 个不透明像素、纯白 (254,253,246)**。
- 截图 6 要的是**整只虹膜被星形取代**（金黄 + 内部渐变 + 外溢光芒），
  对应我们的 `eye_l_ball@2x.png`（**62×60，蓝 (80,122,158)**）。
- 所以这是**换虹膜**，不是换高光 —— 必须新画素材，归 G115。

设计口径（全部来自官方/社区，见 REFERENCE_NOTES 第二十四批）：

- A45.1 **一个参数管一类"特殊瞳"，彼此互斥**。Live2D 创作者 kawase 的原话是
  「きらきら目・ハート目は…同時発動しないので**同一パラメにまとめる**」——
  闪亮眼和爱心眼不可能同时出现，所以归到同一个参数的不同档位。
  我们**已有的 Pose 组就是这个语义**，照着加 `eye_iris_style`（normal / star / …）。
- A45.2 **差分件必须 clip 到眼眶**，并且**绑到眼睛开闭参数上**，否则闭眼时星星会留在脸上。
  （这是 surume1ka 教程里反复强调的一步。）
- A45.3 **星星眼不是一张静态贴图**。zombiefff 的"しいたけ目"做法是两层摇动：
  Sway1 按正负值**缩放**，Sway2 用 warp **上下左右突出**做闪烁，
  再把开闭/笑/呼吸/角度 XYZ 塞进 physics 的 input 制造随机。
  我们有 physics + deformers，这条能落地；**不做闪烁的话就只是贴了张星星，不"生动"**。
- A45.4 **可扩展到同一组的其他档位**：爱心眼、漩涡眼（晕）、`×` 眼。
  素材一次做不完没关系，Pose 组的结构要一次留够。
- 落点：G115 / T39.1~T39.4。

## A46 卖萌动作：手要能举到脸前（2026-10-16）

用户给了三张参考：截图 3「双手遮嘴的惊讶」、截图 4「强烈惊讶（双手张开举起 + 头发炸毛）」、
截图 5「双手捧脸」。**共同点是手必须离开身侧、举到头脸高度**，这是我们现在做不到的。

- A46.1 **现状的硬边界**：手臂是切件旋转，`ParamArmRA → arm_r.rot_deg × −6.0`，
  参数量程 ±1 ⇒ **只有 ±6°**。而"手举到脸前"需要肩 ~140°、肘 ~90°。
  硬转过去会撞上 G103 那条肘部硬折痕，而且袖子是垂着画的，转 140° 必然露馅。
- A46.2 **官方做法是"手臂差分"不是"硬转"** —— Live2D 模型作者（note.com/moimoi_sp）
  把 arm variations 和表情差分并列，在**画的阶段**就另画一套。
  对我们就是 D19 那条老规矩：**被遮挡/没画过的角度必须 AI 重绘**，不能靠几何变换硬凑。
- A46.3 **三个动作共用一套"举起手臂"素材**，差别在手的形状与位置：
  遮嘴（手背朝外、并拢在嘴前）／张开（五指张开、举到肩上）／捧脸（手心贴脸颊）。
  所以素材拆成「上臂举起 + 前臂举起 + 手×3 形状」，不是三整套。
- A46.4 **动作本身要有"预备 → 爆发 → 回落"**，不能线性插值过去；
  截图 4 还要配合头发炸毛（我们有 physics，能用 pulse 驱动）。

## A48 细微表情（微表情）必须做（2026-10-16，用户原话「但是细微表情也要做上」）

**来历**：我在汇报情绪特效（漫符）时写了一句「比做十个细微表情划算得多」，
用户当轮纠正：**「那就继续，但是细微表情也要做上」** —— 不是二选一，两样都要。
这条登记在案，防止我以后再拿"性价比"把它压掉。

**它和已有条目的区别（别搞混，三件不同的事）**：
- **A47.1 情绪强弱两档** = 同一个情绪的**音量旋钮**（小惊讶 / 大惊讶）。
- **A48 细微表情** = **幅度很小、但本身是独立语义**的面部变化。
  不是"惊讶的 20% 版"，而是"她在走神""她不太信""她想笑没笑出来"这种。
- **T43 漫符** = 贴在身上的**符号**（汗/💢/云），是外挂图层，不改脸。

**范围（待细化，先占位）**：
- 眉：单边挑眉（怀疑）、双眉微蹙（为难）、眉尾下垂（委屈但没哭）
- 眼：视线游移/飘开（走神、心虚）、眨眼频率变化（紧张快 / 困倦慢）、
  微微眯眼（打量）、瞳孔轻微收缩放大（受刺激）
- 嘴：嘴角单边微扬（得意、无奈）、抿嘴（忍住）、嘴角轻微下压（不高兴但不生气）
- 复合：呼吸节奏变化（叹气前的吸气）、轻微点头/偏头的"附和"

**硬要求**：
1. **幅度小不等于可以糊弄** —— 要能在用户真实观看尺寸下看出来，否则等于没做（口径同教训 131）。
2. **必须能和现有表情/动作叠加**，不能互斥占用同一条轨（它本来就是"底噪"级别的表达）。
3. **要有自动的、无人触发的那一层** —— 细微表情最大的价值是"没人跟她互动时她也像活的"。

**落点**：T44。

### 分两类，不要混为一谈

- **加法类（耳饰 / 尾饰 / 装饰品）**：往剪影上/外加东西，底下画面不动 → 机器基本现成。

  换衣服要先知道衣服**底下是什么** —— 正是 D19「被遮挡区域必须 AI 重绘」的情形。

  1. **换色**：改 palette 重铺，零新素材。

1. **走声明式表**（延续 G117 / T43.2 的口径）：挂件的插槽、层号、父组、物理预设、

## A52 语音要有真人语感 + 二次元萌系少女音色（2026-10-17 用户第三问，四次追问才收敛）

> 3.（试听我找的两个外部真人音源后）「**两个都不对，又回到那种真人的粤语了**，

> 4.「你的这个语音你都不记得了吗？**截图里你自己做的**，只不过声音要**更萌更有情感**」

### 需求拆成两件事

| # | 要的是什么 | 判定方式 |
| --- | --- | --- |
| **A52-1 语感** | 一句话内部要有起伏：语速不恒定、停顿不只认标点、有重音、句尾有语调 | 闭眼听，能听出"她在说话"而不是"在念稿" |
| **A52-2 音色** | **动漫二次元美少女**，不是真人感、不是方言腔、不是青年女声 | 听感年龄下移；用户能从候选里指定一个 |

### 关键澄清（第 3、4 句带来的路线变更）

- **外部真人音源这条线作废**。用户试听后判定"又回到那种真人的粤语了" ——
  目标是**二次元**，不是"更好听的真人"。
- **基线是我们自己这套**（`edge-tts + zh-CN-XiaoyiNeural`，即用户截图里的小寻 teen 音色），
  要做的是**在它之上更萌、更有情感**，不是另起炉灶。

### 为什么之前"没有变化"（根因，详见 `docs/VOICE_EXPRESSION_PLAN.md §1`）

1. **通道**：实际走的 edge-tts 免费通道**不支持 SSML 情感标签**，
   `emotion_map.json` 的回退链永远落到最后一档 prosody；
2. **参数**：`plan.json` 的 style 全是 `+0%/+0Hz/+0%`，候选升调档从没启用；
3. **方法**：渲染器对一条台词只调用一次合成、整句一组参数 —— 没有能承载情绪的位置。

### 验收口径

1. **盲听（主判据）**：`characters/xiaoxun/voice/demo/` 下同一句话 × 六种情绪
   （neutral / happy / shy / angry / sad / sleepy），**不看文件名**随机播放，
   用户能把其中 **≥4 种**对上标签。
2. **A/B（回答"没有变化"那句）**：`voice/ab/` 下同一句话的"语感关 / 语感开"两版，
   用户能听出区别，且认为"开"更像人说话。
3. **不许发尖（一票否决）**：2026-10-17 用户实听判定"像小黄人和鼠来宝" ⇒
   任何让音色变花栗鼠的做法直接出局。机器判据：演出单里**每一段的 `|pitch| ≤ 14Hz`**
   （`_restraint.max_abs_pitch_hz`，自检第 4 项盯着）；人耳判据：盲听不许出现"氦气感"。
4. **音色选档**：`voice/samples/` 的候选里，用户**指定一个**作为小寻正式音色
   （同一句话、只变音高，排除语感干扰）。
5. **量化（沙箱自测，不依赖人耳）**：
   - 同一句不同情绪，**逐段参数不得完全相同**；多段句至少两种不同参数；
   - 切段拼回必须与原文**一字不差**；
   - 六种情绪的**时长**要拉开（终版实测：sleepy 比 neutral 长 22.4%、angry 短 7.6%）；
   - 选定音色后 `voice_pitch.py --measure` 量 F0 中位数，目标 **200~260Hz**。

## A53 — 需要参考图时，**优先生成完整的参考图**（2026-10-19 用户确认）

用户原话：「你发现没有，生成总体的参考图会省去很多的功夫。**以后需要参考图时优先生成参考图**」「这次的参考图生成完全符合我心里的预期，看到非常顺眼」。

这是对第十五问工序改正的**确认与推广**：不再「挖成品 + 贴 AI 单独生成的碎片」，
而是**先出一张完整的全身差分立绘，再从同一张图上拆件**。
好处在这一轮得到实证 —— 同一发型的后发、头顶、发梢出自**同一次落笔**，
发缕走向、高光位置、色相天然连续，「拼接痕迹」从定义上不存在；
而且几何可以**量出来**（模板 → body_full → rig 的坐标链），不用手调常数。

适用范围：发型、服装、配饰、表情 —— 任何需要"多个件互相配合"的造型工作。
与 Live2D 官方 PSD 教程同口径（先画完整差分立绘，再拆图层）。

### 验收口径

1. **模板层**：`selfcheck_repo.py::check_design_sheets` —— 7 张模板必须是
   1024×1536、鞋底统一对齐到 y=1479、sha16 台账与文件一致（换图不重套准就红）。
2. **切件层**：造型件的 `source` 必须指向 `sheetcut_*.png`，几何必须来自
   `cut_geometry.json`（即**量出来的**），不许在 `attachments.json` 里手填
   `pos_rel` / `sprite_h_rel` 这类常数。接线脚本 `tools/wire_sheetcuts.py` 幂等，
   重跑结果必须逐字节相同。
3. **成品层**：`check_assets` 的「差分发型与本体头发同源配色」（ΔE ≤ 5.0、
   ΔσL ≤ 6.0）与「藏承重件的档位都自带接管件」必须全绿；
   并且**每轮交付都要出四档实拍对照图**（`logs/asset_qa/hairstyles_*.png`），
   用眼睛看过再说话 —— 闸门全绿不是交付证据（用户第十二问）。
