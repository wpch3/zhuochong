### DC08 ✅ 姿势类动作用 `pulse`，不用 `bounce`（2026-10-14）

- 前提：`bounce = amp·sin(π·ease(t/dur))` 的峰值只是一个瞬间，不是一段保持。
- 证据：把 `eval_channel_wave` + `ZEASE_OUT_BACK` 在 Python 里逐行复刻，
  按 60fps 解析算出 **v>0.95 只持续 48ms**；改 pulse 后引擎实测抬起 ≥14px 持续 **693ms**。
- 负控：✅ 两种波形在同一条测量管线下对比（同一脚本、同一采样率）。
- 复查触发：引擎的波形或缓动公式改了，复刻脚本要同步改（否则算的是旧引擎）。

### DC09 ✅ 腿件不但要擦像素，还要**裁画布**（2026-10-14）

- 前提：引擎 bend 曲线的 `t` 是**贴图画布**的 0..1，不是解剖位置（读源码确认）。

- 复查触发：任何改贴图内容边界的工具都要问一遍"画布还代表原来那段解剖吗"。

### DC32 ✅ "动作时脸部模糊"不在渲染管线，在前端画质档（2026-10-15）

- 前提：**先验前提再下结论** —— 上一轮我记过"stroke 时脸部锐度 −40%"。
  这一轮复现时发现**那个测法是错的** —— 它在画布上框死一个矩形量梯度能量，
  而头一动框里的内容就换了（更多平坦皮肤、更少边缘），测的是构图不是清晰度。
  **旧结论作废**（A33 允许推翻，但必须复验）。
- 证据：改成"互相关配准后再量"，并把脸拆成眼区/嘴鼻区两块分别量：
  嘴鼻区 idle −7.4% / clicked −7.0% / stroke −10.6% / head_pat −11.1%，
  **全部落在 idle 自身的噪声带里**；只有眼区在 stroke(−37%)、head_pat(−34%) 掉，
  而这两个正是把眼睛按住半闭的动作 —— 掉的是"眼睛闭着细节少"，不是模糊。
  真正的模糊在显示层：`web/components/stage.js` 每帧请求 `/api/frame.png?s=60`
  （自动档第 2 级），再被 CSS 拉到 ~680px 高显示。同样显示成 424×680，
  引擎原生渲染眼区锐度 **1641**，先渲 466×748 再 bilinear 缩放只剩 **850（−48%）**。
- 负控：① 量了帧 PNG 的尺寸是否随动作变化（7 个动作 ×14 帧全是 466×748）→
  排除"动作让图变大被缩放"；② 冻结时钟后单独施加旋转/平移，锐度 −2.6%~+11.5%，
  而基线自身复测就漂 3% → 排除"旋转重采样导致模糊"；
  ③ 用户静止截图的裙宽 **155px 精确等于 s=75 档的裙宽 155px**，
  另一张 147px = 同档再被窗口宽度缩 5% → 正向锁定是画质档而不是别的。
- 复查触发：① 用户换了屏幕 dpr 或窗口大小后仍报糊 → 先看 `fitDisplay()` 算出的
  `s` 和 `img.style.height`；② 远程预览带宽不够时自动档会降级，**先降帧率到 6fps，
  再降分辨率**（故意的：清晰的 8fps 比糊的 12fps 好看），如果用户反过来嫌卡再调顺序。

### DC37 ✅ 渲染与 PNG 编码都按"行带"切开并行，闸是逐字节一致而不是性能数字（2026-10-15）

- 前提：scale 1.0 一帧 142ms（渲染 60 + PNG/传输 82），只有 7fps；用户要求"本地正常
  分辨率与帧率、放大到整个桌面仍清晰"。合成是 44 个部件按层序逐像素写 `fb`，
  不同 y 的像素互不影响 → **按行带切开天然可并行**（grep 确认 `compute_draw_state` 只读不写）。
- 证据：2 核沙箱（Xeon 2.60GHz）实测 —
  - 渲染 848×1360：51.0 → 30.8ms（**1.66×**）；1696×2720：217 → 128ms（1.69×）。
  - PNG 848×1360：91.5 → 42.1ms（**2.17×**）。拆开看原先是 滤波 17ms + deflate 72ms，
    其中 adler32 每字节两次 `%65521` 就占 14.3ms（改延迟取模 → 2.1ms，校验和一字不差）。
  - 端到端（HTTP 实测）：0.55 档 24→**42.9fps**，1.0 档 7.0→**12.1fps**，
    1.2 档 5.2→**9.1fps**，2.0 档 1.9→**3.6fps**。
  - 另外发现 `send_png` 在**写 /tmp 再读回来再 remove**，每帧三次文件系统往返，已改走内存。
- 做法：`zimg` 加 `clip_y0/clip_y1`，四个会写 dst 的函数（`zimg_clear` / `draw_impl` /
  `draw_tri` / `zimg_composite_masked_blend`）都尊重它；每条带各有自己的 scratch/maskbuf
  并在起线程前预分配。PNG 则是每条带自己滤波 + 压成一个 `BFINAL=0` 的 deflate 段
  （段末补空 stored 块对齐到字节），按字节拼接，adler32 按整份原始数据算 —— 即 pigz 的做法。
- 负控：**10 个变异，全部判红** —— 这才是这条结论的分量所在。
  ① draw_impl 忽略 clip → test_core 红 18 条（真 rig 79052 字节不同）；
  ② composite 忽略 clip → 红 1 条；③ draw_tri 忽略 clip → 红 13 条（34734 字节不同）；
  ④ 各带共享 scratch/maskbuf → 红 18 条（7877 字节不同）；⑤ 单线程路径不重置带缓冲 clip → 红 1 条；
  ⑥ 段末不补对齐块 → PNG 读不回来；⑦ 每段都写 BFINAL=1 → 读不回来；
  ⑧ adler32 只按半份数据算 → 红；⑨ adler32 批长改 65536（溢出）→ 红；
  ⑩ adler32 故意错一位 → **C 侧 stb_image 没抓到，Python 侧 zlib 抓到**。
- ★ ②和⑤ 第一版都**不红**：带遮罩的部件（眼睛/眉毛幽灵）全在头部、正好落在 4 线程的第 0 带里，
  真 rig 上观测不到。②改成在 zimg 层直接做单元负控，⑤改用 8 线程（第 0 带 [0,170) 在眼睛上方）
  才暴露出来。**"闸绿"不等于"闸有用"，得先确认它碰得到被测逻辑。**
- ⑩ 这条尤其要记：**stb_image 不校验 adler32**。所以 C 侧（stb 回读像素）和 Python 侧
  （标准 zlib 解 `/api/frame.png`）是**互补**的两条闸，谁也替不了谁。
- 复查触发：① 以后给 zimg 加任何"写 dst"的新函数，必须同时接 `zimg_clip_range`，
  否则 test_core 的逐字节对拍会红（已验证）；② 若改成脏矩形增量渲染，带划分不再覆盖整幅，
  这套"并行==串行"的闸要重新设计；③ 线程数上限 `ZRIG_MAX_BANDS=8`，核更多的机器要调。

### DC51 ✅ 换高清素材时，"scale 减半"只对标量成立；数组 scale 的绑定必须跟着减半（2026-10-15）

- 前提：T30.1 当时写的是"画布坐标完全不动，变的只有素材像素密度和与之配套的 scale"。
  **这句话只对一半。** zrig 里 `scale` 有两种语义，换算方式不同：
  · 标量 `"scale": s` → `p->scale`，通道**乘性**：最终 = `s × p_s`。
    素材 ×2 + s ÷2 ⇒ 任意 `p_s` 下渲染几何不变，绑定**不用动**。
  · 数组 `"scale": [sx,sy]` → `p->scale_x/scale_y`，通道**加性**
    （`compute_draw_state`: `part_sy = scale_y + (p_sy − 1.0)`）。
    基准 ÷2 了而增量还是 1x 口径 ⇒ **形变整整 ×2**。
- 证据：全 rig 11 条 sx/sy 绑定里真受影响的只有 3 条（都在 `mouth_mask`，
  `mouth_cavity` 经 `motion_from` 跟随）；`eye_*_ball` 是标量 scale，**不受影响**
  （第一遍按"@2x + 有 sx/sy 绑定"扫出 9 条，是误判，按语义重扫后自纠为 3 条）。
  算术与渲染都对得上：`ParamMouthOpenY=1` → `44 × (0.02725 + 0.895) = 40.6px`，
  实测开口 40.6px；减半后 `44 × (0.02725 + 0.4475) = 20.9px`，实测 20.9px，
  正好等于 1x 时代的 `22 × (0.0545 + 0.895) = 20.9px`。
  git 对照锁死回归点：`415486d`（1x，22px 素材 + bind 0.895）→ `d83e7a5`（@2x，
  44px 素材 + bind 仍 0.895）。
- 负控：把 3 条绑定还原成未减半，5 项闸全红并精确复现坏数字
  （开口 40.6px、嘴下沿 body_full y=289 vs 下巴 272）；
  反过来问"如果所有 @2x 件的绑定都减半会怎样"——**会把标量件改坏**：
  标量件的绑定是乘性的，再减半等于形变只剩一半。所以闸只盯数组 scale 的件。
- 复查触发：① 以后再出现 `"scale": [sx,sy]` 的新部件（嘴以外），加进来时
  `make_rig.py` 的 @2x 段会自动处理，但要确认它的绑定出现在 `PARAMS` 里
  —— 动作轨若直接写部件级 `sx/sy` 会绕过换算，那里已有断言拦住；
  ② 哪天把超分倍率从 2 改成别的，`0.5` 和 `× 0.5` 两处都要跟着改。
