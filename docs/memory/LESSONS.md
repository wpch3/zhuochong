# 教训与陷阱（LESSONS）

> 规则：**同一个坑掉两次就是失职**。摔过一跤就写在这里，写清"症状 → 原因 → 正确做法"。

## 一、代码陷阱（已踩过）
1. **deflate 的 distance=1 回溯**：只有当"紧邻的前一个字节与当前字节相同"且"前面已输出过至少 1 字节"时，
   才能用 RLE 复制。否则解码器复制的是前一个字节（`…01 00 00 00…` 被解成一片 `01`）。
   症状：PNG 能解码但 adler 校验失败 / 图像内容错误。**验证方式：与真实 zlib 往返比对。**
2. **合成颜色被钳成纯白**：`zimg` 的 `sample_premul()` 输出颜色归一化到 0..1，而 `zimg_draw()`
   里若再乘 255 就会饱和。约定：**预乘采样一律归一化 0..1**，输出前才乘 255。
3. **`z_dirname()` 原地修改传入缓冲**：`z_path_join(buf, …, "logs/pet.log"); z_dirname(buf);`
   会把 buf 变成 "logs"，后面再用 buf 就错了。**先拷一份再 dirname。**
4. **区域命中坐标未换算**：`regions` 用画布坐标（848×1360），而窗口/帧是缩放后的（如 466×748）。
   平台层必须先把帧坐标换成画布坐标（`zrig_frame_to_canvas`），否则缩放一变就点不准。
5. **唤醒不能用普通请求**：`sleep` 优先级最高且声明 `interruptible: false`，
   任何唤醒必须 `force=1`，否则被状态机拒绝、角色"睡死"。
6. **JSON 生成器 key 后的逗号**：写 key 时已输出逗号，值再走一遍 `w_pre_value()` 会多一个逗号
   （症状：`{"a":1,,"b":2}`，解析失败）。用 `after_key` 标志短路。
7. **JSON Schema 校验器崩溃**：schema 里写 `"type": 123` 这类非法值时不要顺着继续走；
   取子项不能用只支持数组的 `zjson_at`（对象也要能按序号取）。
8. **mini 正则不支持 `{n}`**：`^#[0-9A-Fa-f]{6}$` 这类颜色 pattern 必须支持 `{n}`/`{n,m}` 量词，
   否则合规配置会被误判为错误。
9. **日志文件打不开**：见第 3 条；症状是启动就打印"[log] 无法打开日志文件: ./logs"。

## 二、素材陷阱（已踩过）
1. **洋红噪点残留**：AI 生成图的边缘有"距离远但色相仍是洋红"的抖动像素。
   只按"到键色的欧氏距离"抠图会漏掉它们（放大 4 倍才看得见）。
   正确做法（已实现）：距离判定 **或** 色相判定（`R+B-2G > 阈值`）+ 去孤立点 + **边缘颜色用内部像素外扩**。
2. **白边/棋盘格**：JPG 没有透明通道，棋盘格是画进去的，不能当素材（旧交接文件已警告）。
3. **部件整块裁剪会露馅**：嘴部若直接矩形裁剪会把肤色方块盖在脸上（颜色相近但一动就穿帮）。
   正确做法：按"比周围肤色暗"生成 alpha 蒙版（`mask_mouth()`），只留嘴线。
4. **一张图里抠眼睛（旧路线）**：四次迭代都失败（残留与横带）。
   正确做法：眼睛/嘴**单独生成或按固定框裁剪**，且**所有表情图必须用同一取景**，
   这样才能保证部件互换时位置不漂。
5. **取景不一致 = 部件对不齐**：生成表情图时必须在提示词里锁死"正面、同缩放、同位置"，
   入库前用脚本按眼睛位置做对齐归一（`tools/make_face_parts.py`）。
6. **几何拆件的手臂不能整块旋转**（2026-10-11 实测）：手臂是从单图层上竖切下来的，
   里面必然带着一条外套前襟。绕肩旋转 26° 时那条会甩到身体轮廓外，肩口还会露出锯齿切口。
   能兜住的角度 = 重叠带 ÷ 肩到手的距离 ≈ `38 ÷ 276` ≈ **8°**，挥手远不够用。
   正确做法：手臂改用**网格形变** `bend_x/bend_y` + `curve=tip`（顶边=肩 钉死，越往下位移越大），
   肩口永不开裂，和 Live2D 的手臂变形器同一个思路。真要大幅旋转，先补关节图（GAPS G4c）。
7. **关节重叠带里不能存错内容**：躯干顶端那条重叠带原本是**下巴**，头一转就露出"第二个下巴"。
   必须把它换成颈线那一行向上复制的"脖子桩"。重叠带的作用是"露出来也像那么回事"，
   所以里面装的必须是**被遮住的那层**该有的东西。

## 五、表情对齐（2026-10-11 踩坑，未解决）
1. **虹膜检测不适用于闭眼/困倦/开心^^表情**：这些图没有可见虹膜，且蓝色发尾会被误认成虹膜，
   导致缩放和锚点跳变（同一批图缩放从 0.2 跳到 0.6）。
2. **肤色脸框高度不可靠**：脸框的肤色掩膜会连到脖子与肩部，高度随表情与取景变化，不能当尺子。
3. **结论**：自由生成的表情图不能靠算法事后对齐，必须在生成阶段就锁死取景（或人工给每张图标注锚点）。
   下一步候选：① 用同一张"底稿"做 img2img 只改表情（保持取景）；② 对每张图人工标注双眼中心（一次性、可复核）。

## 七、引擎与配置陷阱（2026-10-11 互动扩展中踩到）
- rig.json 动作缺省 loop 不能默认 true：`zjson_bool(obj,"loop",1)` 会让所有没写 loop 的动作（head_pat、happy…）永不结束。缺省必须是不循环，循环动作显式写 `"loop": true`。
- 帧缓冲在第一次 `zpet_tick` 之前是空的（opacity 0），测试和预览取区域前必须先 tick 一次。
- 非强制动作请求会被“循环中的高优先级动作”挡住：测试里要先 tick 到动作播完再请求，否则误判为逻辑错误。
- zjson 的 `zjson_get_*` 对缺失的可选字段会立即写一条警告到日志（zdiag_warn 直接打印），不能用“静默 diag”绕过；可选字段要先判断键是否存在再调用。
- 在 bash 工具里不要把 cwd 写进 command 参数里（会导致调用失败）；复杂的 Python 编辑请先写成临时脚本文件再执行。

## 四、构建与进程陷阱（2026-10-11 新增）
1. **`make preview` 是“编译 + 前台运行”**（Makefile 的 preview 目标最后一行直接起服务），用它“只编译”会把工具调用阻塞到超时。正确做法：只编译用 `make build/zhuochong_preview`；起服务用后台进程工具，命令 `./build/zhuochong_preview --root . --web web --port 5173 --bind 0.0.0.0`。
2. **改了 C 代码，运行中的预览进程不会自动更新**：必须先停进程、再重编（否则二进制被占用）、再起新进程。症状：接口都 200、代码也编过，但画面还是旧行为。
3. 重编前 `rm -f build/zhuochong_preview`，避免拿到被占用的旧文件。
4. **`pkill -f <关键字>` 会匹配到自己所在的 bash 命令行**（命令字符串里含同样的关键字），结果把自己的 shell 一起杀掉，后面的命令全不执行。要杀进程用精确 pid（`ps` 取 pid 后 `kill`），或用进程管理工具停。
5. **对 Python 生成器做字符串替换时，`return {` 这种片段会命中内层函数**（我把 `part()` 的 return 换掉了，结果 rig.json 里 5 个部件变成 null，而脚本不报错）。改生成器要么用唯一上下文（带上下一行的字段名）定位，要么直接改文件内容后**立刻重跑并校验产物**（部件数、关键字段非空）。
6. 单图层素材下**不要给 head 组发 rot_deg**：画上去的头不会转，只会把贴在上面的五官转走（实测眼睛相对脸部的偏移波动 3.66px → 去掉后 1.06px）。拆出 head_base.png 后再恢复，make_rig.py 已按素材自动判断。

## 2026-10-12 边缘质量：抠像不是病根，零件切口才是

- **不要再去重写 `tools/prepare_sprites.py` 的抠像。** 试过两版\"更正确\"的做法，
  实测都更差（数字见 `docs/ART_PARTS.md` 5.7 的表）：
  - 距离斜坡软 matte + **预乘 LANCZOS 缩放** → 白边光晕 61 → **1197** 像素。
    原因：LANCZOS 有负瓣，强边缘预乘值过冲，再除以小 alpha 被放大成亮斑/紫斑。
  - 换无负瓣的 BOX → 缩放比 0.89、支撑只有 1.1 像素 ≈ 最近邻，
    边界硬跳变 4% → **25%**，锯齿更重。
  - 现用做法之所以够用：塗り足し（bleed）之后**直接按通道 LANCZOS**是安全的。
- **\"切割感\"来自零件切口的二值 alpha**，不是来自抠像。凡是\"按掩码从整图切一块\"的
  地方都要做软切口：掩码两遍 3×3 平均 → `clip(x*1.35−0.18)` → 内部拉回 1.0。
  刘海实测：边界硬跳变 100% → 0%。
- **残留指标要先验证再相信**：旧的 `check_white_residue`（接近纯白 + 半透明）会把
  浅紫头发的正常软边全算成残留；`magenta_residue`（R+B−2G>90）会把角色自己的
  深紫线稿（实测 (48,2,79)）算成残留。改判据以后**新旧数字不可直接比**，
  必须用同一套判据把旧图重算一遍。
- **沙箱没有 scipy**，形态学一律用 `np.roll` 八邻域自己写。

## 2026-10-12 零件做完要\"抓帧看\"，不能只看验收数字

`check_assets` 202 项全绿、`make test` 244 项全绿的情况下，眨眼在画面上是**坏的**
（`blink=1` 眼睛里还是眼白 + 虹膜下缘）。三条教训：

1. **遮罩是按颜色 flood 出来的，必然小于美术意义上的\"眼睛\"**：
   眼白下缘的淡蓝、外眼角的白都在判据之外 → 眼皮盖不住。量化方法：
   把闭眼帧和睁眼帧在眼眶范围内逐像素比，**一模一样的像素就是没被盖住的**。
2. **\"画了\"不等于\"看得见\"**：眼皮自己画的闭眼线落在遮罩外面，被一刀切掉。
   凡是\"画在零件边缘的细节\"，都要确认它在遮罩/可视范围之内。
3. **重建脚本缺一步 = 零件静默过期**：`rebuild_parts.sh` 原来没有眼睑步骤，
   身体一重切，眼皮还是旧几何。**新增零件必须同时加进 rebuild 脚本**，
   并且在脚本里排在依赖它的步骤（rig）之前。

## 2026-10-12 动画底层：三条踩坑（淡入淡出 / 物理 / 跟随）

1. **物理的"输入"不能只读驱动组的 `dx/dy`**。这个角色 17 个动作里，头部运动
   绝大多数写在 `head.rot_deg` 上（sway/idle/happy/clicked/hammered…），只有
   `root` 带位移。按通道取值的话，头一转头发纹丝不动。
   正解：用 `group_matrix(driver)` 把**部件锚点**变换一遍，取变换前后的位移差 ——
   旋转、父链、bend 跟随全都自动算进去。
2. **物理的"输出"必须是 `位置 − 目标`，不能是位置本身**。否则静止时
   弹簧停在 `ratio × 输入` 上，等于给静止姿势加了个永久偏移（头一歪，呆毛就永远歪着）。
   输出差值才能保证"动的时候晚一拍、停下来回原位"。
3. **测"淡入淡出"时别被波形本身骗了**。`pulse` 波形在 `t=t0` 时值就是 0，
   第一次写单测断言"`fade:0` 应该一帧到位"读到 0.00，查了半天其实是波形没走完。
   测幅度必须 tick 过 `dur` 的峰值点，测淡化要选 `sine`/常量这类 t=0 就有值的波形。

另：叠加顺序定死为 **动作（含淡化）→ 指针跟随 → 物理**。
跟随写在物理前面，转头才会甩起头发；物理写在最后，惯性就不会反过来污染动作。

## 2026-10-12 ASan 第一次跑就抓到两个真内存错

**症状**：`make asan` 直接 ABORT，而普通 `make test` 323 项全绿。

1. `zdeflate.c:221` **stack-buffer-overflow（读越界 1 字节）**。
   快速跳过判据 `data[i + best_len]` 里，`i + best_len` 可能**正好等于 n**
   （上一轮匹配一直吃到缓冲区末尾），这时就读到了缓冲区外第一个字节。
   这是 PNG 压缩路径，天天在跑，只是恰好没崩。
   **正确写法**：这个判据前面必须加 `i + best_len < n`。
2. `tests/test_core.c` **global-buffer-overflow**：写坏配置时手写了长度 `90`，
   而那个字符串字面量只有 89 字节。**长度一律用 `strlen()` 算，不许手写数字。**

**教训**：普通编译 + 单测**查不出越界与泄漏**，必须定期跑消毒器。
已加 `make asan`，并进了 `make check` 与 CI。

## 2026-10-13 拆件第七件（侧发/后发）：三条可复用的硬规律

1. **"看不见的像素"照样能害人**。原画里散着几百个 `alpha=1~4`、RGB 是纯绿 `(0,255,0)`
   这类抠像垃圾像素，正常合成下完全看不见；但只要有任何一步做**颜色外扩**
   （`grow_colors`、塗り足し、解污），把它们当成颜色源，就会被重写成 `alpha=255` 的亮点。
   实测躯干多出 88 个纯绿像素，静止看不出来，侧发一摆就在下巴边上闪一颗绿点。
   → **颜色外扩的取色源一律卡 `alpha > 32`**，并且只把"本轮新填的"加进源集合。
   同理：做任何按颜色分区的判据前，先想清楚半透明像素算不算数。

2. **"静止画面 0 像素差"只是及格线，不是验收线**。拆件的真正验收是**动起来之后**：
   零件一摆，原来被它盖住的补画区、塗り足し、垃圾像素全都暴露。
   本件的四个 bug（补画边、塗り足し越界、幽灵发梢、绿点）**静止时一个都看不见**。
   → 验收必须加一步：冻结时钟（`/api/pause?on=1`）把驱动参数推到 ±1 各抓一帧，
   在 5 倍放大下看"摆开后露出来的那块"。

3. **形态学运算要挑对**。补洞用 `fill_holes`，别用"膨胀再腐蚀"的闭运算：
   闭运算会把发丝之间的缝连成片，压在脸上的发丝就被判成脸。
   连通块过滤要在**所有项都合并之后**再做一次（本件把补画区的冷色并进后发之后忘了再过滤，
   脖颈阴影被塗り足し吹成了两个大菱形）。

4. **摆动曲线的"固定边"别搞反**。`zimg_bend_factor`：`tip` = **顶边固定、底端最大**（t²），
   `root` = 底边固定、顶端最大（u²）。后发第一版写成 `root`，结果是**头顶的剪影在晃**
   （摆动集中在帧 y63~88），整个头形都在变。口诀：**哪条边钉在身上就固定哪条边** ——
   呆毛根在下沿用 `root`，侧发/后发/刘海都是从头顶长下来的，一律 `tip`。

5. **压力测试写法三件套**（这轮为"摆动不露底"调了三次才有用）：
   ① **逐像素比，不能比总数** —— 头发一挪会顺手盖住别处的缝，总数相减是个大负数，
   挖了洞照样"通过"（实测 −294 → −285）；
   ② **只数"深处"** —— 头发本来长在剪影边上，摆开露出背景是对的，
   把剪影往里腐蚀 4px 再数，清白素材 7~10 px、真缺重绘 128 px，区分度才出来；
   ③ **模拟摆动要照引擎的曲线剪切**（顶边不动、t² 递增），整件平移等于把发根也搬走，
   而且上下平移会因为整行取整在零件自己身上切出 1px 横缝（假阳性）。
   **新加的检查必须拿"负例"证明它会红**：把左侧发底下的脸挖空 2310 px → 该项立刻 128 > 20。

6. **"交叉淡化"做不出半闭眼**。两张不同的画各 50% 叠起来必然是一只**灰色幽灵眼**，
   调 ramp 斜率、换先后顺序都只能缩短窗口、消不掉（证据：`eye_blink_sheet.jpg` 上排）。
   闭合这件事得靠**擦除/位移**去演——眼眶按下沿压扁 + 眼线跟着下滑；
   两张图只在**已经几乎重合**（都只剩下眼睑上一条线）时才交接，所以曲线要**两头让开**：
   睁眼件 `clamp((1−blink)·4)`、闭眼件 `clamp((blink−0.75)·4)`。

7. **零件只是"又画了一遍"，底图没挖，等于没拆件**。眼睛拆了四件，可脸上 `seg_head`
   原封不动画着整只睁眼——眼眶一收，露出来的是**脸上那只睁着的眼**。
   拆件的完成标准是：**把被零件盖住的那块从底图里挖掉并补画**，
   然后用静态闸守住（`check_assets`「脸上无残留睁眼」直接数眼眶区里剩的暗眼线 + 蓝虹膜像素）。

8. **改 anchor 必须同步改 pos**。`zimg_make_matrix` 的语义是"把 anchor 这个像素点放到 pos 上"，
   只改 anchor 不改 pos，整件会平移一整个锚点偏移。
   另外锚点要放在**内容的边**上，不能放在图的边上：眼眶图底部有空白行，
   锚点放 `[0.5,1.0]` 压扁时整只眼被"吸"向那条空白底边（单测实测下沿跑了 23px）。

9. **挖/补皮肤的三个实战细节**（这轮眼窝）：
   ① 抹一条线要**整条带状外扩**再抹，不能只抹暗像素——线里嵌的白色高光会成为填充色源，
   把线填成一排白方块；② 填一条**横线**用"按列上下插值"，四邻域外扩只能从两头爬，留灰糊痕；
   ③ 软边遮罩要用**软权重加权替换**（`w=clamp((α−24)/72)`），卡死阈值会在斜坡那圈留下原画
   （实测 988 粒白点）。

10. **切件工具切出来的"眼线"常常夹带别的笔画**。`eye_?_lash.png` 里混着虹膜左右两道描边，
   静止时盖在虹膜上看不出来，一随眼皮下滑就拖到脸颊上像两行灰眼泪。
   凡是**要动**的零件，先问一句"它里面有没有本该不动的笔画"，有就逐列只留第一段连续的墨。

11. **动一个零件之前，先确认那块像素到底归谁。** "裙下大腿抬腿露底"第一反应是"腿画短了"，
   真相是 `seg_torso` 切到了 776、**裙摆下那截大腿是画在躯干上的静止副本**。
   补画补半天都没用——它归错件了。逐件单独渲染一遍，比盯着合成图猜快得多。

12. **关节能不能转，取决于缺口开在哪一侧，不取决于补多少画。**
   腿绕髋旋转必在**裆侧裙摆下沿之下**撕口，而补画只能长在下沿**之上**，几何上填不进去；
   改成 bend（`curve:"tip"`，顶边钉死）就构造性零缺口。
   **凡是"从上往下挂 / 被上面的件盖住根部"的零件，一律 bend + tip，不要旋转。**
   曲线写反（`root`）= 根部甩出去，±20px 就漏 700+ 像素——这个错犯过两次（hair_back 一次、腿一次），
   现在已经写成静态闸卡死。

13. **塗り足し要补在遮盖件的"下面"，不是补在它的"边上"。**
   手腕的皮肤续出贴着袖口边补，转 ±20° 就从袖侧探出一小片飘肉。
   正解：续出的部分按 `erode(遮盖件掩码, D)` **往里缩 D 像素**，并让 `L·sin(θmax) < D`
   （实测 10·sin20°≈3.4 < 4 ✓）。同理，手件要画在前臂**底下**，不是上面。

14. **验收闸门必须做负控，否则很可能是"一直绿、其实什么都没量"。** 本轮一口气抓出三个假闸：
   ① **整行横带会量错部位**——腕线正好穿过裙摆，数出来的全是裙和腿（读数与髋 band 一字不差才暴露）；
   关节带与别的部件同高时，必须按该部件自己的外接框加**列窗**。
   ② **四向 `hole_mask` 测不出"敞口缝"**——缝朝外敞开时"左右还有身体"的条件不成立，
   把塗り足し删光照样读 0；要改成**同列上下夹心**。但取样窗套太大又会去数手指缝那种
   "本来就该有的洞"（读数随姿势乱跳 135/153），窗口要卡在关节线上下十几像素。
   ③ **压力姿势里整条链一起转，会把末端零件转出取样框**，框内空白恒为 0；
   **末端关节的闸要单独只转那一级。**
   一条闸写完先问："我把零件故意改坏，它会红吗？"——不会红的闸等于没有。

15. **协议/命名这类"全局口径"要在素材堆起来之前对齐官方。**
   小寻的参数表过去少 18 个标准 ID，还把左右眼并成一个 `ParamEyeLOpen` 别名、腮红自造 `ParamBlush`。
   能力上看不出问题，但凡是写死这些名字的东西（18 个动作、6 个表情、口型、外部工具）
   都会一起错，**越晚改代价越大**。对齐的办法是去拉官方源码（`cubismdefaultparameterid.ts`）
   和官方样本（`Haru.model3.json`），不要凭印象。

16. **"跳过即通过"的检查等于没有检查。** 把 `ParamBlush` 改名成 `ParamCheek` 之后，
   冒烟脚本里的 `if "ParamBlush" in pids:` 不成立，那一项**悄悄消失**（64 → 63 项）而不是变红。
   凡是 `if 条件: check(...)` 的写法，都要先 `check(条件本身成立)`；
   总项数变少也要当成信号去查。

17. **像素级的"参数有没有生效"必须先把时间冻住。** 两个不同时刻的帧相减，
   待机动作 + 呼吸的漂移就有十几像素，足以把"死参数"盖过去。
   正解 = 用同一个时间戳再 tick 一次（dt=0）。
   但要注意 **dt=0 不会让物理衰减**：弹簧不走，可输出 `pos − target` 会随驱动立刻变 ——
   上一个参数甩出去的摆动会污染全局基准帧，所以**每个被测项都要现拍自己的基准**。

18. **先去参考项目里翻，再决定怎么做——这一步能省掉一整条错路。**
   口型音素本来打算加 `ParamMouthA/I/U/E/O` 五个参数。翻完官方标准参数表
   （嘴只有 `ParamMouthOpenY` + `ParamMouthForm`）、Animaze 的 viseme 映射表、
   以及 airi 的 `wlipsync/vowel-driver.ts` 之后才确定：**母音是两个标准参数的组合**，
   自造五个参数就等于主动脱离标准。沙箱里别克隆（3 GB 还会被重置），
   用 `gh api .../git/trees/HEAD?recursive=1` 列目录 + `Accept: application/vnd.github.raw` 取单文件。

19. **"参数能动"不等于"看得见"。** `ParamMouthForm` 以前的 bind 是 ±0.08/0.06，
   在 466px 的渲染帧上只有半个像素 —— 单测能过（值变了），人眼完全看不出。
   判据要落在**画面**上：五个母音两两像素差 > 25px、い 必须比 う 宽。
   另外**锚点错了幅度就白给**：上唇线锚点在左上角时 sx 一缩是整条线往右平移，
   改成中点（`pos` 同步 412→434）才是两边一起咧开。

20. **可选依赖会悄悄降级，必须让它变红。** `make_lipsync.py` 没装 pypinyin 就产不出音素轨，
   包络还是能用（只是退回只开合）—— 这正是"跳过即通过"的翻版。
   做法：生成时打警告 + 自检加一条"口型包络带母音音素轨"，哪天有人用裸环境重跑，
   38/38 变 0/38 会当场红掉。

21. **"谁后跑谁说了算"这种事，别自己拍脑袋定，去查官方的执行序常量。**
   表情和口型都写 `ParamMouthForm`，顺序反了就是"笑着说う 嘴变中性"。
   官方把答案写在 `icubismupdater.ts` 的 `CubismUpdateOrder_*` 里
   （Expression 300 < LipSync 700），而**不是**在 `addUpdatableList` 的调用顺序里
   —— 照着调用顺序猜会猜反。

22. **抄官方算法前先看它的前提。** 官方 LipSync 用纯加算 `addParameterValueById(id, v, 0.8)`，
   前提是它的 LipSync 组**只驱动单调开合的 `ParamMouthOpenY`**。
   我们连 `ParamMouthForm`（±1，正负是两种相反嘴形）一起驱动，加算就会抵消。
   偏离官方做法可以，但必须：① 写清前提差在哪；② 登记进合规表；③ 配一条会红的负控。

23. **自己埋的"安全兜底"会把负控废掉。** `if (vis_mix <= 0) vis_mix = 0.8;` 看着像防呆，
   实际是"把 0 当没填"——于是"权重设 0 应该失效"这个负控永远红不了，
   顺带也让用户没法真的关掉这一层。防呆要用**夹范围 + 警告**，不要**替换语义值**。

24. **分层以后，老断言读的那一层可能已经不动了。** 音素从"回写基础参数"改成"合成时叠一层"后，
   `zrig_param_get()` 恒为 0，三条老断言全失效（但它们当时是"通过"的）。
   凡是改分层结构，必须把断言改读**最终值**，并补一条"这一层不许回写下层"的反向断言。

25. **三态的字段，setter 绝不能收 bool。** `blink_forced` 用 −1/0/1 表示"自动/不闭/强制闭"，
   `zrig_blink_force(zrig*, int)` 的实现却是 `r->blink_forced = on ? 1 : 0` ——
   调用方按字段语义写 `force(-1)` 想表达"交回自动"，反而被当成真 → 醒着也永远闭眼。
   单测当年只覆盖了 `force(0)`，`-1` 这条路从没测过。**语义值和布尔值不能共用一个入口。**

26. **"关掉某个子系统"≠"冻结它的输出"。** 眨眼的 `enabled` 本意是"自动眨眼定时器别跑"，
   却被写进了绘制判断 `if (blink_enabled && blink > 0.001) { 睁眼件淡出；闭眼件淡入 }`：
   关掉以后，表情/手动/动作推出来的闭合度全都跳过淡化，闭眼件 100% 不透明盖住睁眼件 = 一上表情就全闭眼。
   官方 `CubismEyeBlink` 的做法是**只写参数**，绘制永远只看参数值。
   凡是 enable/disable 开关，先问一句：它关的是**产生者**还是**消费者**？只能关产生者。

27. **把"立即生效"的 API 改成"渐进生效"，必须同时分出两个名字。**
   `zrig_viseme_clear()` 从硬切改成平滑松口之后，所有把它当"立刻清干净"用的地方全部失真 ——
   `test_viseme()` 在冻结时钟下根本收不完，误红了「い 比 う 宽」这类毫不相干的断言。
   做法：保留 `clear()` = 平滑，新增 `reset()` = 立刻，然后 `grep` 全部调用点逐个分流。

28. **负控要对着"被改坏的那条公式"算出预期数值再定阈值。**
   这轮第一版"小声说话要透出笑意"写成 `Form > −0.95`，而退回恒定权重时算出来是 −0.25，
   照样过 —— 负控等于没做。收紧成 `0.05 < Form < 0.65`（即"必须明显偏向笑的那一侧、又没完全盖住口型"）后才判红。
   另外选基准状态也要算：原先想用 SIL 帧测力度调制，但 SIL 会自动触发 release，根本测不到。

29. **像素闸也会"跳过即通过"：被测的东西可能被别的东西盖住或顶替。**
   笑眼那一轮三条负控全没红 —— 笑眼补片本来就盖住整只眼（去掉"隐含闭眼"看不出来）、
   眼线件下滑后也在同一位置留一条线（笑眼件不画也有暗像素）、两条睫毛线叠着画差异照样"够大"。
   **真素材的画面里同一块地方有太多东西在说话。** 办法有两条，都要用：
   ① 把不可见的机制加个**只读查询**，用数值断言（`zrig_eye_close/zrig_eye_smile`）；
   ② 另起一个**合成 rig**，把要分辨的几张图摆在**互不重叠**的位置，逐块数像素 —— 这才叫结构闸。

30. **先查官方示例模型的数据文件，比查文档快也准。**
   笑眼怎么做，文档只说"+ 时变成笑眼"；而 `Haru/expressions/F05.exp3.json` 一眼就给出完整口径
   （`EyeLOpen=0 Multiply` + `EyeLSmile=1 Add` + 眉 0.32）。
   官方示例仓库里的 `.exp3.json / .model3.json / .physics3.json` 是**可直接读的真实参数**，
   以后遇到"这个标准参数到底怎么用"，先 `gh api` 把示例模型的数据文件拉下来看。

31. **测动作必须逐帧推进时间，不能一次跳过去。**
   动作切换的淡入权重是在 `zrig_tick` 内部发现"动作变了"那一刻才起算的
   （`fade_t0 = 本次 tick 的 now`）。`tick(t0); request(a); tick(t0+2.0)` 看到的是
   **权重 0 的那一帧**，也就是"动作还没开始动"。一度让我以为挥手动作坏了。
   正确写法：`request(a)` 之后以 1/60 为步长 tick 过去。
   `zrig_action_elapsed()` 返回的是对的（它用传入的绝对时间），**别拿它当"动作已经生效"的证据**。

32. **一个参数绑多条通道时，分清"主力"和"点缀"，别把同一件事绑两遍。**
   给 `ParamBodyAngleX` 同时绑了躯干网格弯曲（主力）和胸组平移（点缀）之后，
   "五官要刚性跟住身体形变"那条单测红了，偏差正好等于胸组平移量。
   还有 `chest.sy` 这种**作用在整组上的缩放**：0.4%/格看着小，满格 4% 就能把 770px 高的
   上身顶端推走 30px。组级缩放的系数要按"满格时顶端跑多远"来定，不是按直觉。

33. **"按 bind 系数反算"是迁移既有动画数据的安全办法。**
   197 条调好的几何通道要迁到参数通道，不要重写（那些数值是美术成果），
   而是 `参数振幅 = 几何振幅 ÷ bind scale`，再用逐像素回归证明等价。
   换算表同时当守门人：遇到没登记的几何目标直接报错，几何通道就长不回来了。


34. **回归比对出现的每一处差异，都要找到机制解释，"余波""抖动"之类的说法等于没解释。**
   这轮 `surprised` 的最大差异落在 t=1.4（动作早就演完了），我第一反应写的是
   "结束后余波，合理"——其实那是个真 bug：动作演完那一帧把 pulse 满值整个闪了出来。
   判据是**时刻要对得上窗口**：循环动作只该在淡入期有差、非循环动作只该在淡出窗口内有差；
   差异出现在解释不了的时刻，就是有问题。

35. **一个效果有几条代码路径，就得在几条路径上都实现它。**
   动作淡出有两条路：当前动作（`a`）和正在淡出的旧动作（`prev`）。只改前者，
   动作演完切换的那一帧立刻露馅。官方的语义能直接提示这一点——
   FadeOutTime 是 **motion 自己的属性**，不是"接替者"的属性，
   所以凡是让这个 motion 出力的地方都要乘它。

36. **"函数写对了"和"调用处用的是这个函数"是两回事，单测只能保前者。**
   `z_ease_sine()` 的数值可以单测，但没法阻止哪天有人把 `compute_group_transforms`
   里的调用换回 `z_smoothstep`。所以 selfcheck 加了一组**静态闸**：正则抠出函数体，
   断言里面有 `z_ease_sine(u)`、没有 `z_smoothstep`、淡出乘法被 `tot > 0.0` 挡着。
   凡是"口径统一"类的要求，都该配一道这样的源码闸。

37. **渲染里的 `if A else if B` 要当成 bug 看：两个效果都成立时，B 被静默丢掉。**
   `draw_state` 里网格形变器和 bend 互斥了不知道多久，G16 多段摆链的第一段
   一直白写，没有任何报错、测试也全绿——因为没人测过"两个同时开"。
   凡是"一个部件/对象上可以挂多种效果"的地方，默认就该是**叠加**，
   要互斥得有明确理由；并且必须有一条"两个同时开"的测试。

38. **"找到第一个就 break"是另一种静默丢失。**
   同一部件上的第二张网格直接没了。写这种循环时先问一句：
   这里真的只可能有一个吗？不是的话就累加，并在加载期拦住加不起来的情况
   （我们这儿是"同部件两张网格尺寸必须一致"）。

39. **判据要能区分"坏法"，不只是区分"好法和原始状态"。**
   测第二张网格没被丢，我写的是 `A+B ≠ 只有B` —— 可掉了 B 的实现会退化成
   `只有A`，它也 ≠ 只有B，负控照样绿。改成 `A+B` 同时不等于 `只有A` 和 `只有B`
   才抓住。**写断言时先想一遍"错误实现会给出什么值"，让判据正好落在中间。**

40. **selfcheck 的源码闸别直接 grep 关键词——会被自己的注释骗。**
   我写了句注释"不能找到第一张就 break"，然后 `"break" not in code` 立刻判红。
   要么只认带分号的真语句（`"break;"`），要么先把注释剥掉再匹配。

41. **做之前先核对"这件事是不是已经做完了"。**
   排期清单上挂着"下一件 = G19 LipSync 接 TTS 包络"，真去查库才发现它
   2026-10-12 就完成了（记作 A4，39 条台词的包络和音素序列都在库里），
   而且 GAPS 里 `G19` 这个号还被另一件事（通知中心）占着。
   **清单会过时，库不会。** 动手前花一分钟 grep 一下产物是否存在。

42. **看 binds 表就下"没跟随"的结论太早——还有 motion_from 这条路。**
   透け眉 ghost 的 binds 里确实没有任何眉参数，我据此判定它不会跟着动；
   实际上它走的是 `motion_from`（照抄本体通道值），而形变器查找同时认
   `motion_from` 源和自己。**同一个效果可能有不止一条传导路径**，
   下结论前把所有路径都走一遍。

43. **几何/配置类的约束放 selfcheck，运行时行为放单测。**
   "眉形不许带位置移动"这条，用渲染像素去测很别扭（眉毛被刘海盖住、质心被
   刘海的暗线条淹没，判据根本不灵敏）；而它本质是**配置层的性质**——
   每个控制点的 dy 都看得到，直接算 `|Σdy|/Σ|dy|` 又准又快。
   选对检查的层次，比把判据写复杂有用得多。

44. **没有浏览器也能测界面：DOM stub 比"看一眼截图"可靠得多。**
   九十行的 stub（createElement/appendChild/classList/querySelectorAll/dataset/style）
   就够把内核和全部组件真跑一遍，连"script 插进 head 就执行"都能模拟。
   它能抓到的东西肉眼反而看不出来：挂载顺序、点击坐标的换算、某个卡片静默没挂上。

45. **重构时"原样搬移"胜过"顺手重写"。**
   把 380 行业务逻辑拆进九个组件，我一行都没重写（连注释都搬过去）。
   在没有端到端验证手段的情况下，重写 = 同时改结构和行为，出问题分不清是哪一边。

46. **组件化多出来的包装层，用 `display: contents` 让它对布局透明。**
   "区域容器 + 插槽"两层 DOM 会打断原有的 grid/flex 父子关系，
   一条 `display:contents` 就让它们不参与布局，既有 CSS 一个字都不用改。

47. **测试自己要扛得住"被测对象不存在"。**
   负控删掉一个组件文件后，web-test 直接 TypeError 崩了（exit 2）而不是报失败。
   崩溃也算发现问题，但看不出是哪一条断言、也没法继续跑后面的检查。
   取对象的地方加一层 `slotOf()` 兜底，缺了就判失败并返回空壳。

48. **用户给的是愿景清单时，框架的任务是"让清单不用列完"。**
   "2027 年以内 AI 能做到的所有事情都要加进去" —— 真去列功能必然漏。
   正确的回应是把它翻译成**可扩展性约束**：能力是注册出来的、供应商与能力解耦、
   加一种新能力不改内核。这样清单永远填得下。

49. **接生态标准之前先查有没有现成的。**
   skills 差点自己定格式，查 super-agent-party 才发现它用的是 Agent Skills 规范
   （`SKILL.md` + frontmatter）。采标准的收益是**整个生态的技能包直接能用**，
   自造格式则是从零积累。查一次的成本远低于造一套。

50. **新建一套契约前，先 grep 老的那套还有没有人在读。**
   `config/providers.json` 已经存在，差点变成"新旧两套供应商定义"。
   grep 发现只有文档提到、没有代码读它，于是迁移内容后直接删掉。
   **并存两套配置是最难查的那类 bug** —— 改了一边，另一边静默生效。

51. **grep 文件名查不到引用 ≠ 没人读它——路径是会被拼出来的。**
   第 50 条删掉 `config/providers.json` 时 grep 了文件名，看着干净，
   结果 `make check` 判红：`zconfig.c` 里写的是
   `load_one_json(c, "providers.json", ...)` + `cfg_path(c, ...)`，
   grep 全路径永远命中不了。**删配置文件的验收标准是"全量闸门还绿"，不是"grep 没结果"。**
   查引用时要同时 grep 不带目录的裸文件名、以及可能的拼接片段。

52. **遇到"新格式 vs 老格式"，不要二选一，让老的变成生成物。**
   C 侧读老格式 `providers.json`，新契约在 `config/providers/*.json`。
   恢复老文件 = 两套并存（第 50 条的坑），强改 C = 动运行时代码有风险。
   第三条路：**新契约是唯一真相，老文件由校验器从契约投影生成**
   （`kind` 做映射：`comfyui`/`mcp` → C 认识的 `local`，原值留 `kind_ext`）。
   老格式的消费者一行不改，而真相只有一份。

53. **`--check` 模式的正确语义是"验证生成物是最新的"，不是"跳过生成"。**
   原来的 `if not only_check` 让 `--check` 直接不碰生成物，
   于是"改了契约忘记重算"这个最阴的状态能一路绿灯过闸。
   改成算出应有内容、与磁盘比对、不一致判红后，两道负控
   （改契约不重算 / 手改生成物）都红了。**生成物过期是静默失效，必须有闸。**

54. **剥注释的时候必须认字符串字面量。**
   给 selfcheck 写源码闸，先剥注释再 grep（第 ★★ 条教训）。
   结果 `zgateway.c` 里的 `"secret://"` 里那个 `//` 被当成行注释，
   半行代码被吃掉，两条正确的闸判红。**剥注释和词法分析是同一件事，
   不能只认 `/*` 和 `//`**。遇到 `"` 就整段保留，还要处理 `\"` 转义。

55. **源码闸要数的是"函数里有几处"，不是"文件里有几处"。**
   想表达"`zgw_secret_resolve` 只有一条成功路径"，写成
   `gw_c.count("return 0;") == 1` —— 整个文件有 7 处 return 0，
   别的函数成功时也 return 0。得先按大括号配平抠出函数体再数。

56. **查参考的收益往往是"改掉还没写的设计"，而不是"抄实现"。**
   G51 动手前查 one-api，两处设计当场改了：路由表从"运行时遍历"改成"预计算索引"，
   余额契约从 `{mode, path}` 改成 `{mode, endpoint, pick, minus}`（因为实测发现
   四家四种算法，单字段表达不了减法）。这两处要是写完了再发现，
   前者是性能问题（还能忍），后者是**契约格式要改，所有已写的契约文件跟着返工**。
   查一次十分钟，省的是返工。

## 57. 先查人家能不能做，再设计抽象

这轮差点直接写"给每个音色加个 style 字段"就完事。实际查了 edge-tts 的 README 才发现
它**根本做不了情绪**（官方明说 custom SSML 被移除），而 MiniMax 用请求体字段、
Azure 用 SSML、Fish 用文本内嵌标签 —— 四家四种机制。
如果按"大家都有 style"去设计，edge-tts 那条路会在运行时报 400，而且是静默的。

**做法**：先把各家的机制查清楚，抽象成 `emotion_mode` 四类，网关负责翻译。
这和之前余额查询抽象成四种算法是同一个套路 —— **差异藏在契约里，不要漏给上层**。

## 58. 能力弱的那一档要如实标注，不能粉饰

`edge_tts` 做不了情绪，契约里就**不准填 `emotions` 字段**（校验器判红），
界面上直接写"无情绪（只能调语速音调）"。
一开始想给它也算个"情绪区分度"分数显得好看点，这是错的 —— 用户选了它然后发现没情绪，
比一开始就看到"不支持"更糟。闸门里专门加了一条"免费通道如实标注做不了情绪"。

同理，"支持几种情绪"这个数字会骗人：MiniMax 的 11 种情绪映射其实只落到 5 个不同取值。
所以清单里给的是**区分度**（能分成几种不同的声音），不是覆盖数。

## 59. 生成物要显示"现在真能用的"，不是"配置里写的"

`config/voices.json` 投影时，如果首选供应商没开（没配密钥），就落到兜底音色，
并在 style 字段里注明"首选 X 没开，先用兜底"。
如果照抄首选，C 侧读到的是一个发不出去的音色 —— 界面说能用、实际静音，最难查。
界面上同样显示"（没配密钥，现在用 晓伊）"。

**判据**：生成物里的每一条，都应该是此刻直接拿去用就能成功的那一条。

## 60. 单测的 stub 可能比真服务宽松，要拿真服务再探一次

音色库面板做完、65 项 web-test 全绿、selfcheck 全绿、提交推送完 —— 然后起了真预览，
`/emotion_map.json` **404**。原因：它放在 `config/` 下，而静态服务只认 `web/` 根。
web-test 的 fetch stub 是直接 `fs.readFileSync` 拼路径读的，所以永远读得到。

**stub 读得到 ≠ 浏览器取得到。** 跑完闸门之后，起一次真服务 curl 一遍面板要的 URL，
这一步省不掉。

补的闸：扫 `web/components/*.js` 里所有 `api("/xxx.json")`，逐个核 `web/` 下有没有这个文件。

## 61. 闸写完必须负控，不然可能是个摆设

上面那条闸第一次写完，跑出来"通过"。改坏组件（让它去取 `/config/emotion_map.json`）
再跑，**还是"通过"** —— 正则 `[a-z0-9_.\-]+` 里没放 `/`，路径中间带斜杠的根本没被匹配到。
闸在空转。

"加了闸 + 一次就绿"这个组合，必须当成"闸可能没在工作"来对待。
判据是**改坏它能变红**，不是"它现在是绿的"。这已经是第二次栽在同一个地方了。

## 62. 跨语言的参数名不能猜，一天栽两次

写立绘调试台时，`/api/viseme` 我按 `id=音素&v=音量` 写，真实签名是 `v=音素&w=音量`；
`/api/pause` 我按 `v=0|1` 写，真实签名是 `on=0|1`。
**两次都返回 `{"ok":true}`** —— C 侧 `qstr(r,"on",...)` 找不到就用默认值，不报错。

第二个错更坑：`pause?v=0` 实际执行的是"冻结"（默认 on=1），于是我在一个**冻结的服务**上
测了半小时参数，得出"ParamAngleX 坏了"的结论，差点去修一个没坏的东西。

**已落闸**：`selfcheck` 扫 `web/components/*.js` 里所有 `"/api/xx?k="` 和
`api("/api/xx", {k:...})`，按大括号配平抠出 C 侧该端点的处理块，核 `"k"` 在不在里面。
三道负控（viseme 写成 id=、pause 写成 v=、调不存在的端点）全判红。

## 63. "返回 ok" 不是"生效了"，判据要读回状态

上面那两个错能潜伏这么久，根因是我拿"HTTP 200 + ok:true"当成功判据。
写验收时判据必须是**读回来的状态**：设参数就回读 `params.json` 的 value，
切表情就回读 `info.expression`，不是看接口返回什么。
`api_smoke` 新增的 9 项全部按这个口径写。

## 64. 像素对比要先量噪声底，而且要分清"依赖 dt"和"不依赖 dt"

拿像素差验证立绘能力时翻了两次车：
1. 用了 `frame.png?s=2` —— `s` 是**百分比**不是档位，于是我在 116×187 的缩略图上
   找眼睛的变化，眨眼只有 61 像素，全判成"没动"。
2. 不冻结时钟测，idle 呼吸自带 **17000+ 像素**的噪声底，把眼睛/眉毛/口型几十到几百像素的
   真实变化全淹了，17 项里误判了 5 项。

**正确做法**：bind 类（不依赖 dt）冻结时钟测，噪声 0；look 类和动作（按 dt 收敛）
走时钟测，先量噪声底再定判定线。两类分开。

## 65. 混合模式（multiply / add）画在透明像素上等于没画

腮红用 `multiply`，摆在脸轮廓外 92% 的面积 —— 满值只带来 27 像素可见变化。
我先怀疑"素材太淡"，把 peak 0.62→0.88、颜色加重，重做出来平均 alpha 从 43 升到 63，
可见变化只从 27 升到 41。**和按 alpha 估算的 ~400 差十倍，这个倍数差本身就是线索**：
不是浓度问题，是有效面积问题。

**定位手法**：把像素差阈值降到 4（而不是 12），看影响区的 bbox，
再读最大变化点**在底图上的 alpha**。读到 10 就说明压在透明处。

**连带教训**：程序化生成的零件，落点要对着底图的**实心范围**算，
不能照 socket / 相邻部件的 pos 推。眼 socket 横跨 x 298..545 看着很宽，
但 `seg_head` 在 y=300 的实心只有 x 345..491 —— 脸是上宽下窄的锥形。

## 66. 区域矩形是"按比例估"的，和素材真实几何对不上

交互区域（摸头/摸身体/点脚）的 rect 来自 `prepare_sprites.py` 的
`suggest_regions()`：头 = 角色高 × 24%，而且假设头顶贴着画布 y=0。
实际 `seg_head` 占画布 y 68..385，head 区域只到 310 ——
**嘴和下巴归了 body，点脸触发的是「摸身体」而不是「摸头」**。

接口是"正常"的：`/api/region` 老老实实返回了 `body`。
单测也绿（stub 里区域表是手写的）。只有把**区域定义和素材几何摆在一起比**才看得出来。
闸就该加在这个层面（`check_assets.py` 能同时读 rig.json 和素材，是对的地方）。

## 67. 一个画面有四种尺寸，别混

做鼠标交互时栽的。同一个角色同时存在：

| 量 | 是什么 | 本仓取值 |
|---|---|---|
| 显示矩形 | `getBoundingClientRect()` | 随窗口变 |
| 画布 | regions 的 rect 用的坐标系 | 848×1360 |
| **引擎帧缓冲** | 画布 × pet scale，**`hover/region/poke` 吃这个** | 466×748 |
| 图片尺寸 | 帧缓冲 × 画质档 `s%`，即 `img.naturalWidth` | s=55 时 256×411 |

`stage.js` 一直用 `img.naturalWidth` 换算点击坐标 —— 画质档是 100 时碰巧等于帧缓冲，
所以从来没暴露。画质一降或 `/api/scale` 一改就整体点偏。
参考项目 airi 的 `useLive2DEyeFocusFor` 把这三个量分得很清（见 REFERENCE_NOTES 第十四批）。

**判据**：写坐标换算时，先问"对端用的是哪个尺寸"，然后在测试 stub 里
把其它几个尺寸**故意设成不一样的值**，用错就会红。

## 68. `make -s` 不会重建预览二进制

`Makefile` 的默认目标是 `all: test`，只建 `build/test_core`。
`build/zhuochong_preview` 挂在 `smoke` 目标下。
改完 C 跑 `make -s` 看到"627 项全过"，很容易以为新代码进去了 —— 实际预览还是旧的。

我因此白查了十几分钟：`info.json` 里新加的 `regions` 一直是空数组，
C 层单独编译验证却是对的（`zpet_region_count=3`）。
判据：`nm build/zhuochong_preview | grep <新函数名>`，或者看二进制时间戳。
改完 C 要 `make -s build/zhuochong_preview`（或 `make -s check`，它经 smoke 会带上）。

## 69. 服务刚起、还没渲染过一帧时，区域命中全是空

`zrig_region_at` 在矩形判定之后还要做 `zimg_hit_test(r->fb, ...)`，
而 `r->fb` 要渲染过才有内容。预览刚启动就查 `/api/region`，三个区域全返回空。
同理 `/api/scale` 改完 scale，**帧缓冲要等下一帧才变成新尺寸**，
而 `info.frame_w/h` 是立刻报新值的 —— 这中间坐标系会短暂错位。

实际 UI 不受影响（stage 一上来就在拉帧），但写测试时会偶发失败：
我的 hover 用例在"跑过一轮"的服务上通过、在干净服务上失败，就是这个。
**测试里改完 scale 要补一次 `/api/frame.png` 再断言。**

## 70. 「规划了但还没做」必须有清单文件，空目录和假素材都不行

想在界面上表达"这个形态我们打算做，只是还没做"，有三条路，两条是坑：

- ❌ **建空目录占位**：`scan_forms()` 只认有 `rig.json` 的目录（这是对的，切到空形态会白屏），
  而且 **git 根本不跟踪空目录**，克隆下来就没了。
- ❌ **放模板素材占位**：假素材会被 `check_assets.py` 的 375 项逐条检查 —— 要么全红，
  要么为它开后门（后门一开，真坏了也查不出来）。更糟的是假图会混进 LoRA 训练数据。
- ✅ **清单文件声明**：`characters/<角色>/forms.json` 写 `status: ready|planned`。

关键是**以磁盘为准**：清单说 ready、但 `forms/<id>/rig.json` 不存在的，引擎照样降级成 planned。
清单只能用来"补充说明"，不能用来"吹牛"。再配一条闸盯住三种坏法（谎报 ready / 做完忘登记 /
planned 却留了半拉子素材），这个分区才不会在半年后烂成一笔糊涂账。

## 71. 「计划不能忘」要落成闸，不是落成文档

用户说"我们所有的计划不能忘"。第一反应是写进文档 —— 但文档本身就是会被忘的东西。
真正的失败模式不是"没写"，而是**写进了 REQUIREMENTS，却没有任何地方安排谁去做**。

所以做了双向追溯闸 `check_plan_traceability()`：
- 每条需求要么自己写明落点（表格第 4 列），要么在 TASKS/GAPS/计划里被引用；
- 每个缺口要么写明修完了，要么在 TASKS 或计划里有排期；
- 计划里出现的 G 编号必须真在 GAPS 登记过（防止凭空冒出一个编号）。

**第一次跑就挖出 16 个登记在 GAPS 里、却从来没进过任何排期的老缺口**
（G5/G6/G9/G10/G11/G13/G14/G24~G29/G32/G33/G44）。这就是证据：靠记性和靠文档都不行，
只有每次 `make check` 都跑的闸才拦得住。写闸时注意要认**既有的多种写法**
（`| G2 (T9.2) |` 把落点写在括号里、状态列 ✅ 的约束类需求不需要排期），
否则满屏误报会逼着人把闸关掉。

## 72. 用户明确排除的东西，要用静态闸钉死

用户说"绝对不要豆包"。这种排除项最容易在几个月后被无意中违反
（"加个供应商矩阵吧" → 顺手把火山加进去）。所以写了两道关键词闸：
`check_platform.py` 扫 `config/` 下 48 份配置，`selfcheck_repo.py` 扫 `src/ web/ config/`
的全部源码。关键词要覆盖别名：`doubao / volcengine / volces / byteplus / seed-tts / 豆包 / 火山引擎 / 火山方舟`。
负控验过：往 `zpet.c` 的注释里塞一个 `volcengine` 就会红。

顺带一个小发现：`read_form_name()` 从 `rig.json` 的 `name` 取形态显示名，
但那字段存的是**角色名**。只有一个形态时看不出问题，四个形态做完会全叫"小寻"。
**同名字段在不同文件里含义可能不同，别想当然。**

## 73. 噪声底为 0 不是"很干净"，是时钟没在走

实测动作效果时拿到这组数字：噪声底 全身 0 / 腿部 0，然后 `shift_weight` 也是 0。
差点判成"新动作没生效"。真相是上一个脚本在一个 404 上崩溃了，
结尾的 `/api/pause?on=0` 没执行，引擎还冻结着。

**噪声底 = 0 本身就是异常**。这个角色不冻结时 idle 呼吸的底噪是
全身 16723 / 腿部 1348 像素。量到 0 说明时钟停了，后面所有对比都没有意义。
以后测任何 dt 驱动的东西，**第一步先看噪声底像不像话**，再看被测对象。

顺带：循环动作（loop + sine 波）在 t=0 时位移本来就是 0，
所以"触发后立刻采样"永远测不出东西 —— 要连采若干帧取峰值。

## 74. 动作通道打在参数上，不在组上

想查"哪些动作会动腿"，按组名 `leg_l` grep 动作通道的 target，0 命中，
差点得出"腿完全没有动作"的结论。实际上 Live2D 的 .motion3 曲线只能打在参数上，
这个项目也照做了 —— target 是 `ParamLegL`，不是 `leg_l`。按参数名查才看到 4 条。

**查"某部位有没有动作"要先搞清楚中间隔着什么**：
部件 ← bind ← 参数 ← 动作通道。少看一层就会误判。

## 75. bend 的 curve 选对了，不拆件也能做关节

腿是一整张图（`seg_leg_l`），没有膝盖、没有脚踝的独立部件。
本来以为要拆件 + AI 重绘遮挡区才能做屈膝，结果不用：

- `curve:"sine"` = 两端固定、中段最大 → 峰值正好在**膝盖**高度
- `curve:"tip"` = 顶边固定、底端最大 → 作用在**脚踝**
- `curve:"root"` = 底边固定、顶端最大 → 作用在**根部**

实测 `ParamKneeL=1.0` 的像素差 **100% 落在腿部区域**，说明 sine 峰的位置是准的。
一张平面图靠选对弯曲曲线就能表达关节，省掉一整轮拆件与重绘。

另外：一个参数可以绑**多条 bind**（`ParamWeightShift` 绑了 root.dx + 两腿 sine 补偿），
这是做"复合姿态"最省事的办法 —— 但这种参数没法用几何通道写法表达，
生成器的通道转换器要支持"直接写参数名"这条路。

## 78. 量「我这个改动有没有效果」，必须有负对照，否则量的是别的东西

给 8 个动作补下半身通道后，第一版判据是「腿部像素变化 ≥ idle 噪声底的 2.0 倍」，
一测 7 个有效，很好看。但有个地方不对劲：**7 个一次性动作的数值整整齐齐挤在
2.0~2.2 倍**，真信号不会这么听话。

于是挑了三个**我没动过、而且本来就没有任何下半身通道**的动作做负对照：

| 负对照 | 腿部变化 | 比噪声底 | 有下半身通道吗 |
|---|---|---|---|
| nod | 5900 | 1.7× | 无 |
| focus | 5289 | 1.5× | 无 |
| clicked | 5107 | 1.5× | 无 |
| **stroke** | **18028** | **5.3×** | **无** |

判据当场废掉。原因想明白就很简单：**整个身体平移，腿的像素自然跟着变** ——
`stroke` 一条腿部通道没有却拿到 5.3 倍，就是因为它整体挪动身体。
「相对 idle 的变化量」量的是"这个动作和站着不一样"，不是"腿在动"。

改成真正的 A/B：同一个二进制、同一个采样脚本，**唯一变量是那 25 条通道在不在**
（生成一份剥掉通道的 rig，重启，测完再换回来）。负对照 `nod` 给出 +128 像素(+2%)，
这才是测量误差底，其余动作 +1349~+2828 一目了然。

**通用教训**：做"效果验证"时，先问一句"如果我的改动根本没生效，这个数会是多少"。
答不上来就说明判据里没有负对照，那个数字再好看也不能信。
这和「闸一次就绿 = 闸没在工作」是同一回事的两种表现。

## 79. 指标饱和会把最好的结果报成最差的

同一轮里，A/B 判据（已经是对的）给 `sleep` 判了 **+1%「基本没用」**，八个里垫底。
差点就去改参数了。先查了一下为什么：

```
腿区总像素      161236   (466 x 346)
腿区角色像素     27137   ← 真正的分母
sleep 实测峰值   28745   = 角色像素的 106%
```

**顶到天花板了**。sleep 把整个身体挪得很远，相对 idle 基准帧，腿部像素本来就
已经全部不一样，再动也不可能更高。这个指标在 sleep 上没有分辨力。

循环动作换成**自方差**：基准帧取自**动作进行中**（等 2 秒进入循环后再拍），
量的是"维持这个状态时身体还动不动"。结果反转：

| sleep | 腿部自方差 | 占角色像素 |
|---|---|---|
| 剥掉新通道 | 734 | 3%（基本冻住） |
| 有新通道 | **7583** | **28%** |

**10.3 倍，是八个动作里最强的一个**，被误判成了最弱。
参照 idle 自方差 7004、sway 11028，7583 落在中间，数值也合理。

两条操作性结论：
1. 任何比例型指标，先算出**分母的天花板**，确认没贴顶再信它。
2. **一次性动作**和**循环动作**不能用同一个指标：前者看"相对静止态的峰值差"，
   后者看"自身随时间的方差"。用错了必然得到反直觉的结论。

顺带一个小坑：`sleep` 的 sine 频率我写了 0.05（**周期 20 秒**），而采样窗只有 3 秒。
即使指标没饱和也量不到。量循环动作前先拿 `1/freq` 算周期，采样窗至少盖住一个周期。

## 80. `pkill -f "[z]xxx"` 的括号技巧防不住宿主命令行

一直用 `pkill -f "[z]huochong_preview"` 避免 pkill 匹配到自己。这次写成了：

```bash
pkill -f "[z]huochong_preview"; sleep 1; (./build/zhuochong_preview ... &)
```

**自己把自己杀了**（exit code -1，后面的实测一条没跑）。因为 `pkill -f` 匹配的是
**完整命令行**，而这条 bash 的命令行里后半段有未加括号的 `zhuochong_preview`。
`[z]` 只防住了 pkill 自身那个进程，防不住宿主 shell。

处置：停进程一律用 `stop_process` 工具（它按进程组精确终止），
不要在同一条命令里既 pkill 又重启同名进程。

## 82. 照着权威建议改，也要验证它在你的架构里真的生效

Live2D 官方眨眼教程字幕原话："闭眼时眼型要比睁眼时横向略窄，这样更自然。"
很权威，照着加了 `aperture_narrow`（眼眶遮罩随 blink 横向收 12%）。

实测：**虹膜宽度 0.25/0.40/0.55 三档都是 123px，一点没变。**

原因是官方说的是**在网格上形变整个眼型**，而我们用的是**遮罩裁切** ——
虹膜（31×30）离遮罩左右边缘很远，收 6% 根本够不到它，只削到眼白外角
（变化 1500~2400 像素，肉眼看不出）。同一句建议，在不同的实现架构里
落地方式完全不同，照抄形式不等于拿到效果。

**当场撤回了**，没留在代码里充数。留一个半生效的特性 + 一段引用官方的漂亮注释，
下次有人读到会以为这事做完了 —— 那就是新的断代源头。
改成记进 GAPS（G87）并写明"这条路已验证走不通，别重走"。

## 83. 编译器警告值一读：漏个大括号差点让眨眼逻辑作用到全身

加 `aperture_narrow` 时写成了：

```c
if ((p->tags & TAG_EYE_APERTURE) && blink > 0.0)
    part_sy *= 1.0 - blink * (1.0 - p->aperture_min);
    part_sx *= 1.0 - blink * p->aperture_narrow;   /* ← 这行在 if 外面 */
```

`part_sx` 那行对**所有部件**生效 —— 一眨眼全身横向缩 12%。
`-Wmisleading-indentation` 精确报了出来（"this 'if' clause does not guard..."）。

这个特性后来因为别的原因撤掉了，但教训独立成立：
**构建输出里的 warning 不要滚过去**，它当场抓到了一个我自己没看出来的真 bug。

## 84. 量「动得够不够」和量「动得一不一致」是两回事，后者我一直没量

用户反馈"颈部会横向整体错误细微的位移，包括兜帽"，还补了一句
**"这些你都不能查询到吗？我在测试网关很容易就看到了"**。

答案是：**我的实测方法对这类问题是瞎的。**

此前所有实测（包括我上一轮专门做的 `measure_motion.py`）量的都是
**整帧或分区的像素变化量** —— 回答的是"这个动作幅度够不够大 / 有没有生效"。
而颈部滑移的幅度完全正常，问题是**头和衣领之间动得不一致**。
分区像素差把它们加在一起，正好把差异平均掉了。

更糟的是我第一次尝试还用了"按横带量不透明像素的水平重心"，
那个方法连方向都不对 —— 同一条横带里混着头、躯干、头发三个组的像素，
重心根本不可比，扫完 50 个参数只报出两个头发参数（而且是误报）。

有用的方法是**逐行水平位移剖面**：取两帧（改一个参数前后），对每一行做
亚像素互相关求位移，然后看位移随 y 的曲线。**位移应当连续变化，跳变就是接缝。**
一跑就看见了：头部恒定 −4.74，躯干顶边 −5.08，中间跳 0.40px。

两条结论：
1. **"幅度"和"一致性"要分别有量法。** 只有幅度的量法，会漏掉所有接缝类缺陷，
   而接缝恰恰是用户一眼就看见的那种。
2. 已把 `--profile` 模式加进 `measure_motion.py`，并在 GAPS 里写明判据。
   加完立刻用它把整条剖面跑了一遍，又发现另外三四处（G90）—— 说明这类缺陷
   之前一直存在，只是没有能看见它们的工具。

## 85. 顶边不等于根部：贴图的边界和解剖学的边界是两回事

颈部滑移的根因，一句话就是：**躯干贴图的顶边其实是脖子和衣领，但 bend 曲线
把它当成了"躯干的顶端"**。`root` 曲线 `f(t)=(1-t)²` 在 t=0 给满额形变，
于是衣领成了全身位移最大的地方 —— 比它上面的头还多动。

这类错误的共同形状是：**几何上的边界（贴图切到哪）被当成了解剖上的边界
（关节在哪）**。同一个坑在这个项目里已经出现过几次：
- 腿部贴图底边 ≠ 脚踝（所以 `tip` 曲线的峰才要专门调）
- 眼眶贴图顶边 ≠ 上眼睑的弧线（所以 lash_travel 不能拿开口高度当行程）
- 现在这次：躯干贴图顶边 ≠ 颈根

处置办法也一样：**显式写出解剖边界**（`bend_hold_above`、`lash_travel`、
`bend_follow_at`），不要让它从贴图尺寸里隐式推出来。
凡是看到代码直接用 `img->h` 或 `pos[1]` 当作关节位置的地方，都要警惕。

## 86. 同一个毛病出现在 15 个地方时，去改那"一个共同的上游"，别去改 15 个下游

用户反馈"光是头在动，身体没联动"。查出来 20 个动作里 15 个身体完全不动。

摆在面前三条路：

**A. 手工给 15 个动作补身体通道。** 就是我上一轮做 `LOWER_EXTRA` 的做法。
 代价：15 个动作 × 若干通道，以后每加一个新动作都得记得补，而且我上一轮
 用这个做法时**自己就埋了一个 bug**（tiptoe 声明 1.5s 实际 1.0s 的死时间）。

**B. 引擎加一层「身体跟随头部」耦合。** 覆盖面最广（连实时视线跟随都管），
 但要新增运行期状态，和现有的动作/表情/物理四层叠加逻辑全都要重新验。

**C. 找那个共同的上游。** 查下来根因非常干净：
 `ParamAngleX/Y` 是内建参数、走 look 系统，**本来就同时写 head 和 chest**；
 唯独 `ParamAngleZ` 是普通参数，只绑了 head —— 而那 15 个里有 12 个用的是它。
 于是只要给 `ParamAngleZ` 补一条 `chest.rot_deg` 绑定就行，**一行数据**。

选了 C。而且比例不是我拍的：**照抄 look 配置里已经调好的 chest/head = 1.2/5.0 = 0.24**，
0.5 × 0.24 = 0.12。既然同一个系统里已经有人调过这个比例，就不要再发明一个。

教训有两层：
1. **看到"N 个地方都有同一个毛病"，先花十分钟找那个共同上游。** 十分钟换掉
   十五处手工改动和一份永久的维护负担，几乎总是划算的。
2. **新引入的系数，优先从系统里已经存在并调好的系数推导**，而不是重新拍一个。
   这样两处的口径天然一致，而且闸可以直接断言这个关系（我就把
   "chest/head 比例必须在 0.15~0.35" 写进闸了）。

## 87. 「把东西整个平移」几乎从来不是对的做法 —— 关节是用来转的

摸头把脖子抽长，根子是一行 `head.dy = -7.0`：把整个头往上平移 7 像素。
平移会改变**两个部件之间的距离**，而解剖上脖子的长度是不变的。

正确的做法是**绕关节旋转**：`ParamAngleZ → head.rot_deg`，绕颈关节转，
头的朝向变了但颈长一点没变（实测 -9.48px → +3.23px）。

这条可以推广成一个检查习惯：**看到对某个组写 `dx`/`dy`，先问一句
「这个位移会不会把它和父组之间扯开」**。
- 扯得开（头和胸、手和小臂、脚和小腿）→ 该用 rot_deg 绕关节转
- 扯不开（整个人跳起来 root.dy、重心左右挪 root.dx）→ 平移才是对的

区别就是：**平移只对「根」合法，对「关节以下的任何东西」都要先怀疑。**

## 88. 两个位移同号叠加 = 悄悄把"踮脚"做成了"起跳"

`ParamTiptoe` 的两条绑定：`root.dy = -7`（整体上提）、`seg_leg_*.bend_y = -5`
（tip 曲线，底端满额）。各自看都"合理"——人要升高、脚踝要收。
**但它们同号，加起来是整个人连脚一起浮空 12px。**
实测角色最底行 1359 → 1347。

用户的反馈是"踮脚脚部没有变化"。这句话字面上成立：脚相对身体确实没变化，
因为它跟着整个人一起飘走了。**用户描述的是现象，根因往往在别处**，
这次就差点被"脚部没拆件"这个看起来更显眼的解释带偏。

一般化：**凡是"多条绑定共同决定一个接地点/接缝位置"的地方，要显式写出
那个不变量，并且让闸去断言它**，而不是逐条看每个 scale 是否"合理"。
这里的不变量是"脚底净位移 = 0"，翻译成断言就是
「root.dy 与腿 bend_y 异号、等量、且腿用底端满额的 tip 曲线」。

同类的不变量还有：裙摆下沿不许穿过腿、头顶不许出画布、颈长不变（LESSONS 87）。

## 89. 花十分钟做图像模拟，省掉一次四分钟重建和一堆接缝债

"脚部拆件"看起来是明摆着该做的：用户点名要、锚点现成、切线实测过、
仓库里还有 `make_arm_parts.py` 这个成熟套路可抄。估算成本：
新工具 + rebuild_parts（≈240s）+ 接通生成器 + 验接缝 + 调图层。

动手之前先做了一件便宜事：**直接在渲染好的帧上，把鞋段以鞋底为锚
压缩 2%/8%/14%/22%，拼成一张对照图看。**（`logs/asset_qa/tiptoe_mock.png`）

结论是：**8% 看不出区别，14%/22% 只是把鞋压扁了，像"踩瘪的鞋"而不是
"抬起脚跟"。** 因为鞋是**正面视角**画的（鞋底着地段对脚踝左右基本对称），
平面内纵向压缩给不出抬跟的读感，平面内旋转则读成崴脚。

于是整个拆件方案被否决 —— 它在没有新素材的前提下不产生价值。

**在投入做一个特性之前，先用最便宜的手段把"做出来会是什么样"摆到眼前。**
对图形类改动，"便宜的手段"通常就是直接 P 一张图。
十分钟的模拟，省掉的不只是工时，更是一份本来会长期背着的接缝维护债。

## 90. 固定数组 + "装满就不装了" = 一个永远不会报错的黑洞

`ZRIG_MAX_PHYS` 是 12，rig 里声明了 13 条，解析循环是：

```c
for (i = 0; i < n && r->nphys < ZRIG_MAX_PHYS; ++i) { ... }
```

第 13 条 `back_x`（后发摆动）就这么**被悄悄丢掉了**。没有报错、没有警告，
rig.json 里白纸黑字写着它，`make check` 全绿，而它从来没有运行过。
它还偏偏是全场最大的一个摆（look_around 峰值 1.77px，裙摆才 0.13）。

发现它纯属意外：我加第 14 条的时候把 `skirt_y` 也挤掉了，
而 `skirt_y` **刚好有单测**，这才红出来。换句话说，
**如果不是碰巧挤掉了一个有测试的条目，这个洞会一直在那。**

这和 LESSONS 里「单测 stub 漏字段 = 测试绿、真服务空白」是同一个家族：
**配置声明了，运行时没生效，而中间没有任何人负责核对两边的数量。**

三条处置，缺一不可：
1. **超限必须是硬错误**，不能是"少装几个"。`if (n > MAX) return error;`
2. **加一道跨文件的数量闸**：扫源码里的 `#define ZRIG_MAX_*`，和 rig.json
   里对应数组的长度比对。
3. **要留余量**（我定的是 85%）。等撞上才报，就已经有人在没生效的配置上
   调了半天参数了。

推广：凡是"配置文件里写 N 条、代码里开 M 个槽"的地方，都要问一句
**"N > M 的时候会发生什么"**。答案是"少装几个"就一定要改成"报错"。

## 91. 验收时用的"干净环境"，可能正好绕开了你要验的那条代码路径

G89 给躯干加了形变平台修颈部滑移，实测 0.34px → 0.04px，加了闸，提交，收工。

**但那个修复只在裙子不动的时候有效。**

原因：部件挂了形变器时走网格路径、没挂时走 warp 路径，**是运行期按
`形变器 amount 是否为 0` 动态切换的**。我只把平台接进了 warp 那条。
而验收时为了消除噪声**冻结了时钟** —— 冻结时物理不积分、裙摆 amount 恒为 0，
于是测的永远是 warp 路径。测得越"干净"，越测不到真实场景。

这和 LESSONS 里「单测 stub 漏字段 = 测试绿、真服务空白」是同一族，
但更阴险：**测量方法本身为了降噪而改变了被测系统的状态**。

两条操作性结论：
1. **凡是"同一件事有两条代码路径"的地方，两条都要有测试**，而且最好是
   在**图元层**直接各测一遍（我最后就是写了个直接调两个绘制函数的单测），
   不要指望从端到端的渲染结果里碰巧覆盖到。
2. **写验收脚本时，显式问一句"我为了降噪做的这些设置，会不会让某条分支走不到"。**
   冻结时钟、关物理、复位参数——每一个都在改变系统状态，都可能让 bug 藏起来。

顺带：这次能发现，是因为去查另一个问题（裙摆区域的位移剖面）时，
顺手查了 `st->dg` 什么时候非空。**查问题时顺手把相邻代码读一遍，经常比正面排查更有效。**

## 92. 剖面工具会把"不同部件恰好在同一高度"误报成接缝

逐行位移剖面的前提是"同一行的像素属于同一个部件"。这个前提在身体中段不成立：
画布 y 727~796 这一带同时有**裙摆**（不随 BodyAngleX 动）和**双手**
（跟着手臂刚性跟随，动 5.66px）。互相关量的是整行 alpha 的综合位移，
于是报出一个 −2.86px 的"位移"和一处 +2.35px 的"跳变" —— 肉眼去看，
那里根本没有接缝。

所以 `--profile` 的输出是**筛查线索，不是判决**。两条纪律：
1. **剖面报了跳变，必须再用肉眼对照图确认**（左=原图/中=改后/右=差异三联）。
   这次三处跳变，肉眼确认下来真接缝是 0 处。
2. 要定位到具体部件，得把 x 范围也框住（只取裙摆那几列，避开手）。

还有一条反面经验：为了避开物理干扰，我一度改成"先跑 3 秒让物理收敛再冻结"，
结果 **settle 期间 idle 也在跑，两次取帧落在不同呼吸相位**，
同一条剖面从 3 处跳变暴涨到 32 处，全是噪声。正解是**冻结时钟 + 关物理**
（为此给引擎加了 `/api/physics?on=`），而不是放开时钟。

## 93. 贴图画布的边界会悄悄改掉形变曲线的语义

引擎的 bend 曲线（root `(1−t)²` / tip `t²` / sine `sin πt`）里的 `t` 是
**贴图画布**的 0..1，不是解剖位置。腿件原本画布底边正好落在鞋底，所以
"tip 在脚底满额、sine 在脚底为 0"这两条是**白捡的**，没人写下来。

拆鞋件时我把切线以下的像素擦了、**画布没裁**。于是画布底边还留在地面下方 142px 的
空白里，脚踝那条线从 t=1.000 掉到 t=0.774：

- `ParamLegL` 的 tip 从 1.00 掉到 0.59 → **摆腿时脚只走 11.6px，原来是 20px（少 42%）**；
- `ParamKnee` 的 sine 从 0 涨到 0.65 → **屈膝把整只脚抬离地面 2.9px**。

两处毛病、一个上游（LESSONS 86 的又一例）。而且两处都**不报错、不崩**，
只是"动作看起来软了一点""人好像有点飘"——正是最难发现的那一类。

操作性结论：
1. **擦像素和裁画布是两件事**。凡是改贴图内容边界的工具，都要顺手问一句
   "这张图的画布还代表原来那段解剖吗？"，并把新尺寸写回 `*_parts.json`。
2. **"白捡的对齐"要写下来**：画布底边 = 地面、画布顶边 = 发根……
   这类隐含约定不写进文档和闸门，下一个人（包括三小时后的自己）必然踩。
3. 已加闸：`check_assets` 的「腿件画布裁到切线」直接断言 `pos.y + h ≤ 切线`。

## 94. 毫秒级的瞬态，轮询取帧是量不到的——要把引擎公式复刻出来算

想量"交叉淡化期间双轮廓会持续多久"，第一反应是跑动作 + 轮询 `/api/frame.png`。
实测单次取帧 ≈45ms（1.6 秒只采到 36 帧），而要量的东西只有 3 帧 ≈50ms——
**采样周期和被测现象同量级，必然漏采**。那一版只捕到 1 帧，差点得出"几乎没有重影"。

正解：把 `eval_channel_wave`（zrig.c）和 `z_ease_apply`（zc.c）**在 Python 里逐行复刻**，
按 60fps 解析计算。几秒钟就能扫完所有候选窗宽，得到一张可比较的表
（[0.25,0.75]→6 帧 / [0.40,0.60]→3 帧 / [0.45,0.55]→1 帧）。
取帧只用来做**静态分档的目视验收**，不用来量时间。

同一条的另一半：复刻的时候顺带发现 `bounce+out_back` 的峰值只停 **48ms**，
而这正是"换了鞋贴图却看不出踮脚"的真因——**没有这次复刻，这个 bug 根本量不出来**。

## 95. 指标要量"合成后的结果"，不是"中间状态的像素计数"

量交叉淡化漏不漏背景时，我一开始统计"脚区半透明像素占比"，
结果端点 11.4%、中段飙到 **65%**，看着像大面积穿帮。其实那是两件鞋各自半透
（0.70 / 0.50）**都落进了 (16,240) 这个 alpha 区间**，而它们叠加后的总覆盖是 0.85，
一点背景都没漏。

**要测"漏不漏"，就得算合成后总 alpha 的最小值**（或者干脆渲染一帧量那个像素），
不能数"有多少像素是半透的"。单测里最后用的就是后者：真渲染一帧，
量重叠处的 alpha = 0.85 ——负控（把曲线换成线性）量到 0.753，一眼能分开。

## 96. 一个参数被多个动作共用时，"补偿"不能加在参数上

`ParamBaseY`（全身上下，走 `root.dy`，满格 40px）被 happy / hammered / clicked /
sleep / wave / tiptoe 六个动作共用。踮脚时发现它会把脚一起抬走（实测底行 747→744），
第一反应是"那就给 ParamBaseY 也配上两只脚的反向补偿"——**错**：
happy 是**跳跃**，脚本来就该离地；补偿一加，蹦不起来了。

正确做法是**在动作那一层解决**：tiptoe 不该用 BaseY（它的升高已经由 ParamTiptoe
给了，而 ParamTiptoe 自带脚补偿），直接把那条通道删掉。

一般形态：**参数是"能力"，动作才是"意图"**。同一个能力在不同意图下的正确行为
可能完全相反，所以约束要写在意图那一层。落到闸门上就是
`check_feet_on_ground`：**默认每个动作都必须站稳，要离地的动作自己写
`"airborne": <px>` 并且数字要对得上**（写死数字才拦得住以后有人把幅度调大）。

## 97. 防断代的闸要查"处处一致"，不是"有一处写对"

给"文档里的数字必须和生成物对得上"写闸时，第一版判据是
`"lift=30" in 文档`。做负控（把文档里某一处 lift 改成 24）时**它没红**——
因为别处还留着一个 lift=30，substring 判据就满足了。

**半对半错的文档恰恰是最坑人的那一种**：照着错的那处做，做完发现过不了闸，
再回头看文档，另一处又是对的，于是怀疑人生。

改成"把文档里所有 `key=数值` 全抓出来，必须**每一个**都等于生成物里的真值"，
负控立刻变红。一般结论：**凡是"文档与数据一致"类的闸，判据都应该是全称的
（∀），不是存在的（∃）。** 同类的还有"所有端点都要写进文档""所有素材都要提交"——
那两条当初就是按全称写的，这条差点写成存在量词。

## 98. 新开一套编号之前，先查这个字母有没有人用了

昨天建结论登记表，顺手把条目编成 `D01~D16`。今天写到第 16 条「被遮挡区域必须 AI 重绘
（**D19** 规则）」时才发现不对劲：`D19` 是 `REQUIREMENTS.md` 里**立绘需求系列**的编号
（D1~D20，D19 = 被遮挡区必须重绘），而我自己的表里也即将有一条 D19。

于是同一个字符串在同一个仓库里指两件事。这正是"断代"最典型的长相 —— 半年后读到
"按 D19 做"，没人知道该翻哪张表；更糟的是**闸也分不清**，`grep D19` 会同时命中两边。

改成 `DC`（DeCision）前缀，连带把闸里三处正则和 TASKS 的描述一起改掉，562 项自检复跑通过。

一般结论：**新开一套 ID 之前，先 `grep -rn "^| X[0-9]"` 看这个字母在仓库里有没有主人。**
本仓已被占用的前缀：`A/B/C/D/E/F/H/I`（需求）、`G`（缺口）、`T`（任务）、`L`（教训）、
`DC`（结论）、`AC`（真机验收）。下一个新表请从没被占用的字母里挑。

## 99. 闸报"0 命中"之前，先让它证明自己能命中

新加的"代码层面不存在输入通道"闸（AC-20）第一次跑就是绿的 —— 全仓 140 个源文件、
11 个注入 API 关键词，一个都没有。**这正是最该怀疑的那种绿**：正则写坏了也是这个样子。

所以这条闸里塞了一段自检：拿两个写死的样本串（`SendInput(1, &in, sizeof in);` 和
`import pyautogui`）喂给自己的正则，**探测器对样本都不报警的话，先判红再说**。
负控验证：把 `\bSendInput\b` 改成 `\bSendInputXX\b` → 自检项立刻红，
而"0 命中"那条还是绿的 —— 如果没有自检，这次改坏就完全看不出来。

一般结论：**凡是"扫全仓、期望 0 命中"类型的闸，都要配一个探测器自检。**
同类的还有"没有豆包关键词""没有 logs 误入库"——它们现在也都是靠"期望 0"活着的。

## 100. 阈值类的判断，要从两边钉

写完"文本够长就算重活（≥600 字节）"，配了一条 900 字节判重活的测试，绿。
负控时把阈值从 600 改成 **60**（等于"一句话就算重活"，分类器废掉）—— **测试照样全绿**。

因为所有用例要么带关键词、要么超长，没有一条落在 60 和 600 之间。
补一条 500 字节、不含任何关键词的用例（"还没到线，不该判重"）之后，再改阈值就红了。

一般结论：**凡是"超过 X 就怎样"的判断，至少要两条用例：一条在线上方、一条在线下方。**
只测"该触发的触发了"，等于只证明了函数不是常量 false；
把阈值改成 0 它照样过 —— 那时候函数是常量 true，一样是坏的。

## 101. "两边动得不一样"不等于"那里裂了"

G90 剖面上那处 **+2.35px** 的跳变，我按老判据直接当成接缝，差一点就去给腿
加绑定。出图一看（`logs/asset_qa/hip_seam.png`）：**裙摆下沿压着大腿**，
裙子跟上身走、腿站着不动 —— 这是一条**自由边**，本来就该相对错开，
真人侧身时裙边也是这么动的。照"修接缝"的思路改下去，等于让腿跟着上身歪，
既不符合人体，又会去碰"脚不离地"那条硬约束。

**判据要带上"两侧是不是同一块东西"**：同一块皮肤/同一件衣服被切成两半
（色距小）才是真接缝；两种材质交界（藏青裙↔肤色腿，色距 66）是自由边。
`measure_motion.py` 现在自己分这两类，省得下次又白查一轮。

**更一般的那条**：任何"异常检测"的判据，都要先问"正常情况下这里会不会也这样"。
不问这句，查到的就全是误报。

## 102. 做对照之前，先看工具自己有没有动那个旋钮

我拿 `/api/physics?on=0` 和 `on=1` 跑了两遍剖面，读数一模一样，差点写下
"和物理无关"的结论。`grep` 一下才发现 `measure_motion.py` 第 219 行
**自己就把物理关了** —— 两次跑的是同一个状态，**对照根本没发生**。

读数一样有两种可能：变量不影响结果，**或者变量压根没变**。
后面这种更常见，也更难发现，因为它看起来和"验证通过"长得一模一样。
外部旋钮 + 自动化工具的组合，动手前先 `grep` 工具里有没有同名的设置。

## 103. 同一个请求给两种答案，先找"隐式状态"

`/api/region` 在首帧之前收画布坐标、首帧之后收帧坐标 —— 因为换算函数在
帧缓冲还没建出来的时候退化成了 1:1。两种答案都是 HTTP 200，都"看起来正常"，
所以这种 bug 能躺很久（我自己的老笔记还把症状记错成"全返回空"）。

**判据**：一个接口的行为如果取决于"之前发生过什么"，而那件事又不在参数里，
那它迟早会在某个调用顺序下出错。修法有两步，缺一不可：
① 把隐式状态变成确定值（rig 记住平台层声明的缩放，不等首帧）；
② 把坐标系写进**答复**里（回报 `space` 和换算后的 `cx/cy`），
让调用方能自己核对，而不是靠读文档猜。

## 104. 计数器只活在内存里，等于没有记账

路由的本地/云端占比一直有，但只在进程内存里 —— 重启就清零。
而那三条阈值（512 token / 85% 负载 / 敏感本地）是抄别人博客的，
**本来就是要用自己的分布重标的**。不落盘，"重标"这件事就永远只是计划里的一行字。

另外：**记账要记全**。只记"落地成功"的决策，会把"两边都没候选"和"敏感被拒"
这两类漏掉，分母变小、本地占比虚高。这次专门加了 `no_candidate` 这个理由就是为此。

## 105. 在画布上框死一个矩形量"清晰度"，量到的是构图不是清晰度

上一轮我用"画布固定框 (300,200)-(560,400) 的梯度能量"得出"stroke 时脸部锐度 −40%"，
这一轮一复现就塌了：头一动，框里的内容就从"眼睛+鼻子"变成"半张脸+一块平坦皮肤"，
梯度能量当然掉。换成**互相关配准后再量同一块内容**，stroke 的嘴鼻区只掉 10.6%，
而 idle 自己复测就掉 7.4% —— 差异全在噪声里。

规矩：**量"画质"类指标前，先问"我的采样窗口跟着目标动了吗"**。
对会动的东西，配准（或按特征重心裁剪）是必须项，不是加分项。
还有一条：**基线要复测两次**。这次基线自身就漂 1886→1947（3%），
不先知道噪声底，任何"−10%"都读不出意思。

## 106. `fuser -k` 杀不掉预览进程，于是我又测了一遍旧二进制

`fuser -k` 的结果**必须复查**。（这是同一类坑的第三次，前两次记在 G98 和更早。）

## 107. 给引擎加新字段，默认值必须让旧行为原样成立

`lash_hold` 第一版我把默认写成 0.5，结果既有的 `test_eyelid`（写了 `eyelid_travel:20`

规矩：新字段的默认值 = 老行为。这样"老测试还绿"本身就是一条负控，

## 108. 前端的"画质档"会同时改变图片的固有尺寸 —— 显示尺寸必须自己钉死

`#pet` 只写了 `max-height:680px`，而每帧请求的是 `/api/frame.png?s=<档位>`。
档位 60 时图片固有尺寸 279×448（小于上限，于是按原尺寸显示），档位 75 时 349×561 ——
**换一次档，立绘在屏幕上就大一圈**。用户两张截图裙宽 155 vs 147 就是这么来的，
看起来像"脸被轻微拉扯/扭曲"。而且自动档从 60% 起步，等于永远在看一张放大的低清图。

规矩：服务端返回的位图尺寸是**传输参数**，不是**布局参数**。
布局尺寸要显式算出来写死（`img.style.width/height`），传输分辨率再按
"显示尺寸 × devicePixelRatio"反推。带宽不够时**先降帧率，后降分辨率** ——
用户对"糊"的敏感度远高于对"不够顺"。


## 109（2026-10-15）"一次就绿的闸"要当成坏闸来查，变异检验必须做在**用户看得到的那条路径上**

规矩：① 变异检验要跑在"用户实际触发的那条路径"上（他点的是浏览器里的摸头按钮，

## 110（2026-10-15）`pgrep -f` / `pkill -f` 第三次杀掉自己；`pgrep -x` 有 15 字符名长上限

`pgrep -f zhuochong_preview` 会匹配到**正在执行这条命令的 bash 自身**，于是整个

## 111（2026-10-15）诊断脚本不许写死 scale —— 用户会自己调

## 112（2026-10-15）「动作期间取两帧做像素对比」基本不成立

idle 动画一直在动，两次取帧隔 1 秒，头的位置就变了 —— 额头那组对比差异像素

② 比**与位置无关的几何量**（本轮用的"格子实心率"、曲率 sag）；
③ 真要比图就用冻结时钟的 C 层测试。

## 113. "闸绿"不等于"闸有用"——先确认它碰得到被测逻辑（2026-10-15）

分块渲染这轮有**两条闸第一版都是假的**：
- `composite_masked_blend` 忽略 clip 的变异，在真 rig 上**一个字节都没变**。
  原因：带遮罩的部件只有眼睛和眉毛幽灵，全在头部，4 线程时正好整个落在第 0 带 `[0,340)` 里，
  跨带的残留根本不存在。改成在 zimg 层直接构造一张 8×8 的图做单元负控才抓得到。
- "单线程路径不重置带缓冲 clip"的变异，用 4 线程也不红，因为第 0 带 `[0,340)` 包住了眼睛
  （y≈266~300）。改成 **8 线程**（第 0 带 `[0,170)` 在眼睛上方）立刻红。

和上一轮笑眼那条（测试里关掉自动眨眼，闸压根碰不到 `blink_hold`）是同一个病。
**固定动作：每写一条闸，先把被测逻辑改坏一次，看它红不红；不红就说明闸选错了观测点。**
顺带：这两条也说明"真 rig 上跑一遍"不一定比"构造一个最小样例"更强——
真素材的布局可能恰好绕开了你想测的分支。

## 114. 两个解码器抓的错不一样：stb_image 不校验 adler32（2026-10-15）

PNG 并行编码的 adler32 故意改错一位：
- C 侧闸（`zimg_save_png` → `zimg_load`，走 stb_image）**全绿**，stb 根本不验 adler32；
- Python 侧闸（`/api/frame.png` → 标准 `zlib.decompressobj`）**立刻红**：
  `Error -3 while decompressing data: incorrect data check`。

所以这两条闸是**互补**的，不是冗余：stb 验的是"能不能解出图"，zlib 验的是"流严不严格合法"。
浏览器用的是后者那一类。凡是自己手写编码器的地方，都要有一条**用标准库解**的闸。

## 115. 后台残留进程会让你测到旧二进制（第五次踩，这次换了个形态）（2026-10-15）

`api_smoke.py` **不自己起服务**（除非 `--spawn`），裸跑是连 5173 上**已经在跑的**那个。
上一轮留下的预览进程跑了 45 分钟还活着，于是：
- `make build/zhuochong_preview` 因 `Text file busy` 静默失败；
- 连跑三次 smoke 都是 202/0 全绿，测的全是**改动前**的二进制；
- 变异检验也因此"判绿"，差点得出"这条闸没用"的错误结论。

规矩：① 变异检验前先 `ps -eo pid,comm | grep zhuochong_previ` 确认没有残留；
② 跑 smoke 一律用 `make smoke`（`--spawn --port 5200`）或自己带 `--spawn --port <新端口>`；
③ `make` 不要加 `-s` 再 `>/dev/null`，重建失败你会看不见。
（杀进程仍然只能 `pkill -x zhuochong_previ` —— `-f` 会杀掉自己，`-x` 有 15 字符名长上限。）

## 113. "改了系数但画面不变"要当成**改动没落到地方**，不是系数不够大（2026-10-15）

G107 查了一整轮才找到真因，弯路全在这一点上。症状：把 `mouth_open.alpha` 的 bind scale
从 −0.9 一路拉到 −3.5，渲出来的对照网格**四行肉眼完全一样**。当时第一反应是"斜率还不够陡"，
差一点就去改更大的数。实际逐字节一量：满张时 −0.9 与 −3.5 两版整个嘴区只差 590 字节、
最大 **12/255** —— 这个部件在满张时本来就看不见，再怎么调都不会影响画面。

规矩：**调参之前先证明这个参数能改变像素**。做法二选一 ——
① 渲"极端值对照"（取值域两端各渲一帧，逐字节 diff，差异必须显著）；
② 直接把部件从 rig 里摘掉渲一帧，看画面少了什么（贡献差分）。
"四行雷同"本身就是一条硬证据，它说的不是"幅度不够"，是"你调的东西不参与成像"。

## 114. 消去法的读图要配**差分图**，光看合成结果会读反（2026-10-15）

同一轮里还踩了一次：做"逐个拿掉嘴部件"的对比图时，6 倍放大下看成了
"去掉 `mouth_cavity` 胡子就没了"，于是把矛头指向口腔件。实际上那一格里胡子**还在**，
只是嘴整个闭上了、胡子落在浅肤色上太淡没看见。后来出了贡献差分图
（`baseline − 去掉某件`，白=这件画的像素）才发现 cavity 画的是一个**干净椭圆**。

规矩：消去法不要只看"少了什么"的合成图，要看**差分图**——
差分图把"这一件到底画了哪些像素"单独拎出来，不受底下其他层的颜色干扰。
放大倍数也要够：6× 看不出的东西 12× 能看出来。

## 115. 不在重建链上的切件脚本 = 一颗定时炸弹（2026-10-15）

`sprites/mouth_open.png` 是 `tools/make_parts.py` 切出来的，而那个脚本**不在
`rebuild_parts.sh` 里**。于是它停在很久以前某次手工运行的坐标上，中间 body_full 换过、
别的件重切过很多轮，它一直没动 —— 实测落点 `y252..275`，真笑线 `y246..250`，
**零重叠**，而所有闸都是绿的（它尺寸合法、有透明像素、不是空图）。

已有闸「切件工具都进了重建链」只匹配 `make_*_parts.py`，`make_parts.py` 恰好也匹配……
但它本来就没进链，闸却没红——因为那条闸查的是"链里引用的工具都存在"和
"`make_*_parts.py` 都在链里"，而 `make_parts.py` 在 `off_chain` 之外却又确实没在链里。
**这条闸当时应该红的。**（本轮新加的三条 selfcheck 盯的是笑线那一处，
更一般的"孤儿切件脚本"检查记为后续。）

规矩：任何写进 `sprites/` 的脚本，要么进重建链，要么在文件头第一行写明
"本脚本不在重建链上，产物是 XXX，谁负责更新"。产物对不上源图的风险，
静态闸很难发现 —— 要有一条"产物落点 vs 实测特征"的对位闸（本轮给笑线加的就是这种）。

## 116. 调试台和正式交互是**两条不同的路**，验收要两条都走（2026-10-15）

G105 返工的直接原因：我所有的验证都用 `/api/poke`（= 舞台下面那排按钮走的路），
而用户习惯用**右边调试台**的动作按钮，那是 `/api/action`。两条路在引擎里分叉得很早：

    /api/poke   → zpet_poke   → match_rule → run_rule → zrig_action_request
    /api/action → zpet_action_request       →            zrig_action_request

清句逻辑写在 `run_rule` 里，调试台那条路根本不经过。**五条 smoke 全绿，用户一点就露。**

规矩：凡是"用户能从界面触发"的行为，列出它的**所有** UI 入口（快捷按钮 / 调试台 /
语音组件 / 聊天），每条入口至少过一遍闸。`web/components/*.js` 里 grep 一次
`api(` 就能把入口数清楚 —— 当时花 10 秒就能避免这次返工。

## 117. 表情参数"看起来合理"不等于"语义正确"，先查官方再调幅度（2026-10-15）

`surprised` 用 `ParamEyeBallForm +1.0` 表达惊讶，直觉上"眼睛瞪大"很合理，
实际渲出来是虹膜被撑大到 1.18x/1.22x，用户原话「像个怪物一样很怪」。

① **瞪大眼有专用参数** `ParamEyeLWide`（"widen **beyond the extents of** ParamEyeLOpen"），

② 惊讶时瞳孔**应该变小**（r/Live2D 两个独立帖子都写 "extra opened eye + smaller pupil"）。
   我们做成了放大，方向反了。
③ 附带发现 `ParamEyeBallForm` 这个名字我们也用错了 —— 官方语义是"弯曲眼睛轮廓"。

规矩：动表情参数之前先在 `docs/REFERENCE_NOTES.md` 里查有没有官方口径，没有就上网查一遍

## 118. 支持你预设结论的数字，要比反对你的数字查得更凶（2026-10-15）

用户问能不能自己渲 3D。我心里的答案是"不行，我们是 CPU 软渲染"，
于是写了个基准去"确认"——第一版跑出 **5 秒一帧（0.2fps）**。
数字完美支持了我的预设，我差点就拿着它去写否决结论。

复查发现**基准本身是错的**：我用随机顶点连三角形，于是每个三角形横跨整个人体包围盒，
包围盒光栅化每帧扫 7.9M 像素再被重心坐标一一剔掉。真实网格的三角形是**小片**
（平均 400px）。改成参数化壳体连相邻点后：**41ms，24fps** —— 完全是另一个结论。
补上纹理采样和 MToon 描边遍后 116.7ms，对照 2D 的 30.8ms，**贵 4 倍，不是做不到**。

规矩：
- **跑出来的数字如果正好支持你动手前就有的看法，先去证伪基准，再去用它。**
  反过来，一个反驳你的数字反而可以先信（它至少不是确认偏误的产物）。
- 性能基准必须做**单调性对照**：无纹理 41.3 → 加纹理 79.1 → 加描边 116.4，
  三档比例合理（1.9× / 1.5×），说明测的是真实工作量而不是某条退化路径。
  一个孤零零的数字，哪怕量了十遍也还是一个数字。
- 基准源码要进仓库（`tools/bench/bench_soft3d.c`），不能留在 `/tmp` ——
  A33.3 要求证据可复算，`/tmp` 下轮就没了。

## 119. "能不能做 X" 先查 X 和已有的 Y 是不是同一件事（2026-10-15）

用户一口气问了四件事：VRChat 接入、3D 模型控制、唱歌、语气变化。
看上去是四个方向、四份工作量。查完官方文档发现**前两件是同一件事**：
VRChat、VMC Protocol、VSeeFace、Warudo、bHaptics、TouchOSC **全都走 OSC over UDP**，
报文格式同一个。写一次约三百行的 OSC 编解码，上面这些一起通；
而"控制 3D 模型"的绝大部分需求（驱动用户已有的 VRM/VRChat 模型）根本不需要我们渲 3D。

反过来，看着像一件事的"唱歌"其实是三件（跟唱同步 / 外挂 SVS 引擎 / 实时合成），
成本差两个数量级，混在一起报等于骗人。

规矩：接到需求先问两句 ——
**"这几件是不是同一件？"**（找公共底座，比如 OSC 总线、音频特征流 A39）、
**"这一件是不是其实是三件？"**（按成本分档，各自单独承诺）。
这一步花十分钟，能省掉整条做错的路。

## 121. 回答"能不能做 X"之前，先查"别人做的 X 是怎么做的"（2026-10-15）

用户问唱歌，我答：「SVS 的输入是乐谱，TTS 的输入是文本，没有逐音符 F0 入口就唱不准调。」
这句话**是对的**。然后我由它推出「所以唱歌要乐谱 + 1–3 小时标注 + GPU 训练」，
**这一步错了**。用户一句话就戳破：「那那些网站上 AI 唱歌的音频怎么来的？」

查下来：网上绝大多数 AI 唱歌**既不是 TTS 也不是 SVS**，是**换音色**——
拿一首已有的歌，把人声替换成目标音色，旋律节奏咬字全部来自原唱。

错在哪：**我查的是"唱歌这件事在技术上怎么实现"，没查"市面上的成品是怎么做出来的"。**
前者让我进了合成这条路，后者才会告诉我主流根本绕过了合成。

规矩：
- 回答"能不能做 X"时，**必须有一步是去看现成的 X 是怎么做出来的**
  （搜"教程/流程/workflow"，不是搜"原理/architecture"）。
  用户看到的是成品，他问的也是成品，不是论文。
- **一个正确的前提 + 一步没查过的外推 = 错误的结论**，而且因为前提是对的，
  这种错特别难自查 —— 当时我还觉得自己"查过了"。外推也要单独查。
- 用户说「网上总会有的」时，大概率他见过成品。**他的质疑本身就是证据**，
  这时候第一反应应该是"我漏了什么"，不是"我再解释一遍为什么难"。
