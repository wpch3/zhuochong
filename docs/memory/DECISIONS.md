# 结论登记表（A33）

> **为什么有这份文件**：2026-10-15 用户指出「你自行推翻了很多自己得出的结论，
> 下次再给出结论之前一定要仔细确认，再三检查。旧结论可以推翻，但是检查必不可少」。
>
> 推翻旧结论本身不是问题 —— **不检查就下结论**才是。复盘 2026-10-14 那轮被推翻的四条，
> 每一条都不是算错，而是**下结论的时候少做了一步验证**：
> 前提没验（"踮脚鞋会变扁"）、只做一次模拟就否决（"脚部拆件不可行"）、
> 指标选错（"异号等量 = 修好了"）、否定结论没复查（"docs.live2d.com 不可达"）。
>
> **编号用 `DC`（DeCision）前缀**：`D1~D20` 在 `REQUIREMENTS.md` 里已经是立绘需求系列
> （D19 = 被遮挡区必须 AI 重绘），两套都叫 D 会让"D19"同时指两件事 —— 这正是断代的温床。
>
> 所以凡是**有后果的结论**（会关掉一条路、会决定别人照着做什么、会写进别的文档）
> 都登记在这里，四个字段缺一不可，`tools/selfcheck_repo.py::check_decisions` 会判。

## 怎么写一条

```
### DC## <状态> 一句话结论（日期）
- 前提：这条结论成立的前提是什么，**这个前提本身是怎么验证的**
- 证据：命令 / 实测数字 / 文件路径（至少两样）
- 负控：故意改坏之后它红不红；或者"确定不受影响"的对照项读数
- 复查触发：什么情况下这条会失效，要重新验
```

状态只有三种：**✅采纳** / **❌否决** / **🔁已推翻**（必须写「→ 由 DC## 取代」）。

**❌否决的门槛最高**：否决会关掉一条路，代价最大 —— 必须回答"如果反过来会怎样"，
不能只拿一次模拟定案（DC01 就是这么翻的车）。

### DC42 ✅ 自己渲 3D 不是"做不到"，是"排在 2D 之后"——我准备的否决被实测推翻了（2026-10-15）

- 前提：用户问「能否制作接入 vrchat 以及 3d 模型控制」。我的第一反应是否决自渲 3D：
  本项目是纯 C 的 CPU 软件光栅器（DC26），没有 GPU 后端，3D 要蒙皮 + 深度 + 卡通着色，
  "显然"跑不动。**按 A33.2，否决类结论必须回答"如果反过来会怎样"，所以先去量。**
- 证据：写了 `tools/bench/bench_soft3d.c`（848×1360、2 万三角、3 层 overdraw、
  4 权重蒙皮、透视正确 UV、双线性纹理、MToon 描边遍），
  `gcc -O2 -o /tmp/vb tools/bench/bench_soft3d.c -lm && /tmp/vb 20000 3 2`：
  **单线程 116.7ms / 8.6fps**；去掉纹理与描边 41.3ms / 24.2fps；4 万三角 131.7ms。
  对照本项目 2D 一帧 30.8ms（DC37）——**3D 约贵 4 倍，不是数量级不可能**。
  再叠上分块多线程（2D 上实测 1.66×/2 核）与用户本机核数，30fps 够得着。
  **所以原来那个否决是错的，当场作废。**
- 负控：**第一版基准给出 5 秒/帧（0.2fps）**，差点让我"拿到数据支持的错误否决"。
  复查发现是基准自己错了：随机顶点连三角形 → 每个三角形横跨整个人体包围盒 →
  包围盒扫描 7.9M 像素再被重心坐标剔掉。改成参数化壳体连相邻点（平均三角 400px，
  和真实网格一致）后变成 41ms。**一个支持你预设结论的数字，要比反对你的数字查得更凶。**
  正向对照：无纹理 41.3 → 加纹理 79.1 → 加描边 116.4，三档单调且比例合理（纹理 ~1.9×、
  描边 ~1.5×），说明测的是真实工作量而不是某个退化路径。
- 复查触发：① 如果 2D 主线（T30/T31）收口后仍有预算 —— 这条就该从"排后"变成"开工"；
  ② 如果实测本机多核下 3D 仍进不了 30fps —— 那时才谈 GPU 后端，而不是现在拿它当借口；
  ③ 真正拦住 3D 的**不是帧率而是工程量**（glTF/VRM 解析、morph target、半透明排序、
  AA、摇骨物理，2D 管线里一样都没有），这个判断如果被某个现成的 MIT 纯 C 库推翻，立刻复查。

### DC45 ✅ 网上的 AI 唱歌主流是"换音色"不是"合成歌声"，我把问题框错了（2026-10-15）

- 前提：用户问「那些网站上 AI 唱歌的音频和视频怎么来的？我们不能做吗？」
  我上一轮答的是「唱歌 = SVS，要乐谱 + 1–3 小时标注歌声 + GPU 训练」。
  **这个框架本身就错了** —— 我默认了"唱歌"= 从零合成歌声，于是整条路被我算得又贵又远。
- 证据：查下来网上 AI 唱歌有**三条完全不同的技术路**，占比最大的那条我压根没提：
  ① **AI 翻唱 = RVC / so-vits-svc（绝大多数，"AI 孙燕姿"这一类）**：
     拿一首**已有的歌** → UVR5/Demucs 分离人声伴奏 → **把人声换成目标音色** → 混回伴奏。
     **旋律、节奏、咬字、情感全部来自原唱，AI 只换音色**，所以根本不需要乐谱、不需要标注。
     RVC（MIT，38.7k★，2026-10-15 当天仍在更新）官方 README 写明
     **「推荐至少收集 10 分钟低底噪语音数据」**，有 ~50h VCTK 底模兜底；
     推理 4GB 显存、训练 6GB，RTX3060 上 200 轮约 1–2 小时。
  ② **端到端生成（Suno / Udio）**：文字 → 整首歌（词曲唱编混全包）。
  ③ **SVS 从零合成（DiffSinger / ACE Studio / Synthesizer V）** —— 我上一轮只讲了这条。
- 负控：**反过来检验"是不是我记错了、其实主流就是 SVS"** —— 不是。
  三个独立来源（知乎教程、CSDN 实操、幕后 muhou 工具站）描述的 AI 翻唱流程**完全一致**，
  都是"分离 → 换音色 → 混音"三步，没有一个提到乐谱或 MIDI；
  so-vits-svc 作者自己的声明也是「这个项目是为了让开发者最喜欢的动画角色唱歌而开发的」。
  另一侧负控：**查 RVC 官方仓库当前树，334 个文件里一个 onnx 都没有** ——
  所以"RVC 导出 ONNX 就能塞进我们纯 C"这个念头当场被我自己掐掉了（只有 `rmvpe.onnx`
  是官方提供的，hubert 和生成器要自己导，社区那个导出工具 ★0 无许可，不能依赖）。
  现实路径只能是**当外部进程调用**。
- 复查触发：① RVC 官方哪天内置 ONNX 导出 → 重新评估能不能进我们自己的运行时；
  ② 出现 CPU 上可实时的 VC（现在 CPU 推理比 GPU 慢 10–20×，实时 90–170ms 必须有 GPU）；
  ③ 用云端 TTS 音色去训练衍生 RVC 模型**可能违反 TTS 服务条款**，这一条我没查到定论，
  动手前必须先读 Azure/OpenAI 的条款，**不许默认可以**。

### DC46 ✅ 人格只能靠工程手段撑住，微调这条路对我们默认是关的（2026-10-15）

- 前提：用户问「能不能像 neuro-sama 一样模仿人，设置几种变量、工作模式」。
  查 Neuro 的真实做法：**人格烤在权重里，不在 prompt 里**。
  Vedal v2（GPT-3 API）时代确实是 prompt 定义人格，v3+ 换成自己微调的 **2B / q2_k** 模型，
  system prompt 退化成只给**情境**（"你现在在玩 Minecraft"）。
- 证据：① 社区复刻项目 kimjammer/Neuro 的关键发现 ——
  **对齐过的基座模型会抵抗 prompt 里要求的性格**（要它凶、要它骂人，它会软回去），
  这是 prompt 路线的硬天花板，也是 Vedal 非微调不可的直接原因；
  ② **PersonaGym（Deng et al. 2024）量化过 drift：10 轮对话 90%+ 人格一致性，
  100+ 轮掉到 60–70%** —— 没有对抗输入，纯粹是上下文累积稀释了 system prompt 的注意力权重；
  ③ **context rot**：上下文不是越大越好，甜点区 **8K–16K tokens**，更大反而更糊；
  ④ 产品侧佐证：Character.AI 30 天事实召回 ~15%，Kindroid（有结构化 backstory + pinned）~80%。
- 负控：**反过来问"那我们是不是也该微调"** —— 查了一圈，对我们默认是关的：
  主路径是云端 API（A23/A28：DeepSeek / Gemini / GPT / Claude），
  这些供应商**不提供"把我的人格烤进模型"这种微调**，就算有也会带来成本、延迟与供应商锁定。
  Vedal 能微调的前提是**他自己有 GPU、而且跑的是 2B 小模型**（i9-10900K + RTX4090 + 128GB）。
  → 所以短期**只能靠工程手段**：身份每轮重锚 + 分层记忆 + 衰减（A41/A43）。
  另一侧负控：**工程手段到底管不管用，必须能量**，不能凭感觉 ——
  所以 A41 里写死了 drift 度量（固定剧本跑 10/50/100 轮，测人格一致性），
  量不出来就等于没做。
- 复查触发：① **A24（本地模型区块）落地、且用户机器有 GPU** → 重新评估 LoRA 微调，
  那时这条的"默认关闭"就要改；② 出现低成本的人格微调云服务（按量计费、不锁定）；
  ③ 工程手段实测在 100 轮仍掉到 70% 以下 → 说明撑不住，必须上微调或换小模型自托管。

### DC48 ✅ 提分辨率不要动坐标系，动像素密度就够（2026-10-15）

- 前提：T30.1 要让立绘放大时清晰。上一轮验完超分路径（DC44）后，
  原计划是「整条切件链切到 2× 坐标系」：prepare_sprites 出 2× 的 body_full，
  16 个切件脚本都在 2× 坐标里跑，make_rig 再把坐标除回画布尺度。
- 证据：**开工第一件事是数改动面，数完就否了这个方案** ——
  坐标散在 **17 个 JSON、上百个字段名**里（pos / size / pivot / patch_pos /
  ball_pos / iris_center / travel / aperture_px / socket_size / lash_travel …），
  而且 `*_px` 后缀里有些是**距离**、有些是**统计量**（filled_px / carved_px），
  逐个判断必然漏，漏一个就是整件错位、而且很难查。

### DC53 ✅ 物理必须按固定步长积分；"按真实 dt 积分"只对了一半（2026-10-16）

### DC51 ✅ 换高清素材时，"scale 减半"只对标量成立；数组 scale 的绑定必须跟着减半（2026-10-15）

- 前提：T30.1 当时写的是"画布坐标完全不动，变的只有素材像素密度和与之配套的 scale"。
  **这句话只对一半。** zrig 里 `scale` 有两种语义，换算方式不同：
  · 标量 `"scale": s` → `p->scale`，通道**乘性**：最终 = `s × p_s`。
    素材 ×2 + s ÷2 ⇒ 任意 `p_s` 下渲染几何不变，绑定**不用动**。
  · 数组 `"scale": [sx,sy]` → `p->scale_x/scale_y`，通道**加性**
    （`compute_draw_state`: `part_sy = scale_y + (p_sy − 1.0)`）。
    基准 ÷2 了而增量还是 1x 口径 ⇒ **形变整整 ×2**。
- 证据：全 rig 11 条 sx/sy 绑定里真受影响的只有 3 条（都在 `mouth_mask`，
  `mouth_cavity` 经 `motion_from` 跟随）；`eye_*_ball` 是标量 scale，**不受影响**
  （第一遍按"@2x + 有 sx/sy 绑定"扫出 9 条，是误判，按语义重扫后自纠为 3 条）。
  算术与渲染都对得上：`ParamMouthOpenY=1` → `44 × (0.02725 + 0.895) = 40.6px`，
  实测开口 40.6px；减半后 `44 × (0.02725 + 0.4475) = 20.9px`，实测 20.9px，
  正好等于 1x 时代的 `22 × (0.0545 + 0.895) = 20.9px`。
  git 对照锁死回归点：`415486d`（1x，22px 素材 + bind 0.895）→ `d83e7a5`（@2x，
  44px 素材 + bind 仍 0.895）。
- 负控：把 3 条绑定还原成未减半，5 项闸全红并精确复现坏数字
  （开口 40.6px、嘴下沿 body_full y=289 vs 下巴 272）；
  反过来问"如果所有 @2x 件的绑定都减半会怎样"——**会把标量件改坏**：
  标量件的绑定是乘性的，再减半等于形变只剩一半。所以闸只盯数组 scale 的件。
- 复查触发：① 以后再出现 `"scale": [sx,sy]` 的新部件（嘴以外），加进来时

  ② 哪天把超分倍率从 2 改成别的，`0.5` 和 `× 0.5` 两处都要跟着改。
