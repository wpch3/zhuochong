# 结论登记表（A33）

> **为什么有这份文件**：2026-10-15 用户指出「你自行推翻了很多自己得出的结论，
> 下次再给出结论之前一定要仔细确认，再三检查。旧结论可以推翻，但是检查必不可少」。
>
> 推翻旧结论本身不是问题 —— **不检查就下结论**才是。复盘 2026-10-14 那轮被推翻的四条，
> 每一条都不是算错，而是**下结论的时候少做了一步验证**：
> 前提没验（"踮脚鞋会变扁"）、只做一次模拟就否决（"脚部拆件不可行"）、
> 指标选错（"异号等量 = 修好了"）、否定结论没复查（"docs.live2d.com 不可达"）。
>
> **编号用 `DC`（DeCision）前缀**：`D1~D20` 在 `REQUIREMENTS.md` 里已经是立绘需求系列
> （D19 = 被遮挡区必须 AI 重绘），两套都叫 D 会让"D19"同时指两件事 —— 这正是断代的温床。
>
> 所以凡是**有后果的结论**（会关掉一条路、会决定别人照着做什么、会写进别的文档）
> 都登记在这里，四个字段缺一不可，`tools/selfcheck_repo.py::check_decisions` 会判。

## 怎么写一条

```
### DC## <状态> 一句话结论（日期）
- 前提：这条结论成立的前提是什么，**这个前提本身是怎么验证的**
- 证据：命令 / 实测数字 / 文件路径（至少两样）
- 负控：故意改坏之后它红不红；或者"确定不受影响"的对照项读数
- 复查触发：什么情况下这条会失效，要重新验
```

状态只有三种：**✅采纳** / **❌否决** / **🔁已推翻**（必须写「→ 由 DC## 取代」）。

**❌否决的门槛最高**：否决会关掉一条路，代价最大 —— 必须回答"如果反过来会怎样"，
不能只拿一次模拟定案（DC01 就是这么翻的车）。

- 前提：T30.1 要让立绘放大时清晰。上一轮验完超分路径（DC44）后，

### DC53 ✅ 物理必须按固定步长积分；"按真实 dt 积分"只对了一半（2026-10-16）

- 前提：用户报"测试台状态会左右轻微抽搐"。我原本的假设是"云端预览才 2.5fps，
  慢摆动被采样成台阶，本地就好了" —— **这个假设只对了一部分，先查才发现另有真因**。
- 证据：探针 `/tmp/ph.c` 用真实角色跑，比同一真实时刻 t=2.0 的物理输出（可复算）：
  | 摆 | 60fps | 2.5fps | 倍数 |
  |---|---|---|---|
  | `ahoge_x` | 0.1983 | 0.7188 | **×3.6** |
  | `hand_r_lag` | 0.0175 | 0.1914 | **×11.3** |
  | `side_l_x` | 0.1251 | 0.3492 | ×2.8 |
  根因在 `physics_update`：`dt = now - phys_last; if (dt > 0.1) dt = 0.1;` 然后**一步**
  显式欧拉。大 dt 下 `vel += acc*dt` 用帧初加速度冲过头，`out = pos - target` 被放大；
  而 clamp 到 0.1 又让物理时钟只走真实时间的 1/4，和主体动画脱钩。
- 官方口径：`CubismPhysics::Evaluate` 是 `_currentRemainTime += dt` →
  `while (remain >= 1/Fps)` 定步积分（步内对输入线性插值 `w = h/remain`）→
  `alpha = remain/h` 对输出插值；累计超过 `MaxDeltaTime = 5.0` 直接丢弃。
  官方注释原文：「この仕様は補間範囲を逸脱したことが原因の**震えたような見た目**を回避を
  目的にしている」——**"发抖的观感"，正是用户报的那个词**。
- 负控：把定步长撤回（= 修前引擎）+ 装上最终闸门 → **6 项全红**，
  且实测值与记录的修前值逐位相同（jitter 0.1483 / 0.5179 / 0.1576 / 0.0967，
  dt=0.1 偏 128%、dt=0.4 偏 452%）。修后同夹具为 0.0590 / 0.1370 / 0.0712 / 0.0517、
  3.9% / 57.9%。
- 如果反过来会怎样：若真因只是"云端帧率低"，那么**同一真实时刻**在 2.5fps 和 60fps
  下的物理输出应当基本相等（只是采样点稀疏）。实测差 3.6~11.3 倍，证伪。
- 复查触发：① 以后谁再往 `physics_update` 里塞"按整帧 dt 算一次"的东西，
  `test_core` 的 G113 组会红；② `ZRIG_PHYS_FPS` 改了的话物理参数要重调
  （Cubism 5.0 起官方默认也是 60，见 REFERENCE_NOTES 第二十四批）；
  ③ 若将来改成变步长隐式积分，这组阈值要按新实现重新量，不能照抄。

### DC51 ✅ 换高清素材时，"scale 减半"只对标量成立；数组 scale 的绑定必须跟着减半（2026-10-15）

- 前提：T30.1 当时写的是"画布坐标完全不动，变的只有素材像素密度和与之配套的 scale"。
  **这句话只对一半。** zrig 里 `scale` 有两种语义，换算方式不同：
  · 标量 `"scale": s` → `p->scale`，通道**乘性**：最终 = `s × p_s`。
    素材 ×2 + s ÷2 ⇒ 任意 `p_s` 下渲染几何不变，绑定**不用动**。
  · 数组 `"scale": [sx,sy]` → `p->scale_x/scale_y`，通道**加性**
    （`compute_draw_state`: `part_sy = scale_y + (p_sy − 1.0)`）。
    基准 ÷2 了而增量还是 1x 口径 ⇒ **形变整整 ×2**。
- 证据：全 rig 11 条 sx/sy 绑定里真受影响的只有 3 条（都在 `mouth_mask`，

### DC65 ✅ 「抽搐」先分清是姿态错了还是帧到晚了，这是两件事（2026-10-16）

- 前提：用户看到的"抽搐"有两种完全不同的来源 —— **姿态函数错了**（同一时刻算出来的
  姿势就是跳的）和**帧到达时刻乱了**（每帧姿态都对，只是到得不均匀）。
  两者的修法在不同的文件里，查错方向会整轮浪费。
- 证据：先验姿态函数 —— 同一段时间用 10fps(11 帧) / 30fps(31 帧) / 60fps(60 帧) /
  不均匀抖动(12 帧) 四种方式推进到**同一个绝对时刻 t=1.0**，`look_x` 分别
  0.89972681 / 0.89985007 / 0.89987096 / 0.89985450，最大差 1.4e-4 = 浮点噪声。
  姿态函数无辜 ⇒ 问题在到达时刻。再量通道：满尺寸一帧 PNG 190.1 KB，
  10fps 需 1.86 MB/s；本地链式拉取上限 40fps，而测试台写死 `setInterval(100)` = 10fps 封顶。
- 负控：第一版 harness 把 `zrig_tick(r, dt)` 当成了传增量，三档固定帧率全返回
  `look_x=0.000000`，差点据此说"引擎有问题"。实际签名是 `zrig_tick(zrig*, double now)`
  传**绝对时间**。改对之后四档才一致。—— 这一跤本身就是负控的价值：
  一个"看起来支持我结论"的异常数字，先怀疑测量装置。
- 复查触发：以后再收到"抖/卡/抽"类反馈，固定按这个顺序查：
  ① 姿态函数对不对（同一绝对时刻、不同帧率，结果必须一致）；
  ② 帧有多大、链路要多少带宽；③ 刷新循环有没有在途保护和顺序保护。
  前两步都没问题才去怀疑物理或动画曲线。另外注意：**本地并发实测没复现出乱序**
  （4 轮 × 6 并发全顺序），所以"旧帧后到"是按代码缺口补的保护，不是实测到的现象。

  （`v = vis_cur[k] + (v − vdef) × (1 − w)`，w 随这一帧口型用力程度缩放）。
  也就是说挂在 Form 上的微表情**一说话就被压掉**，恰恰在最需要表情的时候消失。
  所以新开 `ParamMouthX`（Animaze 扩展表的 ID），实测 `ParamMouthX` 不触碰 `sx`
  —— 单测里有一条负控专门钉这件事。
- 负控：如果反过来会怎样？把微表情挂回 Form 的话，静默时能看、一说话就平掉，
  而且因为 w 是连续的，会出现"说得越用力表情越淡"的渐变，比干脆没有更怪。
  单测 `test_micro_expression` 里那条 `ParamMouthX 不许动 sx` 就是这条决策的守卫：
  哪天有人图省事把 MouthX 的 rot 换成 sx，立刻红。
- 复查触发：① 如果以后把口型合成口径从"覆盖+余味"改回官方的纯加算
  （`addParameterValueById(id, v, 0.8)`），这条的前提就变了，要重新算一遍；
  ② 如果给嘴做了真正的网格变形器（不再是整件变换），单边嘴角应该改走
  「口角L/Rデフォーマ」，那时 `ParamMouthX` 的 `rot_deg` 实现要一起换掉。

### DC67 ✅ 物理核心换成官方那套 2D 粒子摆，新旧内核并存一个版本（2026-10-17）

- 前提：用户说「目前还没有真实的物理效果」。我们的摇物是
  **1D 弹簧 `acc = k(target−pos) − c·vel`，输出 `clamp(pos−target, ±max)` 的像素滞后量**；
  官方是 **2D 粒子链，输出 `DirectionToRadian(parentGravity, translation)` 的摆角**。
  本来有个省事的选项：继续给 1D 弹簧加系数、加段数，把"摆得更软"调出来。
- 证据：1D 弹簧的输出在数学上等于**输入的高通滤波** —— 输入不动，输出必然恒为 0，
  这是模型的性质，不是系数没调好。实测佐证就写在我们自己的挂件表里
  （`characters/xiaoxun/design/attachments.json:127`）：给尾巴混了 `ParamBreath` 权重 2.2/1.6，
  呼吸 0.28Hz 下**尾巴只摆 0.3 px**。而官方的摆静止时仍有姿态，是因为摆角由
  "粒子位置相对重力方向"算出来，和输入动不动无关。所以必须换模型（`zphys2`），
  而不是调参。并存一个版本的理由同样是实测代价：现网 **35 条摆**都在用旧字段，
  一次性迁移会把"默认外观不变"的回归闸全部打红，分不清是迁移错了还是内核错了；
  做法是 `rig.json` 新增 `physics2` 段，两套内核同时在跑、逐件迁移、迁完一件对一次 A/B，
  全部迁完后下一个版本删掉旧内核。
- 负控：如果反过来会怎样？原地把旧内核的输出口径从像素改成弧度的话，
  35 条摆的系数量纲同时失准（像素 → 弧度），而且**没有任何一帧的对照基线**可以判断
  "现在是对了还是只是换了种错法"。守卫：`tools/physics_ref.py` 的 600 步对拍（<1e-6）
  与"旧配置产物逐字节不变"两条闸，任一红就说明并存没做干净。
- 复查触发：① 如果以后决定直接跑官方 `physics3.json`（T47.5）而不再自己存参数，
  `physics2` 退化成运行时结构，这条的"并存"安排要重写；
  ② 如果上了 GPU/多线程求解，DC53 的固定步长口径要重新确认一遍。

### DC68 ✅ 外设联动只记"哪一区按下"，绝不记键值内容（2026-10-17）

- 前提：T48 的键盘/手柄模拟模式（bongo cat 类）要全局监听键鼠，
  技术路径就是 Windows `WH_KEYBOARD_LL` / `WH_MOUSE_LL` 低级钩子
  —— 和键盘记录器用的是同一个 API。省事的做法是先把事件全量记下来再过滤。
- 证据：我们的功能需求只需要知道"哪只手该落下" —— 即**左/中/右三个分区 + 按下/抬起**，
  根本不需要键值。查证 Bongobs-Cat-Standalone 的实现也确认了钩子方案
  **不注入 DLL、系统级生效、游戏前台也收得到**，所以降维不会损失功能。
  据此定口径：钩子回调里立刻把事件降维成"分区 + 按下/抬起"，
  **原始键值不出回调、不进日志、不写磁盘、不上网**；设置里给总开关，
  默认关闭，首次启用要用户显式同意。Linux 走 `/dev/input/eventN` 需要用户组权限，
  安装脚本必须显式提示，不许偷偷加 udev 规则。
- 负控：如果反过来会怎样？先全量记录再过滤的话，任何一次崩溃转储、调试日志、
  或者以后某个"回放最近输入"的调试功能，都可能把用户密码带出去 —— 这是不可逆的信任损失，
  而换来的好处是零。守卫：T48 的代码评审里，钩子回调函数体内不许出现任何
  `fprintf`/`log_*`/缓冲区写入；闸可以做成源码扫描。
- 复查触发：① 如果以后做"打字速度统计/成就"（T48.4），聚合量只能在内存里算，
  落盘的只能是计数，不能是序列；② 如果要支持宏/快捷键自定义（需要真键值），
  那是另一套授权口径，必须重新立条目，不能顺手复用这条。

### DC70 ✅ 摆的参数名直接照抄编辑器旋钮名（2026-10-17）

- 前提：新内核 `zphys2` 要定字段名。旧内核用的是自造名（`k` / `c` / `ratio` / `max`），
  顺手延续下去最省事。
- 证据：社区教程给的是**具体数值配方**而不是公式 —— 例如"延迟跟随"的配方是
  「揺れやすさ中等 + 反応速度低 + 収束最大」，`Mobility` 的常用区间是 0.7~0.99。
  这些数值只有在字段语义一致时才能直接抄。所以字段名取
  **`radius` / `mobility` / `delay` / `acceleration`**（对应编辑器的
  長さ / 揺れやすさ / 反応速度 / 変換倍率，也是 physics3.json 里的 JSON 字段名），
  T47.5 做双向互通时字段一一对应，不用维护映射表。
- 负控：如果反过来会怎样？用自造名的话，每次抄教程都要先做一次心算换算
  （而且换算关系没地方可查，只能靠注释口口相传），physics3 互通还要多一张映射表
  —— 映射表就是以后出 bug 的地方。守卫：T47.5 的"解析→导出→再解析三者等价"对拍，
  如果字段语义偏了，这条闸会红。
- 复查触发：如果官方后续版本改了字段语义（例如 `Mobility` 的归一化区间变了），
  以 `tools/physics_ref.py` 的对拍结果为准，不以字段名为准。
