# 结论登记表（A33）

> **为什么有这份文件**：2026-10-15 用户指出「你自行推翻了很多自己得出的结论，
> 下次再给出结论之前一定要仔细确认，再三检查。旧结论可以推翻，但是检查必不可少」。
>
> 推翻旧结论本身不是问题 —— **不检查就下结论**才是。复盘 2026-10-14 那轮被推翻的四条，
> 每一条都不是算错，而是**下结论的时候少做了一步验证**：
> 前提没验（"踮脚鞋会变扁"）、只做一次模拟就否决（"脚部拆件不可行"）、
> 指标选错（"异号等量 = 修好了"）、否定结论没复查（"docs.live2d.com 不可达"）。
>
> **编号用 `DC`（DeCision）前缀**：`D1~D20` 在 `REQUIREMENTS.md` 里已经是立绘需求系列
> （D19 = 被遮挡区必须 AI 重绘），两套都叫 D 会让"D19"同时指两件事 —— 这正是断代的温床。
>
> 所以凡是**有后果的结论**（会关掉一条路、会决定别人照着做什么、会写进别的文档）
> 都登记在这里，四个字段缺一不可，`tools/selfcheck_repo.py::check_decisions` 会判。

## 怎么写一条

```
### DC## <状态> 一句话结论（日期）
- 前提：这条结论成立的前提是什么，**这个前提本身是怎么验证的**
- 证据：命令 / 实测数字 / 文件路径（至少两样）
- 负控：故意改坏之后它红不红；或者"确定不受影响"的对照项读数
- 复查触发：什么情况下这条会失效，要重新验
```

状态只有三种：**✅采纳** / **❌否决** / **🔁已推翻**（必须写「→ 由 DC## 取代」）。

**❌否决的门槛最高**：否决会关掉一条路，代价最大 —— 必须回答"如果反过来会怎样"，
不能只拿一次模拟定案（DC01 就是这么翻的车）。

## 三、2026-10-15 调研轮（证据等级见 REFERENCE_NOTES 第二十批表头）

### DC17 ✅ 实时 STT 先用 faster-whisper(small/turbo) + Silero VAD，不自己写流式 ASR（2026-10-15）

- 前提：桌宠"听到就回应"不需要字幕级准确度，**端点检测（说完没有）比 WER 更重要**。
  这个前提来自产品定位，不是测量；**如果用户要求做实时字幕，前提就变了**。
- 证据：Whisper 本身不是流式模型（★★ 论文 + 官方讨论）；Whisper-Streaming 论文在 A40 上
  英语平均延迟 3.3s（<https://arxiv.org/html/2307.14743>）；faster-whisper 自带 Silero VAD，
  多家评测给流式 500~800ms（large-v3）/ 200~300ms（turbo）—— **☆ 二手，未实测**。
- 负控：➖ 沙箱没有麦克风，现在做不了。**已登记为真机验收项**（ACCEPTANCE AC-STT-1），
  判据：从"说完"到"首字出来" < 800ms，端点误判率 < 10%。
- 复查触发：真机实测不达标 → 换原生流式族（NeMo FastConformer cache-aware，80~320ms lookahead）。
  **在真机数据回来之前，这条只是"先接哪个"，不是"就用它"。**

### DC18 ✅ 双路由判据定为三支柱：敏感→本地、复杂/长→云端、忙/故障→互相兜底（2026-10-15）

- 前提：本地模型质量低于云端、但没有 API 费且无隐私外泄；两边都可能不可用。
  前提的量化依据来自论文对照表（全本地质量 0.42 / 响应 3.97s vs 全云 0.57 / 1.06s）。
- 证据：<https://arxiv.org/html/2507.15553v1>（★★，路由器综合分 0.752 vs 全云 0.667）；
  三家工程博客给出同一套三支柱与阈值量级（>512 token 上云、GPU 利用率 85/90% 溢出）。
- 负控：✅ **已做（2026-10-15）** —— `tests/test_core.c` 用自造混合路由表（本地 + 云端各一条）
  验了六条分叉；真正的负控是**在敏感分支偷偷加一句上云 fallback**（别人最容易"顺手贴心"的
  那种改动）→ 两项立刻判红。另有一条同局面负对照：**本地全关时，不敏感的请求确实会落到
  deepseek，带 sensitive 的那条被拒** —— 两者唯一的差别就是那个标记。
- 复查触发：阈值（512 token / 85% 利用率）是**抄来的**，必须用自己的记账数据重标；
  真实分流比例若长期偏离 70~85%，说明阈值不对。

### DC19 ✅ 生图支持"本机 ComfyUI + 云端 API"双路；❌ 生视频只走云端 API，不做本地（2026-10-15）

- 前提：桌宠用户的常见显卡是 8~12GB。本地视频模型（Wan 2.x / HunyuanVideo）要 24GB+。
  **这个前提是"常见配置"的假设，不是统计** —— 所以 UI 要先做显存体检再给建议。
- 证据：ComfyUI 有 `POST /prompt` + WebSocket 的现成 API；显存档位多家口径一致
  （6GB 只能 SD1.5 / 8GB SDXL `--lowvram` 约 30s / 12GB 舒适 / 24GB 才谈视频）；
  云端视频 $0.02~0.20 每秒（☆ 二手价格，会变）。
- 负控：**"如果反过来会怎样"** —— 反过来 = 本地跑视频 —— 在 8~12GB 上要么跑不起来、
  要么单条 10s 片子几分钟且画质差，**而桌宠的视频需求本来就是低频**，
  花一条本地推理栈的工程量去服务低频需求不划算。**若用户机器是 24GB+，这条立刻复查。**
- 复查触发：① 用户确认自己的显卡 ≥24GB；② 出现 12GB 能跑的视频模型；③ 云端价格大涨。

  此后素材重做 N 次（刘海 / 侧发 / 闭眼 / 张嘴 / 鞋）**没有一次需要回去重算系数**。
- 负控：➖ 不适用（这是路线选择，没法"改坏一次看红不红"）。
