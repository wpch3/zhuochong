# 结论登记表（A33）

> **为什么有这份文件**：2026-10-15 用户指出「你自行推翻了很多自己得出的结论，
> 下次再给出结论之前一定要仔细确认，再三检查。旧结论可以推翻，但是检查必不可少」。
>
> 推翻旧结论本身不是问题 —— **不检查就下结论**才是。复盘 2026-10-14 那轮被推翻的四条，
> 每一条都不是算错，而是**下结论的时候少做了一步验证**：
> 前提没验（"踮脚鞋会变扁"）、只做一次模拟就否决（"脚部拆件不可行"）、
> 指标选错（"异号等量 = 修好了"）、否定结论没复查（"docs.live2d.com 不可达"）。
>
> **编号用 `DC`（DeCision）前缀**：`D1~D20` 在 `REQUIREMENTS.md` 里已经是立绘需求系列
> （D19 = 被遮挡区必须 AI 重绘），两套都叫 D 会让"D19"同时指两件事 —— 这正是断代的温床。
>
> 所以凡是**有后果的结论**（会关掉一条路、会决定别人照着做什么、会写进别的文档）
> 都登记在这里，四个字段缺一不可，`tools/selfcheck_repo.py::check_decisions` 会判。

## 怎么写一条

```
### DC## <状态> 一句话结论（日期）
- 前提：这条结论成立的前提是什么，**这个前提本身是怎么验证的**
- 证据：命令 / 实测数字 / 文件路径（至少两样）
- 负控：故意改坏之后它红不红；或者"确定不受影响"的对照项读数
- 复查触发：什么情况下这条会失效，要重新验
```

状态只有三种：**✅采纳** / **❌否决** / **🔁已推翻**（必须写「→ 由 DC## 取代」）。

**❌否决的门槛最高**：否决会关掉一条路，代价最大 —— 必须回答"如果反过来会怎样"，
不能只拿一次模拟定案（DC01 就是这么翻的车）。

### DC48 ✅ 提分辨率不要动坐标系，动像素密度就够（2026-10-15）

- 前提：T30.1 要让立绘放大时清晰。上一轮验完超分路径（DC44）后，
  原计划是「整条切件链切到 2× 坐标系」：prepare_sprites 出 2× 的 body_full，
  16 个切件脚本都在 2× 坐标里跑，make_rig 再把坐标除回画布尺度。
- 证据：**开工第一件事是数改动面，数完就否了这个方案** ——
  坐标散在 **17 个 JSON、上百个字段名**里（pos / size / pivot / patch_pos /
  ball_pos / iris_center / travel / aperture_px / socket_size / lash_travel …），
  而且 `*_px` 后缀里有些是**距离**、有些是**统计量**（filled_px / carved_px），
  逐个判断必然漏，漏一个就是整件错位、而且很难查。
  换成：**切件链一行不改**，在它跑完之后插一步把每个 sprite 单独放大到 2×，
  `make_rig` 发现 `@2x` 就改用它并把 `scale` 乘 0.5。
  画布坐标系完全不动 → rig 里所有像素常数（travel / lift / pivot / hold 线、
  `DEG_PER_PX` 那个硬编码的 344）**一个都不用改**。
  实测（44 件全量，`logs/asset_qa/hires_full_ab.png`）：
  锐度 0.55 档 **+81%** / 1.0 档 **+95%** / **1.2 档 +96%** / 2.0 档 +48%；
  耗时 0.55 档 9.16→10.37ms、1.0 档 30.99→32.00ms、1.2 档 44.90→45.61ms、
  2.0 档 130.77→136.25ms —— **代价 1.6%~13%**，因为渲染成本由**输出**像素数决定，
  不是源图大小。入库体积 +2.9MB（只给 rig 真正引用的 42 个件做）。
- 负控：**先只改 4 个脸部件做可行性验证，再全量** ——
  4 件版 1.0 档锐度 ×1.947、2.0 档 ×1.948，四档性能全部在 ±1% 噪声内，
  确认"缩小采样会走样"这个担心不成立（肉眼也确认没有振铃）。
  闸侧三条改坏实验全部精确报红：scale 忘了减半 → 点名 seg_head；
  一半 2× 一半 1× → 点名 hair_front 并说明 mask 会对不上；
  @2x 尺寸冒充 → 报出 51x18->96x36。
  另外 check_assets 自己抓出 **21 个键色垃圾像素**（超分把 alpha<40 的洋红残留抬上来了，
  正是 DC44 复查触发条件②预言的），已在高清化里按**和 check_assets 完全一致的口径**修掉。
- 复查触发：① 以后要做 4× 时先重测性能，1.6%~13% 的代价不保证线性；
  ② 新增部件忘了跑高清化 → 「rig 引用的 @2x 都在」那条闸会红，不要靠记忆；
  ③ 如果哪天真的需要在 2× 坐标系里做几何（比如切更细的件），
  再回头评估改坐标系，但那时应该先把 17 个 JSON 的坐标字段收敛成统一 schema。

### DC53 ✅ 物理必须按固定步长积分；"按真实 dt 积分"只对了一半（2026-10-16）

- 前提：用户报"测试台状态会左右轻微抽搐"。我原本的假设是"云端预览才 2.5fps，
  慢摆动被采样成台阶，本地就好了" —— **这个假设只对了一部分，先查才发现另有真因**。
- 证据：探针 `/tmp/ph.c` 用真实角色跑，比同一真实时刻 t=2.0 的物理输出（可复算）：
  | 摆 | 60fps | 2.5fps | 倍数 |
  |---|---|---|---|
  | `ahoge_x` | 0.1983 | 0.7188 | **×3.6** |
  | `hand_r_lag` | 0.0175 | 0.1914 | **×11.3** |
  | `side_l_x` | 0.1251 | 0.3492 | ×2.8 |
  根因在 `physics_update`：`dt = now - phys_last; if (dt > 0.1) dt = 0.1;` 然后**一步**
  显式欧拉。大 dt 下 `vel += acc*dt` 用帧初加速度冲过头，`out = pos - target` 被放大；
  而 clamp 到 0.1 又让物理时钟只走真实时间的 1/4，和主体动画脱钩。
- 官方口径：`CubismPhysics::Evaluate` 是 `_currentRemainTime += dt` →
  `while (remain >= 1/Fps)` 定步积分（步内对输入线性插值 `w = h/remain`）→
  `alpha = remain/h` 对输出插值；累计超过 `MaxDeltaTime = 5.0` 直接丢弃。
  官方注释原文：「この仕様は補間範囲を逸脱したことが原因の**震えたような見た目**を回避を
  目的にしている」——**"发抖的观感"，正是用户报的那个词**。
- 负控：把定步长撤回（= 修前引擎）+ 装上最终闸门 → **6 项全红**，
  且实测值与记录的修前值逐位相同（jitter 0.1483 / 0.5179 / 0.1576 / 0.0967，
  dt=0.1 偏 128%、dt=0.4 偏 452%）。修后同夹具为 0.0590 / 0.1370 / 0.0712 / 0.0517、
  3.9% / 57.9%。
- 如果反过来会怎样：若真因只是"云端帧率低"，那么**同一真实时刻**在 2.5fps 和 60fps
  下的物理输出应当基本相等（只是采样点稀疏）。实测差 3.6~11.3 倍，证伪。
- 复查触发：① 以后谁再往 `physics_update` 里塞"按整帧 dt 算一次"的东西，
  `test_core` 的 G113 组会红；② `ZRIG_PHYS_FPS` 改了的话物理参数要重调
  （Cubism 5.0 起官方默认也是 60，见 REFERENCE_NOTES 第二十四批）；
  ③ 若将来改成变步长隐式积分，这组阈值要按新实现重新量，不能照抄。

### DC77 ✅ 粒子摆内核照抄官方算法，但**修掉官方那处变量覆盖 bug**（2026-10-17 晚）

- 前提：T47.1 要把摆换成官方那套 2D 粒子链。"照抄官方"听起来天经地义，
  但官方 `UpdateParticles()` 里那段把摆随重力方向旋转的代码是这么写的：
  `direction.X = cos*direction.X − direction.Y*sin;`
  `direction.Y = sin*direction.X + direction.Y*cos;`
  **第二行用的是上一行刚被覆盖掉的 `direction.X`** —— 这不是我记错，
  本轮直接从 `api.github.com` 拉下 `Live2D/CubismNativeFramework`
  的 `src/Physics/CubismPhysics.cpp` 原文核对过（第四十四批）。
- 证据：① 这个 bug 平时看不出来：`radian = DirectionToRadian(lastGravity, currentGravity)/5.0`，
  重力方向不变时 radian=0 ⇒ cos=1、sin=0 ⇒ 两种写法结果一样，所以官方多年没人修；
  ② 但我们下一步就要做**风**（T47.3）和**拖动惯性**（T47.4），
  那两件事天天在改重力方向，radian 不再是 0，错误写法会让摆每步都被拉伸一点点
  （它不是旋转矩阵，长度不守恒）；③ 我们的实现里每步都有"归一化回 Radius"的约束，
  所以不会越拉越长，但**方向是错的**，表现为风越大摆得越歪、越不对称。
- 负控：两边的常量和算法一旦不同步，`tests/data/phys2_golden.json` 的 600 步对拍立刻红 ——
  实测把 `ZPHYS2_AIR_RESISTANCE` 从 5.0 改成 5.05（1%），位置偏差就到 **1.138e-01**、
  摆角 1.949e-01，远超 1e-6 的闸。另外 `selfcheck_repo.py::check_phys2` 会比对
  C 与 Python 两侧的三个常量，并校验 Mobility∈[0.7,0.99]、Radius 沿链不变长（都做过负向对照）。
- 复查触发：T47.5 做 `physics3.json` 导入时，如果拿公开模型跑出来的观感和官方 SDK 对不上，
  **第一个要怀疑的就是这里** —— 届时加一个 `compat_official_rotation` 开关，
  让导入的模型按原样（带 bug）跑，自有模型按正确写法跑，不要两边互相迁就。
  另外角度的**旋向**也已经对齐官方（`currentGravity = (sin a, cos a)`），
  这一条同样要在导入测试里复验。

### DC76 ✅ 移调不是年龄感：音高最多 ±14Hz，"萌"靠换音色和节奏，不靠升调（2026-10-17 晚）

- 前提：DC74 认定"年龄感优先用引擎自带的 pitch"，其前提是「引擎 pitch 在模型内部重新合成，
  F0 变了共振峰会跟着自洽」。**这个前提这次被用户的耳朵直接证伪**：语感档上线后用户的原话是
  「现在的语感开了后感觉像小黄人和鼠来宝的音色」—— 小黄人 / 花栗鼠正是"只搬 F0、不搬共振峰"的听感标志。
  我之所以敢用那个前提，是因为五档升调样本时长完全一致（7.49s×4），**但"时长不变"只说明引擎没动节奏，
  根本不能推出"共振峰跟着移了"**。这是一次推理跳步，不是数据错。
- 证据：① 链路复盘：`moe_shoujo` base **+18Hz**，叠情绪（surprised +18）与句尾上扬（+10）之后
  峰值顶到克制上限 **+46Hz**，38 条台词全跑在 +24~+46Hz 区间 —— 正好是发尖最明显的区间；
  ② 声学资料（PLOS ONE `journal.pone.0081022` / phonalab，第四十二批 §42.4）：
  年龄感 = F0 **与** 共振峰间距 ΔF 共同决定，只动 F0 的后果就是花栗鼠；
  ③ 改法与复测：`config/prosody.json` 把 `base_pitch_hz` 18→**0**、句尾上扬 6→4、
  11 种情绪的音高起伏整体压进 ±6Hz、`_restraint.max_abs_pitch_hz` 46→**14**，
  CI 重渲后实测**每一段的音高绝对值都 ≤14Hz**（A/B 六组峰值：4/12/14/8/12/4Hz）。
- 负控：反过来会怎样 —— 把音高压掉会不会"不萌了、又听不出情绪了"？实测**没有**：
  A/B 的时长分层一点没塌（sleepy **+60.8%**、shy **+38.3%**、中性 +10.1%，与降音高之前逐项相同），
  六情绪 demo 仍然 angry 4.49s → sleepy 6.11s 拉得开。
  这反过来证明了一件事：**"听得出情绪"靠的是节奏/停顿/重音，本来就不是靠音高**。
  常设闸门：`_restraint.max_abs_pitch_hz = 14` + `voice_prosody.py --selftest` 第 4 项（克制上限）；
  候选阶梯里**故意留着 +18Hz（⚠ 开始发尖）与 +30Hz（⚠⚠ 小黄人反例）两档**，
  下次谁想加码，先去听这两条。
- 复查触发：换到 Azure Dragon HD（晓伊 cute/shy）/ MiniMax 少女音 / IndexTTS2 之后，
  "萌"由音色模型本身提供，这条 ±14Hz 的上限可以重新评估 —— 但**重评的判据必须是用户盲听**，
  不是参数好看，也不是我觉得"理论上应该可以"。若将来真要做年龄感迁移，
  走 `tools/voice_pitch.py::youthify()` 的 F0 + 共振峰**同步**移（Praat change gender 口径），
  并用 `--measure` 量 F0 中位数前后对照（目标 200~260Hz）。

### DC74 🔁 年龄感优先用引擎自带的 pitch 参数，后处理移调只作兜底（2026-10-17）→ 由 DC76 取代

- 推翻记录：当天晚上用户实听语感档的原话是「现在的语感开了后感觉像**小黄人和鼠来宝**的音色」。
  错不在"用引擎 pitch 还是用后处理"，错在**把移调当成了年龄感的主力**。
  下面"证据③"里'五档时长完全一致'被我读成了"共振峰自洽"，其实它只证明了引擎**没动时长**，
  恰恰是纯移调的特征。**这条前提是被用户的耳朵证伪的，不是被新资料证伪的** —— 见 DC76。
- 前提：用户说小寻"听着像青年"，要更像少女。我们手上有两把刀：
  ① 合成引擎自带的 `pitch`（edge-tts / Azure / MiniMax 都有）；
  ② 自己写的后处理 `tools/voice_pitch.py::youthify()`。**得先定哪把是默认。**
  这个前提本身是查出来的，不是拍的：少女音的年龄感由 **F0 与共振峰共同决定**
  （PLOS ONE 0081022 / phonalab），只动其中一个必然出怪味。
- 证据：① 引擎 `pitch` 是**在模型内部重新合成**，F0 变了共振峰也跟着自洽，
  这是厂商训练出来的；② `youthify()` 走的是"重采样同时抬 F0 与共振峰 → 相位声码器拉回时长"，
  方向正确（和 Praat `Change gender` 的 PSOLA 同源），但它是**在已经合成好的波形上二次加工**，
  多一道有损环节；③ 本轮实测：晓伊 +0/+15/+25/+35/+45Hz 五档一次渲染出来，
  时长完全一致（7.49s×4），说明引擎只动了音高没动节奏 —— 这正是我们要的解耦。
- 负控：如果反过来（默认走后处理）会怎样？那就要在每条台词上多跑一次重采样 +
  相位声码器，**延迟与失真都加在实时链路上**，而实时 TTS 恰恰最吃延迟；
  而且一旦后面换成 Azure/IndexTTS2（它们自己就有更好的音高与情感控制），
  这层后处理会变成"和引擎打架"的多余环节。守卫：`plan.json` 的候选表里
  **音高一律写成引擎参数**（`"pitch": "+25Hz"`），不写成后处理系数。
- 复查触发：如果引擎 pitch 拉到上限（edge-tts 约 ±50Hz）仍然不够小，
  或者用户选定的音色在高音高下出现金属感/齿音，再启用 `youthify()` 做最后 1~2 档
  —— 届时必须用 `--measure` 量 F0 中位数（目标 200~260Hz）前后对照，不能凭耳朵加码。

### DC75 ✅ 情绪一律落在"演出单"这层中间抽象，不直接写供应商 API（2026-10-17）

- 前提：edge-tts 没有情感标签、Azure 有 9 种 style、MiniMax 有 7 种 emotion、
  IndexTTS2 是 8 维情感向量。**四家接口形状都不一样**，而我们注定要换通道
  （A 路线 edge → B 路线 Azure/MiniMax → C 路线本地）。

- 负控：故意把情绪表的数值全调平（`--selftest` 第 6 项），

### DC51 ✅ 换高清素材时，"scale 减半"只对标量成立；数组 scale 的绑定必须跟着减半（2026-10-15）

- 前提：T30.1 当时写的是"画布坐标完全不动，变的只有素材像素密度和与之配套的 scale"。
  **这句话只对一半。** zrig 里 `scale` 有两种语义，换算方式不同：
  · 标量 `"scale": s` → `p->scale`，通道**乘性**：最终 = `s × p_s`。
    素材 ×2 + s ÷2 ⇒ 任意 `p_s` 下渲染几何不变，绑定**不用动**。
  · 数组 `"scale": [sx,sy]` → `p->scale_x/scale_y`，通道**加性**
    （`compute_draw_state`: `part_sy = scale_y + (p_sy − 1.0)`）。
    基准 ÷2 了而增量还是 1x 口径 ⇒ **形变整整 ×2**。
- 证据：全 rig 11 条 sx/sy 绑定里真受影响的只有 3 条（都在 `mouth_mask`，
  `mouth_cavity` 经 `motion_from` 跟随）；`eye_*_ball` 是标量 scale，**不受影响**
  （第一遍按"@2x + 有 sx/sy 绑定"扫出 9 条，是误判，按语义重扫后自纠为 3 条）。
  算术与渲染都对得上：`ParamMouthOpenY=1` → `44 × (0.02725 + 0.895) = 40.6px`，
  实测开口 40.6px；减半后 `44 × (0.02725 + 0.4475) = 20.9px`，实测 20.9px，
  正好等于 1x 时代的 `22 × (0.0545 + 0.895) = 20.9px`。
  git 对照锁死回归点：`415486d`（1x，22px 素材 + bind 0.895）→ `d83e7a5`（@2x，
  44px 素材 + bind 仍 0.895）。
- 负控：把 3 条绑定还原成未减半，5 项闸全红并精确复现坏数字
  （开口 40.6px、嘴下沿 body_full y=289 vs 下巴 272）；
  反过来问"如果所有 @2x 件的绑定都减半会怎样"——**会把标量件改坏**：
  标量件的绑定是乘性的，再减半等于形变只剩一半。所以闸只盯数组 scale 的件。
- 复查触发：① 以后再出现 `"scale": [sx,sy]` 的新部件（嘴以外），加进来时

### DC56 ✅ `motion_from` 只抄运动，不抄透明度 —— 否则差分件这条路根本不成立（2026-10-16）

- 前提：星形虹膜要跟着常态虹膜一起转一起缩（所以用 `motion_from`），
  但两者的淡入淡出必须相反（一个淡出、一个淡入）。
  我原本以为 `motion_from` 本来就只抄几何 —— **`zrig.c` 的注释也是这么写的**
  （「透明度仍然是自己的」），但代码写的是 `r->p_alpha[mi]`，注释和实现对不上。
- 证据：真机截图 `logs/asset_qa/star_eye_ingame.png`（旧版）—— 切到星星眼之后
  **两只眼睛变成空白眼球**：`ParamStarEye` 把常态虹膜 `alpha` 推到 0，星形件照抄了
  这个 0，于是两张图一起消失。改 `compute_draw_state`：
  `opacity = p->opacity * r->p_alpha[pi] * pose_opacity(r, pi)`（`mi` → `pi`）。
- 负控：在 `git archive HEAD` 的整树副本上跑（`/tmp/nc_mf`，旧引擎 + 新单测）：
  `tests/test_core.c::test_motion_from` 的新用例红 —— 「Swap=1 时差分件必须顶上来，
  画面不能空（**27559 → 0**）」。修后 784 项全绿。
- 逐像素影响面：现有两个 `motion_from` 用户（`brow_*_ghost`、`mouth_cavity`）
  都没有 alpha 绑定，`p_alpha[mi] == p_alpha[pi]`，画面逐位不变。

### DC67 ✅ 物理核心换成官方那套 2D 粒子摆，新旧内核并存一个版本（2026-10-17）

- 前提：用户说「目前还没有真实的物理效果」。我们的摇物是
  **1D 弹簧 `acc = k(target−pos) − c·vel`，输出 `clamp(pos−target, ±max)` 的像素滞后量**；
  官方是 **2D 粒子链，输出 `DirectionToRadian(parentGravity, translation)` 的摆角**。
  本来有个省事的选项：继续给 1D 弹簧加系数、加段数，把"摆得更软"调出来。
- 证据：1D 弹簧的输出在数学上等于**输入的高通滤波** —— 输入不动，输出必然恒为 0，
  这是模型的性质，不是系数没调好。实测佐证就写在我们自己的挂件表里
  （`characters/xiaoxun/design/attachments.json:127`）：给尾巴混了 `ParamBreath` 权重 2.2/1.6，
  呼吸 0.28Hz 下**尾巴只摆 0.3 px**。而官方的摆静止时仍有姿态，是因为摆角由
  "粒子位置相对重力方向"算出来，和输入动不动无关。所以必须换模型（`zphys2`），
  而不是调参。并存一个版本的理由同样是实测代价：现网 **35 条摆**都在用旧字段，
  一次性迁移会把"默认外观不变"的回归闸全部打红，分不清是迁移错了还是内核错了；
  做法是 `rig.json` 新增 `physics2` 段，两套内核同时在跑、逐件迁移、迁完一件对一次 A/B，
  全部迁完后下一个版本删掉旧内核。
- 负控：如果反过来会怎样？原地把旧内核的输出口径从像素改成弧度的话，
  35 条摆的系数量纲同时失准（像素 → 弧度），而且**没有任何一帧的对照基线**可以判断
  "现在是对了还是只是换了种错法"。守卫：`tools/physics_ref.py` 的 600 步对拍（<1e-6）
  与"旧配置产物逐字节不变"两条闸，任一红就说明并存没做干净。
- 复查触发：① 如果以后决定直接跑官方 `physics3.json`（T47.5）而不再自己存参数，
  `physics2` 退化成运行时结构，这条的"并存"安排要重写；
  ② 如果上了 GPU/多线程求解，DC53 的固定步长口径要重新确认一遍。
