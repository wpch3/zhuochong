# 结论登记表（A33）

> **为什么有这份文件**：2026-10-15 用户指出「你自行推翻了很多自己得出的结论，
> 下次再给出结论之前一定要仔细确认，再三检查。旧结论可以推翻，但是检查必不可少」。
>
> 推翻旧结论本身不是问题 —— **不检查就下结论**才是。复盘 2026-10-14 那轮被推翻的四条，
> 每一条都不是算错，而是**下结论的时候少做了一步验证**：
> 前提没验（"踮脚鞋会变扁"）、只做一次模拟就否决（"脚部拆件不可行"）、
> 指标选错（"异号等量 = 修好了"）、否定结论没复查（"docs.live2d.com 不可达"）。
>
> **编号用 `DC`（DeCision）前缀**：`D1~D20` 在 `REQUIREMENTS.md` 里已经是立绘需求系列
> （D19 = 被遮挡区必须 AI 重绘），两套都叫 D 会让"D19"同时指两件事 —— 这正是断代的温床。
>
> 所以凡是**有后果的结论**（会关掉一条路、会决定别人照着做什么、会写进别的文档）
> 都登记在这里，四个字段缺一不可，`tools/selfcheck_repo.py::check_decisions` 会判。

## 怎么写一条

```
### DC## <状态> 一句话结论（日期）
- 前提：这条结论成立的前提是什么，**这个前提本身是怎么验证的**
- 证据：命令 / 实测数字 / 文件路径（至少两样）
- 负控：故意改坏之后它红不红；或者"确定不受影响"的对照项读数
- 复查触发：什么情况下这条会失效，要重新验
```

状态只有三种：**✅采纳** / **❌否决** / **🔁已推翻**（必须写「→ 由 DC## 取代」）。

**❌否决的门槛最高**：否决会关掉一条路，代价最大 —— 必须回答"如果反过来会怎样"，
不能只拿一次模拟定案（DC01 就是这么翻的车）。

### DC42 ✅ 自己渲 3D 不是"做不到"，是"排在 2D 之后"——我准备的否决被实测推翻了（2026-10-15）

- 前提：用户问「能否制作接入 vrchat 以及 3d 模型控制」。我的第一反应是否决自渲 3D：
  本项目是纯 C 的 CPU 软件光栅器（DC26），没有 GPU 后端，3D 要蒙皮 + 深度 + 卡通着色，
  "显然"跑不动。**按 A33.2，否决类结论必须回答"如果反过来会怎样"，所以先去量。**
- 证据：写了 `tools/bench/bench_soft3d.c`（848×1360、2 万三角、3 层 overdraw、
  4 权重蒙皮、透视正确 UV、双线性纹理、MToon 描边遍），
  `gcc -O2 -o /tmp/vb tools/bench/bench_soft3d.c -lm && /tmp/vb 20000 3 2`：
  **单线程 116.7ms / 8.6fps**；去掉纹理与描边 41.3ms / 24.2fps；4 万三角 131.7ms。
  对照本项目 2D 一帧 30.8ms（DC37）——**3D 约贵 4 倍，不是数量级不可能**。
  再叠上分块多线程（2D 上实测 1.66×/2 核）与用户本机核数，30fps 够得着。
  **所以原来那个否决是错的，当场作废。**
- 负控：**第一版基准给出 5 秒/帧（0.2fps）**，差点让我"拿到数据支持的错误否决"。
  复查发现是基准自己错了：随机顶点连三角形 → 每个三角形横跨整个人体包围盒 →
  包围盒扫描 7.9M 像素再被重心坐标剔掉。改成参数化壳体连相邻点（平均三角 400px，
  和真实网格一致）后变成 41ms。**一个支持你预设结论的数字，要比反对你的数字查得更凶。**
  正向对照：无纹理 41.3 → 加纹理 79.1 → 加描边 116.4，三档单调且比例合理（纹理 ~1.9×、
  描边 ~1.5×），说明测的是真实工作量而不是某个退化路径。
- 复查触发：① 如果 2D 主线（T30/T31）收口后仍有预算 —— 这条就该从"排后"变成"开工"；
  ② 如果实测本机多核下 3D 仍进不了 30fps —— 那时才谈 GPU 后端，而不是现在拿它当借口；
  ③ 真正拦住 3D 的**不是帧率而是工程量**（glTF/VRM 解析、morph target、半透明排序、
  AA、摇骨物理，2D 管线里一样都没有），这个判断如果被某个现成的 MIT 纯 C 库推翻，立刻复查。

### DC43 ✅ TTS 唱不了歌，这是接口层面的事，不是调教不够（2026-10-15）

- 前提：用户问「唱歌」。诱惑是把现有 TTS 加上音高参数糊一个"会唱"的效果 ——
  这正是本地音色被用户否过两次（2026-10-11，"机械音"）的那条老路。
- 证据：**输入接口就不是一回事**。SVS（DiffSinger、arXiv 2105.02446）的输入是
  music score —— 歌词 + 逐音符音高 + 音乐时值；TTS 的输入是 text。
  Azure SSML 的 `<prosody pitch>` 作用于整个被包含的文本段，不提供逐音符 F0 曲线入口；
  ElevenLabs v3/v4 走 audio tags（`[happy]`/`[whispers]`），官方明说
  **不支持 SSML `<break>`**，更没有旋律控制，且声明 tags 不保证生效。
  **没有逐音符 F0 入口，就不可能唱准调**，这跟音色好不好、参数调不调没关系。
- 负控：按 A34.6，这条没法"改坏重跑"（否决一条路线无法改坏重跑），给三项替代检验：
  ① 反向找过有没有"TTS 直接唱歌"的生产级做法 —— 找到的全是独立 SVS 栈
  （DiffSinger / NNSVS / OpenUtau / VISinger），没有一个是拿 TTS 改的；
  ② 可证伪判据写死：**只要哪家 TTS API 暴露了逐音符 F0 / MIDI 入口，这条立刻失效**；
  ③ 代价明写：选外挂 SVS 的代价是用户要装 Python + PyTorch + GPU、
  要 1–3 小时标注歌声数据训练音源库（DiffSinger 自动建库只支持中文）——
  这个代价必须写进 UI，不许等用户点下去才发现。
- 复查触发：OpenAI/Azure/ElevenLabs 任一家发布带音符级音高控制的接口；
  或出现可在 CPU 上实时推理的开源 SVS。

### DC17 ✅ 实时 STT 先用 faster-whisper(small/turbo) + Silero VAD，不自己写流式 ASR（2026-10-15）

- 前提：桌宠"听到就回应"不需要字幕级准确度，**端点检测（说完没有）比 WER 更重要**。
  这个前提来自产品定位，不是测量；**如果用户要求做实时字幕，前提就变了**。
- 证据：Whisper 本身不是流式模型（★★ 论文 + 官方讨论）；Whisper-Streaming 论文在 A40 上
  英语平均延迟 3.3s（<https://arxiv.org/html/2307.14743>）；faster-whisper 自带 Silero VAD，
  多家评测给流式 500~800ms（large-v3）/ 200~300ms（turbo）—— **☆ 二手，未实测**。

### DC18 ✅ 双路由判据定为三支柱：敏感→本地、复杂/长→云端、忙/故障→互相兜底（2026-10-15）

### DC32 ✅ "动作时脸部模糊"不在渲染管线，在前端画质档（2026-10-15）

- 前提：**先验前提再下结论** —— 上一轮我记过"stroke 时脸部锐度 −40%"。
  这一轮复现时发现**那个测法是错的** —— 它在画布上框死一个矩形量梯度能量，
  而头一动框里的内容就换了（更多平坦皮肤、更少边缘），测的是构图不是清晰度。
  **旧结论作废**（A33 允许推翻，但必须复验）。
- 证据：改成"互相关配准后再量"，并把脸拆成眼区/嘴鼻区两块分别量：
  嘴鼻区 idle −7.4% / clicked −7.0% / stroke −10.6% / head_pat −11.1%，
  **全部落在 idle 自身的噪声带里**；只有眼区在 stroke(−37%)、head_pat(−34%) 掉，
  而这两个正是把眼睛按住半闭的动作 —— 掉的是"眼睛闭着细节少"，不是模糊。
  真正的模糊在显示层：`web/components/stage.js` 每帧请求 `/api/frame.png?s=60`
  （自动档第 2 级），再被 CSS 拉到 ~680px 高显示。同样显示成 424×680，
  引擎原生渲染眼区锐度 **1641**，先渲 466×748 再 bilinear 缩放只剩 **850（−48%）**。
- 负控：① 量了帧 PNG 的尺寸是否随动作变化（7 个动作 ×14 帧全是 466×748）→
  排除"动作让图变大被缩放"；② 冻结时钟后单独施加旋转/平移，锐度 −2.6%~+11.5%，
  而基线自身复测就漂 3% → 排除"旋转重采样导致模糊"；
  ③ 用户静止截图的裙宽 **155px 精确等于 s=75 档的裙宽 155px**，
  另一张 147px = 同档再被窗口宽度缩 5% → 正向锁定是画质档而不是别的。
- 复查触发：① 用户换了屏幕 dpr 或窗口大小后仍报糊 → 先看 `fitDisplay()` 算出的
  `s` 和 `img.style.height`；② 远程预览带宽不够时自动档会降级，**先降帧率到 6fps，
  再降分辨率**（故意的：清晰的 8fps 比糊的 12fps 好看），如果用户反过来嫌卡再调顺序。

### DC33 ✅ 半闭眼要靠"笑眼件 + 上眼线延迟下滑"，不是把睁眼压扁（2026-10-15）

- 前提：引擎的眨眼是"眼眶开口压扁 + 睁眼件/闭眼件交叉淡化"，
  交叉淡化区间写死在 `zrig.c`：睁眼 `(1−blink)/0.45`、闭眼 `(blink−0.55)/0.45`。
  停在这段里 = 屏幕上同时有半透明的压扁睁眼和半透明的闭眼线。
- 证据：七档阶梯图 `logs/asset_qa/eye_ladder.png` 里 0.5/0.4 两格就是用户截图那只
  "扁平青色透镜眼"（瞳孔和高光全没了），0.5 时左眼还有一个黑钩。
  黑钩来源是上眼线随 blink **线性下滑 21.5px** 压进虹膜：
  A/B 实测 `logs/asset_qa/lash_ab.png`（三列：线性 / 二次 / 不滑）显示 0.3~0.6 这一段

### DC37 ✅ 渲染与 PNG 编码都按"行带"切开并行，闸是逐字节一致而不是性能数字（2026-10-15）

  - PNG 848×1360：91.5 → 42.1ms（**2.17×**）。拆开看原先是 滤波 17ms + deflate 72ms，
    其中 adler32 每字节两次 `%65521` 就占 14.3ms（改延迟取模 → 2.1ms，校验和一字不差）。

- 做法：`zimg` 加 `clip_y0/clip_y1`，四个会写 dst 的函数（`zimg_clear` / `draw_impl` /
  `draw_tri` / `zimg_composite_masked_blend`）都尊重它；每条带各有自己的 scratch/maskbuf
  并在起线程前预分配。PNG 则是每条带自己滤波 + 压成一个 `BFINAL=0` 的 deflate 段
  （段末补空 stored 块对齐到字节），按字节拼接，adler32 按整份原始数据算 —— 即 pigz 的做法。
- 负控：**10 个变异，全部判红** —— 这才是这条结论的分量所在。

  ② composite 忽略 clip → 红 1 条；③ draw_tri 忽略 clip → 红 13 条（34734 字节不同）；
  ④ 各带共享 scratch/maskbuf → 红 18 条（7877 字节不同）；⑤ 单线程路径不重置带缓冲 clip → 红 1 条；
  ⑥ 段末不补对齐块 → PNG 读不回来；⑦ 每段都写 BFINAL=1 → 读不回来；
  ⑧ adler32 只按半份数据算 → 红；⑨ adler32 批长改 65536（溢出）→ 红；
  ⑩ adler32 故意错一位 → **C 侧 stb_image 没抓到，Python 侧 zlib 抓到**。
- ★ ②和⑤ 第一版都**不红**：带遮罩的部件（眼睛/眉毛幽灵）全在头部、正好落在 4 线程的第 0 带里，
  真 rig 上观测不到。②改成在 zimg 层直接做单元负控，⑤改用 8 线程（第 0 带 [0,170) 在眼睛上方）
  才暴露出来。**"闸绿"不等于"闸有用"，得先确认它碰得到被测逻辑。**
- ⑩ 这条尤其要记：**stb_image 不校验 adler32**。所以 C 侧（stb 回读像素）和 Python 侧
  （标准 zlib 解 `/api/frame.png`）是**互补**的两条闸，谁也替不了谁。
- 复查触发：① 以后给 zimg 加任何"写 dst"的新函数，必须同时接 `zimg_clip_range`，
  否则 test_core 的逐字节对拍会红（已验证）；② 若改成脏矩形增量渲染，带划分不再覆盖整幅，
  这套"并行==串行"的闸要重新设计；③ 线程数上限 `ZRIG_MAX_BANDS=8`，核更多的机器要调。
