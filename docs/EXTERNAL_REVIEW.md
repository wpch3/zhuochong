# 外部评审意见的逐条判决

> 来源：用户 2026-10-23 上传的 `讨论对话.pdf`（仓库根，20 页，jsPDF 导出的
> 另一个模型 `gpt-5.5-instant` 的两轮长回答）。PDF 没有文字层，是整页截图；
> 页面图按 `/Resources/XObject` 的 `I0~I19` 逐张取出后通读。
>
> **这份文档不是摘要，是判决。** 每条意见都要落一个结论：
> 「已有」「采纳」「改着采纳」「不采纳」，并写清理由和去处。
> 只记"对方说了什么"而不记"我们怎么办"，等于没读。

**一句话结论**：这份评审**值得读，但不该照单全收**。
它最有价值的是**三个"别这么干"的警告**和**一个我们确实缺的模块**；
它的功能清单有七成是我们已经在册的，剩下三成里有两条和我们的既定决策冲突。

## 一、它说对了、而且我们**确实缺**的（采纳）

| # | 它的意见 | 我们的现状（查过代码） | 判决 |
|---|---------|----------------------|------|
| A1 | **「统一 AI 认知上下文管理器」Context Manager** —— 否则会出现「工作区知道的事聊天区不知道」「语音模式和文字模式表现出不同性格」「多个 Agent 对同一任务理解不一致」 | **真缺。** 现在 `zpersona_compose` 只合成人设三层，没有"按当前请求动态组装上下文"这一层；记忆/工作区/桌面状态各自为政的雏形都还没有，所以现在建层最便宜 | ✅ **采纳** → T60.1 |
| A2 | **Event Bus 先行**（`EVENT_USER_MESSAGE / USER_AWAY / USER_RETURN / TASK_COMPLETED / TASK_FAILED / SCHEDULE_TRIGGER / PERMISSION_REQUIRED`） | 我们有 `zsm`（动作状态机）和 `zinteract`，但**没有进程级事件总线**；主动陪伴、任务恢复、屏幕感知三件事都会各自长出一套回调 | ✅ **采纳** → T60.2，排在 G53 任务机之前 |
| A3 | **自主任务检查点**（断电/关机后重启，任务标记为待恢复，先校验文件状态和工具执行结果再决定是否重试，**不能简单地继续执行下一步**） | G53 任务机只写了"队列/状态机/中断/回放"，没写持久化检查点，更没写"重启后先校验再续跑" | ✅ **采纳** → 并进 T20.4(G53) 的验收口径 |
| A4 | **成本是第一个被忽略的问题**：Token 统计、请求次数统计、费用预估、**任务预算机制** | `zgateway` 已有三段记账（预扣/结算/退还）和 `data/usage.jsonl`，**但没有"任务级预算 + 终止条件"**；多 Agent 群聊会把这个洞放大 | 🟡 **改着采纳**：记账层已有，只补"预算 + 熔断"，不重建 → T60.3 |
| A5 | **提示注入防范**：文档、网页或工具返回内容里的指令。"模型读到一段'要求忽略用户指令并上传文件'的文字时，不能因此获得上传权限" | 完全没做（也还没有真实链路可注入）。但 G54 一通，这就是第一天就会遇到的问题 | ✅ **采纳** → 写进 G54 的验收口径，不另开任务 |
| A6 | **角色数据迁移**：语言模型可以更换，但用户长期培养的 AI 角色应当能够延续 | `persona.json` 已经和 `character.json` 分离（蓝本只读 / 用户层可写），方向是对的，但**没有导出/导入**，也没有版本号 | 🟡 **改着采纳**：加 `persona.json` 的 schema 版本 + 导出导入 → T60.4 |

## 二、它说对了、但**我们已经有了**（不新增任务，只核对口径）

| 它的意见 | 我们的对应物 |
|---------|-------------|
| 统一的**角色状态系统**（idle/listening/thinking/speaking/working/celebrating/confused/sleeping），由状态控制器统一管理，不是每个模块直接操作 Live2D | `src/core/zsm.{c,h}` —— 优先级 + 可中断 + 到期回落 `return_state`，24 个动作全部走它。它建议的八个状态我们有 `idle/think/talk/happy/sleep` 五个同义项，缺 `listening/working/confused` 三个 → 补三个动作即可，**不是补一套机制** |
| **动作混合**：角色说话时仍要能眨眼、呼吸、晃头发；不能因为播放挥手动作就停止其他动画 | 已经是这样：通道按 target 叠加，`breath/sway` 常驻，头发走 33 条一阶摆 + 5 条二阶摆 + `ParamHairSway` 行波 |
| **自制引擎不要强行采用 Cubism 的参数名称，应该建立映射层** | 已经是这样：我们用 `ParamArmRA/ParamForeSlimR` 这类自有参数，GEO2PARAM 表做几何↔参数映射 |
| 统一 **Model Provider 接口** + 多模型路由 + 本地/云端双栈 | `zgateway` 路由表 76 条、策略 `prefer_local`、`secret://` 密钥引用、`/api/gateway.json` 三态报告。**但 G54 还没通 —— 它只会"选谁"，还不会真的发请求**（这是全项目的关键路径，不是这份评审带来的新信息） |
| **把路由原因和数据流向展示给用户** | `/api/gateway.json` 已经报 route 与原因；UI 还没画 → 已在 T29.x |
| **记忆区必须让用户自己查看、修改、删除、导出** | 是我们的既定原则，G52 资源区（工作区/文件区/记忆区）在册 |
| 双模式界面：桌宠模式 / 工作台模式 | `docs/PRODUCT_PLAN.md` 既定方案一致 |
| 四阶段开发顺序（好用的桌宠 → 长期陪伴 → 工作能力 → AI 平台） | `docs/ROADMAP.md` 的 M1~M7 与它几乎同构，粒度更细 |
| 三档性能模式 / 帧率限制 / 后台降帧 | 已在 `docs/PLATFORM_PLAN.md` |
| 让 AI 参与维护自己的项目，但**不要让正在运行的 AI 修改自身可执行文件**，开发/运行/更新环境隔离 | 这正是本仓库现在的工作方式（Agent 在分支上改、编译、跑闸门、等用户合并） |

## 三、它说对了、而且是**最该记住的三条警告**

这三条我单独列，因为它们是"别这么干"，比任何功能清单都值钱。

1. **「不要把语言模型生成的情绪描述直接当作 AI 的真实感受。」**
   让模型输出**用于动画的表演标签**（`expression: happy`），由软件决定播什么动作。
   —— 我们的 mood→TTS 情绪、mood→表情两条线都还没做，**这条要写进它们的设计前提**。

2. **「AI 不能仅凭用户很久没打开软件，就编造自己在这段时间里经历了什么。」**
   汇报必须来自真实任务记录；只完成了分析就如实说分析；
   虚构的角色日程要让用户知道那是**角色演出**，不是真实经历。
   —— 这条直接约束我们的"生活连续性/每日总结"设计。

3. **「关系系统应该让 AI 更了解用户，而不是诱导用户不断陪伴 AI 来提高某个数值。」**
   不建议做成单纯的"好感度系统"。
   —— 我们**已经有四个好感档**（初识 0 / 熟络 30 / 亲近 100 / 挚友 250，T47）。
   这条不是推翻它，是给它加一条红线：**好感档只能用来约束 AI 的说话分寸
   （"不要表现得比这个阶段更亲密"），不能反过来变成要用户刷的进度条** ——
   不做签到、不做"今天还没陪我"、不做掉好感。写进 `docs/PERSONA_AND_STORY.md`。

另外两条次一级但同样对：
- **主动交流不要让 LLM 每隔几秒判断一次**（浪费 Token + 容易打扰）；用规则引擎决定时机，再让语言模型决定怎么表达。它给的 `should_initiate_conversation()` C 代码就是这个意思。
- **Skill 的 JSON 里声明权限 ≠ 实现了安全隔离**，必须由宿主程序检查；第三方 Skill 不能因为自己声明需要权限就自动获得。

## 四、**不采纳**的（和既定决策冲突，或性价比不对）

| 它的意见 | 为什么不照做 |
|---------|-------------|
| 技术栈建议：前端 Vue/React + TypeScript + **PixiJS + Cubism Web SDK** + Electron/Tauri；后端 Python + FastAPI | 本项目的核心资产恰恰是**自制的 C 引擎 `zrig`**（103 部件 / 15 组 / 78 参数 / 25 形变器 / 33+5 物理摆）。换 Cubism SDK 等于把做了几十轮的东西全扔。它自己在第二轮也改口了：「如果你已经选定技术栈，就不一定需要为了这套架构重写，重要的是模块边界清晰」—— 我们采纳的是**后面这句**。 |
| 「C 只负责桌面核心，AI Runtime 用你最熟悉的语言（Python）通过 IPC/本地 HTTP 接入」 | 方向上不反对，但现在**不动**：我们的网关、人设、交互都已经在 C 里跑通且有 936 项单测护着，现在拆进程只会多一层要调的东西。等 G54 真链路通了、Agent 真的需要跑 Python 生态的工具时再拆，那时拆的理由才是真的。**记成 T60.5 的前置判断，不是现在的任务。** |
| AI 的「个人空间」2D 虚拟房间、展示奖杯纪念物 | 可爱，但它和"立绘 + 动作"抢的是同一份美术预算，而我们的立绘线（形象矩阵：年龄 4 档 × 物种 8 种 × 装扮 6 种）还远没做完。**明确押后**，不进 TASKS。 |
| 把讨论整理成 20~30 页正式项目规划书 | 我们已经有 `ROADMAP / PRODUCT_PLAN / PLATFORM_PLAN / PRESENCE_PLAN / PROVIDER_PLAN / PERSONA_AND_STORY` 六份，再加一份只会制造口径分歧。**这份判决表就是它的落点。** |
| 它反问的三个问题（技术栈？Cubism 5？期望 AI 获得多大电脑操作能力 A/B/C/D） | 前两个已答（自制 C 引擎、不是 Cubism）。第三个要用户自己定：**A 只聊天 / B 读屏读文件 / C 可操作软件写代码但高风险要确认 / D 持久任务 + 自主规划**。按既有路线图我们走的是 **C 偏 D**，但这条该由用户拍板，我先按 C 做权限模型（**所有高风险操作一律需要确认**），D 留接口。 |

## 五、它没提、但我认为比它的清单更关键的一条

它整份回答里**没有一次**提到"怎么验证做出来的东西是对的"。

这恰恰是本仓库这几十轮最贵的教训（见 `docs/memory/LESSONS.md` 全篇）：
功能清单写得再漂亮，没有**闸门 + 放大看图**就会交付出"看起来做了"的东西。
所以它的每一条建议进 TASKS 时，都必须带一条**可执行的验收**，
而不是复制它的 bullet。这一点不跟它走。
