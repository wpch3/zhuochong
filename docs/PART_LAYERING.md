## 一、Live2D 靠这五件事做到"完整 + 局部覆盖 + 层次"

### 1.1 一件一张**完整**的图（含看不见的部分）

Live2D 的每个 ArtMesh 是一张**独立、画满**的图。被别的件挡住的地方**也必须画出来**，
并且切口要往外多画一圈（日文社区叫 **塗り足し**，英文 bleed），
因为形变一发生，原来挡住的边就会露出来。

> 这一条是所有"Live2D 感"的地基。**只要有一件是按遮挡关系"切出来"的，
> 它一动就会露白/露缝** —— 我们现在的长发件（G66.24/G66.25）就是反例：
> 它不是画出来的长发，是从成品图上"抠多边形 + 平涂补齐"的拼块，
> 所以边是直的、拼缝是 1px 亮线、发尾是等高切齐。

### 1.2 层次 = **绘制顺序**，不是"切割"

Cubism 里"谁压谁"只有一条规则：`Draw Order`（绘制顺序）。想露出就调整顺序，
**不靠把图切成互补的形状**。所以同一件在不同表情下都能保持完整轮廓。

我们的 `rig.json` 也有 `layer`（全序单值），这一条**已经对**。
问题不在"没有顺序"，而在**顺序只有一个维度**：长发要么全在手臂上、要么全在手臂下，
没法"左半边在手上、右半边在手后"。

### 1.3 局部覆盖 = **クリッピングマスク（Clipping Mask）**

官方手册（<https://docs.live2d.com/en/cubism-editor-manual/clipping-mask/>）：
在要裁的 ArtMesh 的 `Clipping ID` 里填**遮罩 ArtMesh 的 ID** 即可。
要点：

| 事实 | 细节 |
| --- | --- |
| 多张遮罩 | ID 用**逗号**分隔，多张取**交集**（`ArtMesh1, ArtMesh2`） |
| 遮罩本身可以不可见 | 把它的**不透明度设 0%** 仍然能当遮罩用 —— 这是官方推荐的"参考用遮罩"做法 |
| 数量上限 | Native / Web **36 张/模型**；Unity **64 张/场景**；Native 打开 `_useHighPrecisionMask` 可去掉上限 |
| 计数方式 | 按 **ID 排列组合**去重：`A,B` 与 `B,A` 在 Native/Web 算同一张，Unity 算两张 |
| 遮罩全部隐藏时 | **裁切被解除**（被裁的件完整显示），不是"被裁件消失" |

> 最后一条值得单独记：**我们引擎现在的行为和官方相反** —— `zrig.c` 是"遮罩隐藏 ⇒
> 被裁件一起消失"。做表情/换装开关时两者观感完全不同（官方会"整块冒出来"）。
> 这一条要进 T66.21b 的合规表。

### 1.4 遮罩的**白边**是官方承认的坑，且有官方解法

手册原文：遮罩轮廓上**半透明的部分**会把底下 ArtMesh 的颜色透上来，于是轮廓出现一圈"rim"。
官方给的规避法：

1. 复制一份遮罩 ArtMesh；
2. 把 `Clipping ID` 指向**副本**；
3. 把副本**放大**到把原件的轮廓完全盖住；
4. 副本不透明度设 **0%**；
5. 副本与原件**做同样的变换**。

> 这正好对应我们量到的 `hair_long_back` 里 **1.93% 的 1–2px 亮缝**（G66.25）：
> 那是拼块边缘的半透明带互相透色。**不是"画得不好"，是遮罩/透明边缘的固有现象**，
> 有标准解法。

### 1.5 变形器层次（Warp / Rotation Deformer）

`パーツ（Part）` 是**分组节点**（有自己的不透明度与显示开关），
变形器可以挂在 Part 上，网格挂在变形器下 —— 于是"整束头发一起弯、单股再各自弯"
是**树**，不是扁平的位移数组。这也是"层次"的另一半含义：
**不只是前后遮挡，还是父子变形的嵌套**。

### 1.6 开源实现里的等价物（用来对照我们的引擎设计）

- **Inochi2D**（`github.com/Inochi2D/inochi2d`）：`Mask` 是**一等节点**，
  内部持有 `MaskSource[]`（每个含 `maskSrc` + `mode`），渲染时
  `drawList.pushMask(mode)` … 子节点 … `drawList.popMask()`（见
  `source/inochi2d/nodes/visual/mask.d`）。也就是说：
  **遮罩不是挂在某件上的一个字符串属性，而是一段"绘制区间 + 模式（含反向）"**。
  另外 `part.d` 有 `isMasking`（任何视觉节点都能当遮罩源）、`composite.d`（混合模式）、
  `solo.d`（互斥显示）、`meshdeformer/latticedeformer`（网格形变）。
- **pixi-live2d-display**（`github.com/guansss/pixi-live2d-display`）：把官方 runtime
  重写成"高层 API"，说明社区普遍的做法是把 `draw order + clipping` 当成渲染管线的
  **第一等公民**，而不是后加的特例。

## 二、我们和它的差距（拿第七问的四个 bug 对照）

| 维度 | Live2D | 我们（现状） | 第七问里的表现 |
| --- | --- | --- | --- |
| 一件一张完整图 | 强制（含塗り足し） | **没做到**：长发是抠图+平涂拼块，手臂是六件补丁 | 发尾一刀切、举臂成团 |
| 遮盖求解 | 只靠 Draw Order | 也是 Draw Order（**对**） | — |
| 局部覆盖 | Clipping ID，可多张取交、可反向 | `parts[].mask` 单值、无反向、无求交 | 长发/手臂无法交错 |
| 遮罩隐藏语义 | 裁切**解除** | 被裁件**消失** | 换装/表情开关观感不同 |
| 分组/父子 | Part + 变形器树 | 骨 + 网格，**扁平**（G66.3 已记：一片顶点只能被一条通路驱动） | 整束头发不能既跟头又跟身体 |
| 残留处理 | 重画，不"洗" | 用颜色判据"洗"，且洗成了近白（G66.24） | 灰紫腕带 / 幽灵手 |
| 边缘 | 预乘 alpha + 遮罩副本放大 | 距离斜坡软 matte + LANCZOS（**这个是做对的**，见 G4p） | — |

## 三、三套方案（可叠加，建议 A → B，C 只在必要时局部用）

### 方案 A：**部件完整 + 裁切收边**（保住现有引擎，重做素材）

**做什么**

1. 所有会露出的件重画成**完整图 + 塗り足し 6–10px**，特别是：
   - 长发：拆成 **后发 / 侧发 ×2 / 胸前发 ×2 / 头顶**五组，每组一张完整图；
   - 袖子：**上臂 / 前臂 / 袖口环**三件，袖口独立跟腕；
   - 手：重画默认件（G66.27），`pad` 改成带阴影的楔形。
2. 遮罩能力扩到 Live2D 同级：`mask` 支持**数组（交集）** + `mask_invert`；
   语义改成"遮罩隐藏 ⇒ 裁切解除"。
3. 遮罩白边按官方解法：给关键遮罩（眼眶、嘴）配一张**放大 + 0% 透明度**的副本。

**成本**：素材为主（长发 5 张 + 臂 6 张 + 手 3 张 ≈ 14 张），引擎改动小。
**风险**：仍是"全序单值 layer"，长发与手臂**互相穿插**的场景（抬手时手穿过头发）
只能选一个顺序 —— 但这个场景在小寻的日常动作里很少。
**能修掉**：G66.24 / G66.25 / G66.26 / G66.27 / G66.28 的大部分。
**验收闸**：每件出"静止拼回 ≡ 原图（≤2/255）"+"角度压力姿势 0 空洞"两张机检，
外加腕/肘/发尾三处 3× 目视图。

### 方案 B：**区域遮罩（region mask）**——引擎能力，解决"交错"

**想法**：Live2D 用"拆件 + 排序"绕过交错；我们可以更进一步：
给每件声明若干**区域**（矩形/多边形 + 在该区域内的排序），
渲染时**按区域**决定顺序。等价于"局部 z 序"。

**接口草案**（只是提议，未实现）：

```json
{ "id": "acc_hair_long", "layer": 58,
  "regions": [
    { "rect": [0, 0, 848, 620],  "layer": 260 },   // 上半身：在手臂之上
    { "rect": [0, 620, 848, 900], "layer": 120 }    // 腕部：让手压住头发
  ] }
```

**成本**：引擎要加"区域覆盖层 + 逐区域裁剪的绘制桶"，估算 200–300 行 C + 8 条单测；
素材不用重画。**风险**：区域边界会出现**硬接缝**（同一个件被切成两个绘制段），
必须配"边界羽化/重叠带"，否则又回到"硬直线"的老毛病。
**建议**：先把 A 做完，B 只做"两三个区域"的最小版本，用来解决"手穿过发"。

### 方案 C：**深度带（z-band）**

给每件的每个区域一个深度值，渲染时全局排序（软件光栅下等价于逐像素 z 缓冲）。
**优点**：最接近 3D 的正确性。**缺点**：与我们"逐件合成 + 遮罩"的管线冲突很大，
且 Live2D 社区也不用它 —— **不建议**。记在这里只是为了让"为什么不用"有据可查。

### 更好的办法？两条来自社区经验、值得抄的

1. **不要用"切割"解决遮挡**：这条是 Live2D 与 CLIP STUDIO 教程反复强调的。
   我们的 `tools/cut_from_sheets.py` 路线（从成品图抠）**根本上是错的**，
   它只能产出"看起来对、一动就穿帮"的件。（参考：CLIP STUDIO 官方 tips
   `tips.clip-studio.com/ja-jp/articles/2684`，本项目 `tools/clean_hair_residue.py` 里已引用）
2. **长发按"束"分，不按"整块"分**：日本社区做长发模型时普遍把头发拆成
   前发 / 侧发 / 后发 / 胸发，每束 3–5 个网格段，**每束单独定层次**。
   这样"手穿过头发"是"某一束排在手后面"，而不是"整头长发在最上或最下"。

## 四、为什么不能现在动手

用户的这一轮要求是**先讨论、观察、规划、记录**。而且方案 A 要动：

- `acc_hair_long` / `hair_crown_long`（长发底图）
- `arm_*` 六件、`hand_l/r`
- 眼线件（`eye_l_lash_up` 之类，G66.28 需要）

按项目规矩，**受保护基线（teen rig / body_full / 九态眼件 / 闭眼笑眼件 / 眉毛件）
不能单方面改**，必须先出方案 + 目视证据给用户确认。

**所以本轮只交了这份文档 + GAPS 的七条实测记录。** 下一轮建议顺序：

1. 先做 G66.31 的两件 QA 工具（分层隔离探针 + 素材残留体检）——**不动美术**，
   但让后面每一刀都能"关了看"；
2. 再做 G66.24（洗掉长发里的幽灵手/袖口）——**只删不画**，风险最低、收益最大；
3. 然后 G66.28（眨眼三件套）与 G66.27（手）——都要动受保护件，先给图；
4. 最后才是 G66.25/G66.26（长发与袖子重造），按方案 A 执行。
