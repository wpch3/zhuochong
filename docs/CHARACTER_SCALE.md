# 角色规模与"自定义形象生成空间"

> 起因：用户第七问第 6 条 ——「只做七个 AI 吗？市面上出名的 AI 就这些？
> 本地 AI 形象要自定义 → 要给自定义生成空间。还有更好的想法？出几套备选方案。」
>
> 状态：**2026-10-26 提案，未动任何代码。** 角色设定在用户确认前仍只是提案。

---

## 一、先把问题问对

现在 `characters/` 下有八个目录：

| 角色 | 素材 | 状态 |
| --- | --- | --- |
| 小寻 | teen（四形态里一个） | 有素材 |
| 闪电 / 神鱼 / 双喜 / 童林 / 小晨 / 星璇 / 月见 | 无 | `contract_only`（39 骨契约 + 8 挂点 + 四形态 planned） |

"只做七个够不够"这个问题，答案不是"再多做七个"。原因是：

1. 用户要的是**本地 AI 形象可自定义** —— 预设再多也填不满这个需求；
2. 每个角色 × 四形态 × N 套服装 × 兽娘件，是**乘数**关系。
   按 7 角色 × 4 形态 × 5 服装 = 140 套 rig 来算，纯手工不可能收敛；
3. 真正值钱的是**"长出新角色的机制"**，而不是角色数量本身。

**结论：目标从"做七个角色"改成"做一套能长出任意角色的管线 + 若干示范角色"。**

## 二、市面上"出名的 AI 形象"为什么不能当清单抄

大致分四类（只描述类别，不点具体商业角色做设定，避免抄袭）：

1. **虚拟主播型**（有 Live2D 模型、有直播、有性格）：数量以千计，头部的只有几十个；
2. **虚拟歌手 / 官方企划型**：有版权方、形象固定；
3. **AI 助手型**：很多产品**根本没有形象**（纯对话），有形象的也多是静态头像；
4. **开源社区型**（Inochi2D / Live2D 示例角色、开源 VTuber 工具链的示例模型）：
   这类才是我们真正可以对标"规格"的 —— 它们的特点是**形象与引擎分离**，
   模型是数据包，引擎不认识"小寻"。

第 4 类给的启示很直接：**形象必须是"数据包"，不能是代码里的分支。**
我们现在（`character.json` + `skeleton.json` + `forms.json` + `design/sockets.json`）
方向是对的，缺的是**打包、导入、以及"没有美术也能出一个能动的形象"**。

## 三、三套备选方案

### 方案 A —— **参数化生成器**（没有美术也能出形象）

**一句话**：把"一个角色"拆成一组**可调参数**，跑一条命令生成骨架 + 占位式的**真素材**
（不是程序画的 SVG，而是按参数驱动的分层重绘/取色，仍走 `check_assets` 的真伪闸）。

参数维度（对应已有的 41 骨契约）：

| 维度 | 参数 | 落到哪 |
| --- | --- | --- |
| 体型 | 头身比 1:3.5~1:7、肩宽、腰位、腿长 | `skeleton.json` 骨长 |
| 形态 | 少女 / 萝莉 / 青年女性 / Q 版 | 同一骨架的 4 组骨长 + 4 套网格密度 |
| 五官 | 眼型 9 态基座、瞳色、眉形、嘴型 | 眼件/眉件/嘴件配色 + 网格 |
| 发型 | 前发 6 型 × 后发 6 型 × 侧发 3 型 × 呆毛 2 型 | 发件槽位 + 独立束 |
| 兽娘 | 耳（猫/狐/鹿/狼/兔）× 尾（4 型）× 角（3 型） | `design/sockets.json` 挂点 |
| 服装 | 上装/下装/外套/鞋袜/配饰 各 3~6 型 | 部件集合 + 槽位覆盖 |

**成本**：中高（要做 4 体型 × 6 发型 × 6 服装的**基础件库**）。
**风险**：容易退化成"换色"，看着像同一个角色 —— 必须靠"发型/兽娘/服装"三个维度拉开差异。
**收益**：用户点几下就能出一个**可动**的自定义形象；也是我们做 140 套 rig 的唯一现实路径。

### 方案 B —— **上传立绘，半自动拆件**

**一句话**：用户给一张正面立绘（或 AI 生成的一张），我们自动定位五官/关节 →
自动拆件 → **人工校正界面**（拖几条线）→ 出 rig.json。

流程（6 步，每步都要有"不合格就停"的闸）：

1. 抠底（去背景）→ 透明 PNG；
2. 定标：虹膜质心 / 瞳距 / 鼻尖 / 口角 / 肩线 / 肘 / 腕 / 胯 / 膝 / 踝（模板匹配 + 手工微调）；
3. 拆件：按"完整画 + 塗り足し"规则从**分层 PSD** 或**单图**切（单图需要重绘被遮挡区，
   这是最贵的一步，正是我们现在踩的坑 —— 见 `docs/PART_LAYERING.md`）；
4. 网格：按件自动布 4×4~10×12 网格；
5. 绑参数：眼球/眨眼/口型/头发束 自动接线，其余手工；
6. 出包：`character pack`（见方案 C）。

**成本**：最高（拆件与重绘是瓶颈）。
**风险**：第 3 步"补画被遮挡的部分"必须人工或 AI 重绘，**不能糊**。
按用户"不许假素材"的规矩，自动拆件出来必须人工过一遍才能进库。
**建议**：先做**半自动**（只自动第 1、2、4、5 步，第 3 步给人做），
把"最难的一步"留给人，反而能保证质量。

### 方案 C —— **形象包（character pack）**：让 A 和 B 的产物都能装进来

**一句话**：定义一个**可导入导出的形象包格式**，里面是"数据 + 素材 + 校验"。

```
packs/<pack-id>/
  pack.json          # id / 名字 / 版本 / 作者 / 许可 / 本体尺寸 / 依赖
  character.json     # 人设（性格、口癖、声音、开场白）
  skeleton.json      # 骨契约（39~41 根，可扩）
  forms/<form>/      # teen / child / young / chibi 每形态一套
    rig.json         # 部件 + 网格 + 动作 + 物理
    sprites/*.png
  outfits/<id>/      # 服装包：覆盖哪些件、加哪些件
  motion/            # .motion3 兼容包（已有）
  expressions/       # .exp3 兼容包（已有）
  voices/            # 可选
  checksums.json     # 每文件的 sha256
```

**为什么它排第一**：格式一旦定下来，方案 A、方案 B、以及"手搓的 7 个角色"
**走同一条入库路径**；新增角色**不需要改 C 代码**（已有的
`check_form_portable` / `mod_lint` / `check_skeleton` 就是按这个思路做的闸）。
**成本**：低（主要是把现在的散装目录规范化 + 写导入导出 + 校验）。
**风险**：定得太早会限制后面；建议只钉**最小公共字段**，其余放 `x-` 扩展位。

## 四、还有更好的想法？（三条）

1. **"形象 = 骨架模板 + 外观包"两层分离**：
   骨架（骨长、网格密度、动作曲线）按**体型模板**共享（少女/萝莉/青年/Q 版各一套），
   外观（配色、发型、服装、兽娘件）才是每个角色独有的。
   这样 140 套 rig 里真正要单独做的是 **140 套外观 + 4 套骨架**，工作量降一个数量级。
   我们已经有"41 骨契约"这个地基，**这条路是顺势的**。
2. **把"性格"也参数化**：现在 `character.json` 的 persona 是一段文本；
   可以拆成"语气（敬语/口语）＋活跃度＋吐槽率＋口癖表"四个旋钮，
   让同一个外观换一套旋钮就是"另一个 AI"。这对"多兽娘人设、性格各异"是直接支撑。
3. **兽娘件做成"可关开关"的挂点组**（`design/sockets.json` 已经有 8 个挂点）：
   耳/尾/角各自能一键关回纯人类 —— `shenyu`（鹿娘）的 contract 里已经这么写了，
   把它固化成**机检闸**（缺件时 `status` 必须是 `partial`，不能是 `full`）。

## 七、用户的追问：「形象包会不会把每个 AI 变成套皮的 VTuber？」

这是本文最重要的一个问题，比技术选型重要。我的判断写在这里，供决策留痕。

### 7.1 风险是真的，但风险不在"包"，在"包里装什么"

- **套皮**的定义：外观不同，**行为相同** —— 同一套动作、同一套情绪反应、同一套说话节奏；
- **独立个体**的定义：外观、行为、**记忆**、**与用户的关系**都不同。

如果形象包只装"骨架 + 贴图 + 服装"，那它就是一个皮肤库，做八个角色就是八个皮。
**所以问题不是"要不要做包"，而是"包的语义定在哪一层"。**

### 7.2 我们手上已经有行为层的差异化基础（不是从零开始）

| 层 | 现有承载物 | 能不能按角色不同 |
| --- | --- | --- |
| 外观 | `forms/<form>/rig.json` + sprites | 已经是数据 |
| 动作 | `actions[]`、`.motion3` 外部动作（T66.21 已通） | 可以每角色一套 |
| 表情 | `.exp3`（T66.22 已通） | 可以每角色一套 |
| 情绪→姿态/参数 | `mood_params`、`poses.mood_map`、`tail_flick` | 已经是数据，且**每个情绪节奏不同** |
| 反应规则 | `config/interactions.json`（18 条） | 可按角色覆盖 |
| 性格/口癖 | `character.json` persona、`dialogue.json` | 已经是数据 |
| 声音 | `voices/` + lipsync 包 | 已经是数据 |
| 记忆 | 记忆区（`docs/memory` 的运行时对应物） | 待做，但天然是 per-character |

也就是说：**"独立个体"的差异本来就该写在数据里，而不是写在代码里。**
统一底层不是套皮的原因 —— 相反，**统一底层是"让每个角色都能一样好"的前提**：
八套代码 = 八个独奏者，谁都不能变强；一套管线 + 八份行为档案 = 交响乐团。

### 7.3 所以包的语义要从"外观包"升级成"**角色包**"

形象包（character pack）里应当装五样东西，缺一不可：

1. **骨架 + 外观**（形态 / 服装 / 兽娘件 / 物种轴）
2. **动作与物理**（自有动作集，可覆盖默认；自己的摆动刚度、尾巴节奏）
3. **情绪档案**（情绪 → 表情 / 姿态 / 参数曲线，允许每角色一套）
4. **性格与反应**（persona、口癖表、`interactions` 覆盖、主动说话的频率）
5. **声音与记忆种子**（音色包 + 初始记忆/称呼/关系）

并且规定：**包可以覆盖任何默认行为，不只换图。**

### 7.4 一条必须守住的线（机检闸）

"套皮"之所以会发生，是因为**没人强制新角色带自己的行为**。所以加一条硬闸：

> 一个新角色如果只有外观、没有**至少 3 个独有动作 + 2 条独有反应规则 + 1 套独有情绪映射**，
> 它在 `forms.json` / 包里只能标 `skin_only`，**不允许标 `full`**。

这样"套皮"不是被禁止，而是**被明确标注**：你可以做皮肤，但你不能把皮肤说成角色。

### 7.5 另一个反直觉的观点：标志性特征要能被机检

真正让一个角色"是它"的，往往是 2~3 个**标志性特征**（小寻的鲸鱼发夹与长发、
神鱼的鹿角与短尾、某个角色的口头禅与歪头习惯）。
建议每个角色在 `character.json` 里声明 `signature[]`（至少 3 条），
并且其中至少 1 条是**行为**（如"生气时会飞机耳 + 尾巴夹紧"）而不是纯外观 ——
这条能被 `interactions` / `mood_params` 机检，也能被用户一眼认出来。

### 7.6 结论

- **目标照旧**：形象包 + 可扩展管线，不是"再多做七个角色"；
- **但把包改名改义**：不是"皮肤包"，是"**角色包**"（外观 + 行为 + 声音 + 记忆种子）；
- **加一条闸**：没有独有行为的只能算 `skin_only`；
- **兽耳/兽尾属于"物种轴"**，是角色包里最容易被当成"皮肤"的一层 —— 所以它更要有
  自己的行为（耳抖节奏、尾巴情绪映射），才不会被读成贴纸。这也正是 `G66.32` 里
  "左右耳独立 / 尾巴四姿态"要修的实际理由：**行为差异要能被看见**。

## 八、用户的追问：「做成形象包，是不是更能做出服装、配件、配饰、动态动作和视觉效果？」

是，而且这正是形象包**最大的实际收益**——但要先把"包"从"一张图 + 一套骨架"扩成**槽位体系**，
否则服装和特效会重新变成"改 rig 的散活"。

### 8.1 为什么包能救这一块

现在做一套新衣服，流程是：改 `outfits/<id>.json` 覆盖躯干/袖/腿/鞋的贴图 → 手动确认层号与
遮罩关系 → 如果带新配件，还要手工往 rig 里加件、想层号、接参数。**每加一次都要碰 rig。**

包的做法是把这些变成**声明**：

| 轴 | 包里怎么表达 | 就绪度 |
| --- | --- | --- |
| 服装 | `outfits/<id>/` 覆盖哪些件 + 新增哪些件 + 各自的层/遮罩 | 机制已有（`zpet_set_outfit`），缺"新增件"（T66.20b） |
| 配件/配饰 | `attach/*.json` 挂在 `design/sockets.json` 的命名挂点上（8 个） | 挂点已通（T66.19），缺"饰品件本身" |
| 动态动作 | `motion/*.motion3.json`（已能导入）+ `physics` 参数块 | 通（T66.21） |
| 表情 | `expressions/*.exp3.json`（已能导入） | 通（T66.22） |
| 视觉效果 | `fx/*.png` + `fx.json`（参数门 + 生命周期 + 加算/混合） | **缺口最大**，见下 |

### 8.2 视觉效果（FX）要单独成为一"类"，不能再当散件

现有 FX 是 8 个 `fx_sparkle_*` 这样的散件，靠一条 `ParamStarEye` 当总闸、
靠 `idle` 的 `ParamSparkle1..8` 各自排班。这套能跑，但**加第二种特效就会互相打架**：
没有"效果"这个容器，谁都想占 300+ 的层号，谁都想抢同一个参数。

建议在包里引入 **effect 声明**（纯数据，不动引擎语义）：

```json
{ "id": "star_eye_burst", "gate": "ParamStarEye", "layer_base": 300,
  "parts": ["fx_sparkle_1", "...", "fx_sparkle_8"],
  "schedule": { "mode": "flick", "interval": [0.6, 1.8], "scale": 0.8 },
  "blend": "add" }
```

好处：①一个效果一个门，互不干扰；②层号自动分配，不用人肉数；
③"这套特效属于哪个角色"变成数据，换角色就换 `fx/`。

### 8.3 但要守一条：包不等于"无限换皮"

第八节的槽位一旦齐全，技术上可以做"一套外观 + 换十套衣服"的十个角色，它们会**长得像同一个人**。
所以配一条机检闸（与第七节的 `skin_only` 同源）：

> **每个角色至少有一套"只属于它"的服装 + 一个专属配饰 + 一个专属特效**，
> 且这三样必须写进 `character.json` 的 `signature[]`。缺任何一项 ⇒ 不许标 `full`。

### 8.4 结论

- 服装 / 配件 / 动作 / 表情 / FX **都应该走包**，这正是包的价值；
- 但 FX 必须先有"效果容器"（gate + layer_base + schedule + blend），否则会重演"抢层号、抢参数"；
- 槽位齐全之后，**"专属三件套"是防止套皮的最后一道闸** —— 不是禁止共享，而是要求每个角色
  至少有一样东西是别人没有的。
