# 骨骼体系 v1（humanoid_v1）—— 先做骨骼底层还是先做别的

日期：2026-10-25 ｜ 第六十五问 ｜ 任务 T66 ｜ 契约文件 `characters/<id>/skeleton.json` ｜ 闸 `tools/check_skeleton.py`

## 0. 一句话结论

**先做骨骼底层，而且顺序是「契约 → 少女刚体骨接全 → 网格骨（变形器树）接进 rig → 参数/物理驱动 → 服装挂点 → 其余三形态复用」。**
黑边按你说的排到最后。理由不是"骨骼重要"这种空话，而是体检出来的三条事实：

| 事实 | 数字（本机实测） | 后果 |
|---|---|---|
| 引擎已经有变形器树，但 **rig 里一处都没用** | teen 103 个部件里用 `parts[].deformer` 的 **0 个**；chibi 47 件里 **0 个** | 手臂/头发/裙摆现在只能整块刚体转，做不出 Live2D 那种"根骨带动梢部" |
| 四个形态的骨名**对不上** | teen 15 根（含 forearm/elbow_fold/hand）· chibi 9 根（缺 6 根） | 同一套服装/动作写到 Q 版上，那段身体**悄悄不动**，没有任何报错 |
| 骨名没有契约 | 只有 `groups` 里随手起的 id | 换 AI 角色/加配件全都要重编一遍坐标 |

所以这一轮先把「骨」这件事**变成契约 + 闸**（已完成），再往上接。

## 1. 现状体检：引擎的"骨"其实有两层，第二层闲置

| 层 | 引擎里的东西 | 能力 | teen 用量 | 备注 |
|---|---|---|---|---|
| **刚体骨** | `rig.json` 的 `groups`（pivot + dx/dy/rot/sx/sy） | 绕关节转/缩/移，父子串联 | 15 根，103 件全部挂满 | 现在所有动作、物理、视线都只作用在这一层 |
| **网格骨** | `rig.json` 的 `deformers`（逐顶点，可 `parent` 成树，可 keyform） | 逐顶点形变、键形插值、父子复合 | 25 个网格，**却都平铺挂在部件上、没有父子、也没被任何部件反向引用** | P0 刚做出来的能力，**还没进内容** |
| 参数/绑定 | `params[].binds`（`group`/`part`/`deformer` + `param`） | 参数 → 骨 | 78 个参数 | 绑到 deformer 的极少 |
| 遮罩 | `parts[].mask` | 二值遮罩（无软边） | 13 件 | 见 §4 的 P1-3 |

一句话：**引擎那层已经就位，缺的是"把内容接上去"和"四形态共用一个骨架语义"。**

### 2.3 挂点（`kind: socket`）—— 2026-10-25 T66.19 落地

`socket_head_top` / `socket_face` / `socket_ear_l/r` / `socket_neck` / `socket_wrist_l/r` / `socket_back`。
挂点**没有 pivot**：它的位置 = 父骨 pivot + 一根"形态锚点 + 相对偏移"的向量，所以骨一转挂点跟着转，
而挂点的**名字**和所在骨由角色级契约固定。这就是"配件不漂"的机制保证。

四段分工，谁都不许替别人说话：

| 段 | 文件 | 回答什么 |
|---|---|---|
| 声明 | `characters/<角色>/skeleton.json`（`bones[]`，`kind: socket`） | **有哪些**挂点、各自挂在谁的骨上 |
| 位置 | `characters/<角色>/design/sockets.json` | **在哪**（`ref` + `pos_rel` + `unit`，四形态共用一张表） |
| 尺度 | `forms/<形态>/design/anchors.json` | 这个形态的锚点实际在哪（像素尺度） |
| 落地 | `forms/<形态>/rig.json` 的 `sockets` 段：`{id: {group, pos}}` | 引擎唯一认的东西 |

配件挂上来只要两行：

```json
{ "id": "acc_ear_cat_l", "socket": "socket_ear_l", "dpos": [0, 0] }
```

`pos` 由生成器算好一起写进 rig（美术/QA 工具要读它），但**位置只有一个来源**：挂点 + `dpos`。
引擎装载时会核对两者，差 > 1px 就报错 —— 这种不一致不会立刻显形，只会在换装/换形态之后
表现成"配件漂了"，那时候已经没人记得是哪一次改的。

探针：`GET /api/sockets.json` 给每个挂点的 `pos`（骨架摆在哪）与 `screen`（过完父骨矩阵之后
**这一刻**在哪，画布像素 × 当前缩放）。"配件跟着手腕动"能不能机检，就看 `screen` 动没动。

姿势关节诊断：`GET /api/bones.json` 返回当前帧肩/肘/腕世界 pivot、两段长度、included angle 与 flex（伸直=0°），并将非刚体膝标成 mesh-only。`/api/frame.png?debug=bones` 与该端点共用 `group_matrix()` 世界坐标：肩→肘红线、肘→腕绿线、腕蓝点。**不能用 rig 静态 pivot 直接当动作姿态**；这曾使骨骼叠图在手臂实际转动后仍看起来像 bind pose，已在 T31.19 修正。IK 原型与限制校准见 `docs/qa/IK_STAGE1.md`、`characters/xiaoxun/design/joint_constraints.json`；未完成目标映射之前，solver 不接入正式 motion。

★ 为什么位置不写进 `skeleton.json`：那是角色级契约，一份；形态的尺度在四份 `anchors.json` 里。
把 teen 量出来的像素写进角色级文件，等于让 teen 的像素去将就 chibi（T2.2.0 量过：平均偏 92 画布像素）。

★ 这一节的旧文（2026-10-24）只写了"挂点没有 pivot，位置永远由父骨算出来"——而当时
**没有任何一件配件挂在上面，rig 里连 `sockets` 段都没有**。声明齐全、实现为零，闸也全是绿的。
T66.19 才把它接到地（LESSONS 439）。

### 2.4 豁免（waivers）

Q 版手臂是整件素材，所以 `forearm_l/r`、`elbow_fold_l/r`、`hand_l/r` 六根骨在 chibi 上**显式豁免**，

"动作里那段不动"，肉眼几乎看不出来。

## 4. 自制 Live2D 底层还缺什么（体检结论，按优先级）

### P0 —— 不补就做不出"Neuro-sama 级"的动

1. **单网格多骨加权（skinning 权重）**。现在一个网格的位移只能来自**一条** keyform/amount 通路，
   两骨不能同时影响同一片顶点；裙摆要"上缘跟腰、下缘跟摆动"，只能靠多张网格叠。
   → 每顶点 `weights: [{bone, w}]`；验收：两骨反向各 50% 时顶点位移为 0。
2. ~~**父级 warp 位移场传给子**（G58.8）~~ —— **2026-10-25 T66.10 已做**。
   父件网格的位移场按 (cols×rows) 控制点做双线性取样、喂给子件的每个顶点；
   子件没有自己的网格时**借父件的分辨率**现搭一张（"三条带子不用各写网格"）。
   闸：`test_parent_warp_inherit`（三层：父场 → 有网格的子件 → 无网格的子件 + 不挂链对照）。
3. ~~**keyform 插值只有线性**~~ —— **2026-10-25 T66.11 已做**。
   每段可写 `ease`（`linear`/`in`/`out`/`in_out`/`out_back`/`out_elastic`/`out_bounce`）、
   `step`（阶梯），或四个数的三次贝塞尔 timing curve（`[x1,y1,x2,y2]`，x 必须 ∈[0,1]）。
   写错的三种情形（不认识的名字 / 第一组 key 写 ease / 贝塞尔 x 出界）都在加载时报错。
   闸：`test_keyform_ease()`，含手算值对拍（贝塞尔 `[0.25,0.1,0.25,1]` 在 x=0.5 → 0.8024）。
   **还没做**：内容侧还没有一条真 keyform 用上缓动（现有 rig 全是 amount 通路），见 T66.11b。
4. **骨骼继承模式**。Live2D 的 親子付け 有"固定位置/只继承旋转/只继承缩放"等模式；
   现在只有一种（全继承），做"头转但帽子不转"这类件就得多加一根骨。
5. **软边遮罩**。现在 `mask` 是二值（见 LESSONS 408：二值遮罩会把羽化切掉）。

### P1 —— 决定"好不好用"、会不会反复返工

6. **骨架可视化/量骨工具**：在预览上点两下就得到 pivot，并写回 `skeleton.json`。
   现在 pivot 全靠人在图上读坐标 —— 这是最容易量错、也最难发现的一环。
7. **网格编辑/权重涂刷**：哪怕最简版（矩形区域 + 衰减），否则"每根骨独立"只能靠手写控制点表。
8. **参数融合与多绑定优先级**：同一参数驱动多根骨时的叠加顺序（现在按数组顺序）。
9. **混合栈补齐**：`normal/multiply/screen` 已有，还缺 `overlay/add` 与"只在剪影内混合"。
10. **每帧网格采样成本**：103 件 × 平均 3×3 控制点还好，但 512 部件 × 5×5 会变贵 ——
    需要脏标记（参数没变就不重算）。现在每帧全算。

### P2 —— 生态与互操作

11. **`cubism model3.json` 的结构映射**：参数表、动作、物理这三类 json 是公开格式，可以映射进来；
    但 **`.moc3` 的网格数据是专有格式**，需要 Cubism Core（授权），我们不做，也不假装能读。
12. **导出**：把我们的 rig 导成别人能读的形式（图 + 参数曲线），用于社区互换。
13. **多语言/多角色的骨名别名**：不同画师的习惯叫法（`shoulderL` vs `arm_l`）要有映射表，
    否则"兼容其他 AI 形象"每次都要改闸。

## 5. 3D 模型与三渲二：在计划里吗？

**分开答，因为两者状态不同：**

| 项 | 在计划里吗 | 现状 | 位置 |
|---|---|---|---|
| **3D 模型（VRM/VRoid）能不能吃进来** | ✅ 在 | 只做了源码/架构预审，**没有加载过任何真实 `.vrm`**；结论是"现在不做主程序集成" | `docs/VRM_SPIKE_REPORT.md`（P1.12）· `ROADMAP` T33（0/3）· `DC42`（自渲 3D 排在 2D 主线之后） |
| **三渲二（3D 渲染成 2D 卡通观感）** | ❌ **不在** | 全仓库只有一处提到"卡通"且与渲染无关；没有任何 toon/描边/色阶 的规划 | 本轮新写：`PRODUCT_PLAN.md` 第十节 + T66.7 |

我们的定位（写进计划，避免以后又争一遍）：

- **主线永远是 2D 分层 Live2D 路线**：CPU 软件合成、零外部依赖、透明小窗、包体小。
  这是已经跑了 1000+ 单测和四形态素材的那条路。
- **3D 是可选第二后端**，前提是：① 2D 主线达标；② 有合法可测的 VRM 样例；
  ③ 用独立预览进程/目录，不把 Unity/VRC SDK 拖进主程序。
- **三渲二** = 3D 后端上的一组着色规则（色阶量化 + 边缘描边 + 单方向硬阴影 + 高光带），
  它的**前置**是 3D 后端存在，所以排在 VRM 之后；但它反过来对 2D 有用：
  同一套"卡通着色规则表"可以给 2D 立绘做**光照一致性**（比如夜里整体压暗、暖光提亮），
  这部分可以提前做（T66.8），不需要 3D 后端。

### 7.2 三条踩出来的接线规矩（都写进生成器注释 + 测试）

1. **`parts[].deformer` 要点链的「根」，不是中段。** 引擎有一条校验：纯变换节点（没有 part、没有 parent）
   必须被某个部件点名，否则整份 rig 拒绝加载。第一版点的是中段 → `hair_ahoge_root` 没人引用 →
   teen 加载失败、**静默退回 chibi**（预览 exit 3 才暴露）。
2. **中段骨的绑定必须带 `lag`。** 没有 lag 时根和梢同相位被推，看着是一根刚性钟摆。
   `selfcheck` 里早有这条闸（梢部形变带行波延迟），尾巴那四条就是被它抓出来补的。
3. **绑定表必须按「根→中段→梢」排。** 逐条 `insert(0)` 会把中段排到根前面，闸照样报红；
   现在同一参数的链式绑定整体倒序插入。

## 9. 多角色：脚手架 + 「契约态」（2026-10-26，T66.23）

### 9.1 问题：八个角色里只有一个是"看得见"的

硬需求是**每个 AI 独立形象**（八个角色、四形态、多套服装、多种兽娘）。到这一轮为止的实况：

| 角色 | skeleton.json | forms/*/rig.json | 美术 |
|---|---|---|---|
| xiaoxun | ✅ 39 根骨 | teen / chibi | 全套 |
| 其余 7 个 | ❌ 没有 | 0 | 0（只有 `character.json` + `dialogue.json`） |

这个状态有两个坑，性质完全不同：

1. **手工抄骨架**：想给第二个角色做形象，得照着 xiaoxun 的 `skeleton.json` 抄 39 根骨。
   抄漏一根的表现是「动作里那段不动」，肉眼几乎发现不了 —— 这正是骨架契约存在的理由。
2. **"目录看着像做完了"**：手工建一个 `characters/xxx/` 再拷一份骨架进去，目录结构和做完的角色
   一模一样。闸只查「骨架和 rig 对不对得上」，两边都空着就互相通过了 —— **空对空也是绿**。

### 9.2 解法

| 层 | 改动 |
|---|---|
| 新工具 | `tools/scaffold_character.py`：从 `humanoid_v1` 模板派生 `skeleton.json`（骨名/父子/kind/required/waivers/forms/chains 一字不差）+ `design/sockets.json`（8 个挂点）+ `forms.json`（四形态全 `planned`）+ 一份 `todo` 清单。`--list` 打印八个角色的真实进度 |

### 9.3 为什么 `sockets.json` 可以继承，`head_body_ratio` 不行

挂点位置是 (`ref`, `pos_rel`, `unit`) 三元组：`ref` 指向形态锚点（头顶/眼线/腕/腰…），
`pos_rel` 是相对该锚点的偏移，`unit` 说明用头高还是身高归一。**换角色后要重标**，但重标只影响
"配饰挂在哪"，不影响骨、动作、换装 —— 所以继承一份当起点是可接受的，代价写在
`inherited_from` 字段里（谁抄的谁）。头身比不一样：它是给人体比例定标的标量，
`xiaoxun` 就因为"设计稿 1:6 / 实测 1:4.65"翻过一次车，凭空写一个数必然错。

## 10. S5 施工记录（2026-10-26）：单网格多骨加权（T66.9 / P0-1）

> 这是 Live2D 底层"每根骨都能独立绑"的最后一块硬骨头。

**问题**：一片顶点只能被一条通路驱动。裙子只有一张网格 + 一根旋转骨时，
要么整条跟着腰走（下摆僵），要么整条跟着摆走（腰被扯）。Live2D 里靠"多条骨 + 蒙皮权重"。

**做法（不引进第二套坐标系）**：给每张位移网格加一张**逐顶点权重表**
`deformers[].w`，长度 `(cols+1)*(rows+1)`、取值 0~1，乘在该网格每个顶点的位移上。
两张互补的网格 = 两段骨的线性混合：

| | 上缘 | 中段 | 下缘 |
|---|---|---|---|
| 「跟腰」网格 w | 1.0 | 0.5 | 0.0 |
| 「跟摆」网格 w | 0.0 | 0.5 | 1.0 |
| 实测位移 (dx,dy) | (10, 0) | (5, 6) | (0, 12) |

为什么不是"每顶点一组骨名 + 权重"（真·蒙皮）：那要引入 LBS 权重求解与另一套坐标，
和现有的"形变器树 + 逐顶点位移场"冲突；而在这个渲染模型里，**位移场加权与两段骨
线性混合的结果是同一个**，代价却小得多。以后真上 3D 后端时再换 LBS。

**闸（三道，缺一不可）**：
1. `w` 长度必须等于顶点数（不按"取前几个"糊过去）；
2. 取值 0~1，越界**拒载**（不静默钳位 —— 钳位会把"写错了"变成"看起来有点怪"）；
3. 同一部件上（没写 `w` 的按 1 算）**逐顶点权重和 ≤ 1** —— 位移是相加的，
   和 >1 就是同一个顶点被推两次：画面是"裙子比腰多走一倍"，而单看每张表都合法。

C 侧加载时三条都拦（`zrig.c load_deformers`），静态侧另有一份
（`tools/check_skeleton.py` ⑥c，`make check` / `selfcheck` 都会跑）。

**实测（[测试锁]）**：`test_deform_weights()` —— 权重混合三档全对；
不写权重的负控实测 (10,12)（两向叠加，正是"被推两次"的画面）；
权重和=2 与长度=3 两组负控均**拒载**。`make test` 1343 项 / 0 失败。

**内容侧为什么先不套**：现有三处同部件多网格（`skirt_main` / `arm_?_fore` / `acc_hair_*`）
是**用零位移分区**表达"这段只有这段动"的，本身没有叠加问题；硬套权重只会改画面、
不会更对。权重留给真正的多骨混合场景 —— 例如裙子按 T66.16 拆成独立件之后，
上缘跟腰、下缘跟摆（已记为 T66.9b）。

## 11. 父组继承度（T66.12 / 2026-10-26）

> Live2D 里每根骨都挂着一行「父级继承」：跟随方式、影响度、是否继承旋转/位置。
> 之前我们的组只有"全跟"一种，等于所有部件都绑死在父组上 ——
> 想让发梢只跟平移不跟转头，只能靠多写一份反向关键帧去抵，抵不干净就抖。

**做法**：组上新增 `inherit`，四个取值，缺省 `full`（老 rig 一个字节都不用改）：

| `inherit` | 含义 | 典型用途 |
|---|---|---|
| `full`（缺省） | 位置 + 旋转 + 缩放，全跟 | 普通部件、子骨 |
| `rotation` | 只吃父组的旋转，**不吃平移** | 绕某点转但不跟着挪的挂件 |
| `position` | 只吃父组的**平移**，不吃旋转 | 想让发梢跟着身体上下、但不跟着转头甩出去 |
| `none` | 完全不继承，自己在世界坐标里 | 想单独摆位的部件（如贴在屏幕上的 UI 挂件） |

**关键实现细节（踩过）**：父矩阵的平移列 `pm[4],pm[5]` **不等于**父组的位移 ——
它里面混着"绕枢轴旋转"产生的那一段（实测 −110px）。要表达"只跟平移不跟转"，
必须取 `pm(父枢轴) − 父枢轴`，直接读平移列会把旋转的副作用一起带进来。

**验收（[测试锁]）**：`test_group_inherit()` —— 父组平移 10px + 旋转 90°、挂点 (110,10)：

| `inherit` | 实测屏幕位置 |
|---|---|
| `full` | (100.0, 10.0) |
| `rotation` | (-10.0, 110.0) |
| `position` | (120.0, 10.0) |
| `none` | (110.0, 10.0) |

写错名字（`"rotatoin"`）⇒ `zdiag_error` 拒载整份 rig（不许拼错一个字母就静默退回 `full`，
那样"发梢不跟着转头"的 bug 会以最难查的方式出现）。`make test` 1379 项 / 0 失败。

## 12. 软边遮罩（T66.13 / 2026-10-26）

> 硬掩码能切掉直角，但切不掉「颜色不一致」这条阶差 —— 那句话（LESSONS 408）是这一节的起点。

**问题**：遮罩是 alpha 相乘（`zimg_composite_masked_blend`），语义没错，但**边缘仍是一刀切**：
睫毛被遮罩横着截断、补片的平涂色和原画差几度时，边界换到哪儿都一眼可见。

**做法**：部件级 `"mask_feather": 半径`（画布像素，0~16）。遮罩画完后对它的
**alpha 通道做一次可分离盒式模糊**（横一趟、纵一趟 = 三角斜坡），再照常做 alpha 相乘。
按设备像素取整（`r × scale`），所以 0.5 缩放下写 4 在画面上是 2——和素材同一尺度。

**为什么是盒式而不是高斯**：要修的不是斜坡的数学形状，而是「有没有斜坡」。
盒式两趟是线性成本，也不会像小半径高斯那样被截断成"看起来没生效"。

**分块渲染的坑（这轮最容易漏的一条）**：模糊要读相邻行，而每条带只画自己那几行。
只读本带 ⇒ 带的接缝上会出现**两条水平硬线**，比原来的问题更难看。
所以有羽化的遮罩**先把读写区上下各扩 r 行**再画、再模糊，写回时仍只碰本带。
`test_mask_feather` ③ 用 1 线程 vs 4 线程**逐字节比**守这条（现在是 0 字节不同）。

**验收（[测试锁]）**：
- `test_mask_feather()`：不写羽化时中间 alpha ≤2 个（硬线）；写 6 时斜坡 **24 个像素**、
  单调递增、遮罩正中仍 255；多线程与单线程逐字节相同；三条负控（半径 17 / 有羽化没遮罩 /
  把 6 写成字符串）**全部拒载**。
- `make test` 1392 项 / 0 失败；`make asan` 同数（这一轮 ASAN 抓到并修掉了
  `band_ftmp` 在 `zrig_free` 里没释放的 270KB 泄漏）；`make selfcheck` 715 / 0；`make smoke` 321 / 0。
- 静态闸 `check_skeleton.py` ⑥d：`mask_feather` 必须是数字、0~16、且真的挂了 mask。

**内容侧：量了，但没套**（诚实记账）。试了两处，都用放大图看过：

| 试的地方 | 改动像素 | 眼看结论 |
|---|---|---|
| 眼件遮罩（socket）2px | 505 px | 眼角边缘变糊。动画眼睛要的是脆边，**不套** |
| 透け眉（`brow_?_ghost`）6px | 120 px（最大差 18 级） | 眉毛可见那条其实**整个落在刘海内部**，边缘不在画面上，改了几乎看不出 |

证据图：`docs/qa/2026-10-26-feather-eye.png`、`docs/qa/2026-10-26-feather-brow.png`。
⇒ 这个旋钮是给「遮罩边界真的横穿可见区」的件准备的（例如 T67.6 手臂三件套的袖口遮罩）。
**能加不等于该加**：没有量到改善就不写进 rig。眉毛是受保护件，真要动先出方案与放大图。

## 13. 裙摆两段骨混合：现状与下一步（T66.9b，2026-10-26 设计，未施工）

> T66.16 已经把裙子从躯干里切出来并接上了 `skirt_root → skirt_mid` 两级骨链。
> 但「上缘跟腰、下缘跟摆」这件事**还差一块引擎能力**，这一节把它写清楚，免得下一个人
> 以为只是"调一下参数"。

**现在是怎么动的**（读代码得到的事实，不是估计）：`ParamSkirtSway` 同时推
`skirt_root`（1.2°/单位）与 `skirt_mid`（2.6°/单位、0.11s 行波延迟）；
`skirt_main` 的链上被标了 `skirt_root`（部件 `deformer`）和 `skirt_mid`（三张网格的 `parent`），
于是 `deform_chain_matrix()` 把**两级旋转都作为刚体变换**连乘到整件上 ——
所有顶点（含裙腰）一起吃这两个旋转。裙腰离中段骨枢轴 113px，2.6° 就是约 5px 的拖拽。

**为什么权重 `w` 解决不了它**：`deformers[].w` 加权的是**逐顶点位移场**
（`deform_vertex_at` 的产物），而这里的位移来自**链上的刚体矩阵**。
两者在渲染管线的不同阶段，权重够不到矩阵那一层。

**要加的能力（下一步，编号 T66.9c）**：让一条链的刚体变换也能按**行**加权，
即「这个顶点吃这条链的多少」。数学上就是 `p' = (1−w·I)p + w·(M p)`，逐顶点做。
影响面：
- `zimg_draw_mesh_bend_blend_t` 现在只收一个矩阵；要收「基础矩阵 + 加权矩阵 + 每顶点 w」；
- 分块渲染不受影响（仍是逐像素、无跨行依赖），但 `test_render_bands_identical` 要重跑；
- 静态闸要新增一条：`chain_w` 长度 = 顶点数、0~1、**同一部件上刚性权重与网格权重各自求和 ≤1**
  （两套权重相乘的关系必须写清，否则会出现"被推两次"的老问题）。

**判据（施工时必须先写下来，否则又会变成"看起来动了"）**：
把 `ParamSkirtSway` 推到满格，量三个位置 —— 裙腰（y≈595）位移 **≤1px**、
中段（y≈708）位移约为现在的 60%、下摆（y≈810）位移 **≥ 现在的 100%**。
三项同时成立才算做成；只量"下摆动了"没有意义（现在下摆也在动）。

**为什么这一轮不动手**：它要改渲染管线的公共函数签名，而裙件是受保护基线的一部分
（用户明确要求动之前先出方案 + 证据 + 放大图）。这一节就是那份方案的第一步。

## 14. 逐顶点加权刚体（T66.9c / 2026-10-26，引擎完成、内容待确认）

> 第 13 节写下的问题：`skirt_main` 的链上同时标了 `skirt_root` 和 `skirt_mid`，
> 两级旋转作为**刚体**连乘到整件，裙腰跟着一起转。逐顶点权重 `w`（T66.9）
> 加权的是**位移场**，够不到矩阵层。这一节补的就是矩阵层。

### 14.1 做法

形变器上新增 `"chain_w": [w0, w1, …]`（长度 = 该部件网格的控制点数）：

```
p_out = (1 − w_q) · M_skip · p_q  +  w_q · M_full · p_q
```

`M_full` 是整条链，`M_skip` 是**把写了 `chain_w` 的那个节点当恒等**之后的链
（`deform_chain_matrix_skip()`）。因为
`lerp(A·p, B·p, w) ≡ ((1−w)A + wB)·p`，实现上只需要算两个候选坐标再插值，
不涉及旋转的球面插值，也不引入第二套坐标系。

`zimg` 侧新增 `zimg_draw_mesh_chainw_blend_t()`；原来的
`zimg_draw_mesh_bend_blend_t()` 与它共用同一个内核（`mesh_bend_core`），
口径只有一份 —— 这是"网格路 / warp 路必须算出同一个结果"那条老规矩的延续。

### 14.2 加载期闸（四条，前三条拒载、第四条只警告）

| 情况 | 处理 | 为什么 |
|---|---|---|
| 长度 ≠ 部件网格控制点数 | 拒载 | 逐顶点对不上，加权就是错的 |
| 取值超出 0~1 | 拒载 | 钳位会把"写错了"变成"看起来有点怪" |
| 同一部件的链上**两个**节点都写 `chain_w` | 拒载 | 两段骨抢同一片顶点，语义说不清 |
| 部件没有自己的网格 | **只警告** | 同一个链节点常被好几件共用：裙身有网格、里布（`skirt_lining`）是借它的位移场的。这种情况"里布没有网格"是正常的（实测踩到过，当时按拒载做，整份 rig 直接加载失败） |

静态闸另有一份：`tools/check_skeleton.py` ⑥e（长度 / 取值 / 只许一个），不必起引擎。

### 14.3 实测（[测试锁]）

`test_chain_weight()`：3×3 网格挂 `cw_root → cw_mid`（90° 旋转），三排权重 0 / 0.5 / 1：

| 排 | 满格旋转 | w 全 0 | 0 / 0.5 / 1 |
|---|---|---|---|
| 上排 | (200, 0) | (100, 100) | (100, 100) |
| 中排 | (100, 0) | (100, 200) | (100, 100) |
| 下排 | (0, 0) | (100, 300) | (0, 0) |

- 上排 w=0 与"没有那段旋转"逐位一致 → **不吃**；

- 中排落在两者正中 → 线性插值，没有跳档。
- 渲染侧另量**alpha 加权重心**（纯色矩形转 90° 面积不变，像素总数会绿着放过"根本没转"）：
  满格 (99.5, 99.5) · w 全 0 (199.5, 199.5) · 混合 (110.6, 132.6) —— 两者之间。
  这两个端点是几何算出来的（200×200 的块绕上边中点转 90°，重心 (200,200) → (100,100)）。
- 四条负控：长度 8≠9、取值 2、空数组、链上两个 `chain_w` 全部拒载；无网格只警告。
- 新端点 `/api/vertex.json?id=&c=&row=&scale=`（GET/只读，回 `{ok,id,c,row,scale,x,y}`）：
  给某个控制点这一帧的**落点**
  （`/api/partmesh.json` 给的是位移场，量不出"裙腰被按住没有"）。
